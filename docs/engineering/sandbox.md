# 沙箱隔离方案（设计）

> 状态：**设计，未实现** ｜ 对应 Topic 07 ｜ 相关：[threat-model.md](./threat-model.md)

本文是**设计文档**，不是实现说明。文中标为「已实现」的部分只有权限模型与
运行时控制；沙箱本身本次没有代码。

## 1. 要解决什么问题

Agent 会执行两样危险的东西：

1. **模型生成的代码**——如果产品要做「让学习者写代码、Agent 运行并讲解」。
2. **被诱导的工具调用**——工具本身是安全的，但参数可能来自被投毒的内容
   （见威胁模型路径 A、C）。

沙箱要解决的是第二类的**最后一道防线**：即使权限模型放行了一个工具，它
的执行也不应该有能力影响宿主进程之外的东西。

## 2. 与权限模型的关系

**权限模型与沙箱解决的不是同一个问题，两者不可互换。**

| | 权限模型 | 沙箱 |
|---|---|---|
| 回答的问题 | 「这个工具**该不该**被调用」 | 「这个工具的运行**能造成什么**后果」 |
| 拦截时机 | 调用之前 | 执行之中 |
| 拦截对象 | 工具身份 | 工具的副作用 |
| 挡住 | 未授权的工具调用 | 已授权工具的越界破坏 |
| 挡不住 | 模型被诱导调用**已授权**的工具 | 调用本身就不该发生的情况 |

一句话：**权限模型缩小攻击面，沙箱限制爆炸半径。**

具体到本项目：`read_notes` 被授予了 `fs:read`，但如果它内部因为路径拼接
出错读了 `/etc/shadow`，权限模型完全无能为力——它只知道「read_notes 被
允许调用」。这正是沙箱存在的理由。

## 3. 隔离层级

按隔离强度递增排列。**选层的依据是「这个工具能碰到什么」**，不是「它看起来
危不危险」。

| 层级 | 机制 | 隔离强度 | 适用 | 成本 |
|---|---|---|---|---|
| **L0** | 同进程直接执行（当前实现） | 无 | 纯计算、纯内存的工具 | 零 |
| **L1** | 子进程 + `rlimit`（CPU/内存/文件大小）+ 无网络 + 只读挂载 | 中 | 受限的文件读取、计算 | 低 |
| **L2** | 容器（只读根文件系统 + 丢弃特权 + seccomp + 无网络） | 高 | 需要写临时文件的工具 | 中 |
| **L3** | 远程 microVM / 托管沙箱（每会话独立） | 最高 | 模型生成的代码 | 高（依赖外部服务） |

### L0：同进程

当前所有工具都跑在 L0。**这是有意的起点，不是疏漏**：绝大多数学习教练的
工具（读笔记、生成题目、算知识点覆盖度）不碰文件系统也不碰网络，同进程执行
最简单也最快。

L0 的**适用条件是显式的**：工具必须只依赖参数与返回值，不读环境变量、不读
凭证、不发起网络请求、不写文件。

**L0 的风险**：工具实现里的一次 `open()`、一次 `requests.get()`，就把它变成了
L0 上的一个洞，而且这个洞不会被任何权限模型发现——因为权限模型管的是
「调不调」，不管「调了之后干什么」。

### L1：子进程

把工具的执行搬进一个子进程，用操作系统原语限制它：

- `resource.setrlimit` 限制 CPU 时间、地址空间、文件大小、进程数。
- 子进程环境变量**清空**（不继承 `OPENAI_API_KEY` 等凭证）。
- 工作目录设为一次性临时目录，退出即删。
- 网络用网络命名空间或防火墙规则切断。

L1 适合「需要读文件但不该写、不该联网」的工具。它挡不住内核级逃逸，但挡得住
绝大多数应用层事故。

### L2：容器

容器是 L1 的强化版，加上文件系统隔离（只读根 + 明确的可写挂载）、
`--cap-drop ALL`、seccomp profile 限制系统调用、只读挂载宿主目录。

L2 的成本是要有容器运行时。本项目当前是单机 Python 库，引入容器运行时是
**架构级**的决定，不该在实现沙箱功能时顺手做掉。

### L3：远程沙箱

参考实现 `ai-agent-from-scratch` 的做法：`sandbox_executable` 标记的工具，
其源码被送进远程沙箱（E2B）预注册，模型生成的代码在沙箱里跑，沙箱在
`finally` 里销毁。

L3 的优势是**隔离边界不在本进程内**——即便沙箱逃逸，攻击者得到的也不是宿主机。
劣势是引入外部依赖（延迟、成本、可用性），以及一个必须信任的第三方。

## 4. 选层规则

不要逐个工具拍脑袋决定，用一条可判定的规则：

```
工具会读写宿主文件系统吗？        ── 会 ──> L1 及以上
工具会发起网络请求吗？            ── 会 ──> L1 及以上（且需考虑出站白名单）
工具能执行模型生成的代码吗？      ── 能 ──> L3
其它                              ──> L0
```

**默认向上取一级**。不确定时选更强的隔离——因为事后发现某个工具其实会碰
磁盘，代价远高于一开始就多开一层。

## 5. 关键设计点

### 5.1 工具自声明隔离需求，而不是集中配置

隔离层级应该是**工具契约的一部分**，像 `scopes` 一样：

```python
ToolDefinition(
    name="run_python",
    description="运行一段 Python 代码",
    scopes=("exec:run",),
    isolation="sandbox",  # ← 需要隔离
)
```

理由与权限作用域一样：**集中配置会漏**。谁新增了一个工具，谁就该声明它的
隔离需求；运行时不认识这个工具，就没法默认给它正确的一层。

### 5.2 隔离层是执行机制，不是运行时分支

运行时不应该长成 `if tool.isolation == "sandbox": ...`。正确的形状是：

```
Dispatcher → 权限检查 → 参数校验 → 执行器(Executor)
                                        ├── L0Executor: 同进程调用
                                        ├── L1Executor: 子进程 + rlimit
                                        └── L3Executor: 远程沙箱
```

执行器按工具声明选择。运行时完全不知道沙箱的存在——这与「运行时不实现工具
执行」是同一条边界。

### 5.3 沙箱不是权限的替代品

在沙箱里运行一个工具**不代表它有权运行**。反过来也一样。两条检查都要在，
且顺序是：**先权限，后隔离**——不对无权的调用做沙箱启动这种昂贵的事。

### 5.4 沙箱逃逸与凭证

沙箱里**不能有凭证**。这不是「少传几个环境变量」的问题，而是原则问题：
沙箱的边界是「进程能碰到什么」，凭证在环境变量里就意味着沙箱能碰到凭证。
凭证应当由宿主侧的代理层持有，沙箱通过一次受控调用去换取结果。

### 5.5 人工确认：权限之外的第三道门

高风险工具（删除、转账、发邮件）应当要求人工确认。这在 OWASP 分类里对应
T10（Overwhelming Human in the Loop）——引入它同时也会引入「确认疲劳」这个
新问题，所以确认必须**按风险分级**，不能所有工具都确认，否则用户会闭眼点同意。

参考实现的 `requires_confirmation` + `confirmation_message_template` 是这个
机制的一个具体形态。本项目当前**没有**实现，它需要一个暂停/恢复的运行时状态，
属于后续议题。

## 6. 实施顺序

按「先便宜后昂贵、先堵洞后上能力」排序：

| 步骤 | 内容 | 状态 |
|---|---|---|
| 1 | 权限模型：作用域、检查点唯一、可见性过滤 | **已实现** |
| 2 | 契约防护：schema 畸形不崩溃运行 | **已实现** |
| 3 | 工具自声明隔离需求（`ToolDefinition.isolation`） | 未实现 |
| 4 | L1 执行器：子进程 + rlimit + 无凭证环境 | 未实现 |
| 5 | 风险分级的人工确认 | 未实现 |
| 6 | L3 执行器：远程沙箱（仅当产品需要代码执行） | 未实现 |

第 3 步是第 4 步的前置：没有「工具声明自己需要隔离」这个契约，第 4 步只能靠
一张集中配置表，而集中配置表一定会漏。

第 6 步**取决于产品是否要做「运行学习者写的代码」**。这个需求还没进入产品
范围，因此 L3 现在做就是为想象中的需求写代码。

**归属**：第 3～5 步的实现归 **Day 65 Security Review**——沙箱是对威胁模型
T11「Unexpected RCE and Code Attacks」的正式回应，而 Day 65 本就是「按 Threat
Model 逐项检查」的地方。（2026-11-19 决定：此前沙箱与 T6 都没有归属 Topic。）

## 7. 明确不做的

- **不做「安全」的假象**。L0 不等于安全，文档里写清楚比留一句「已做沙箱」有用。
- **不把沙箱当万能药**。它管不了模型被诱导说出不该说的话（威胁模型路径 C）。
- **不在本阶段实现代码执行**。没有产品需求支撑。
