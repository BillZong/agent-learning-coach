## 正文

### 1. 记忆不是向量库

「给 Agent 装一个向量库」是关于记忆最常见的误解。向量检索解决的是
**「从一大堆候选里挑出相关的」**——它是一个**选择**机制，不是记忆本身。

记忆至少有三层完全不同的东西：

| 层 | 存什么 | 谁访问 | 生命周期 |
|---|---|---|---|
| **工作记忆** | 当前这一轮对话 | 模型 | 随上下文窗口滚动 |
| **情景记忆** | 「发生过什么」——某次工具调用、某个结论 | 模型（按需） | 会话内或跨会话 |
| **语义记忆** | 「知道什么」——用户的水平、偏好、已掌握的知识点 | 应用层 | 跨会话，长期 |

只有第三层适合用向量检索。前两层的问题不是「怎么检索」，而是「**哪些内容根本
不该占上下文**」。

这正好对应 LangChain 总结的四类上下文工程手段——**write / select / compress /
isolate**：

- **write**：把内容写到上下文窗口之外（草稿本、笔记、文件）。
- **select**：运行时把需要的内容选进窗口。
- **compress**：保留完成任务所需的 token，丢掉其余。
- **isolate**：把上下文拆开隔离（子 Agent、沙箱、state 的不同字段）。

本项目目前实现了 **compress**（规则式）与 **isolate** 的一部分
（`ExecutionContext.state` 不进模型上下文）。**write** 与 **select** 属后续
Topic。

#### 存储与呈现分离

实现上有一条贯穿全局的原则：**存储与呈现分离**。

```
事件历史（存储，永远完整）  →  ContextBuilder（按预算投影）  →  发给模型的内容（呈现）
```

这条原则的回报不止于「省 token」：

1. **裁剪不丢信息**。模型这一轮看不到的内容还在上下文里；下一轮预算放宽时
   它可以重新出现。**丢弃是不可逆的，裁剪不是。**
2. **策略可替换**。换一套裁剪策略不影响存储，也不影响别的调用方。
3. **可观测**。构建结果携带 token 数与丢弃条目数——「这次请求为什么变短了」
   有答案。

最后一条常被忽略，但它决定了上下文工程能不能被**迭代**。没有观测，你只能
凭感觉调参数；有了观测，你能看出是哪一步的裁剪在起作用。

#### 注意力预算

Anthropic 引用 Chroma 的 *context rot* 研究指出：**随着上下文里的 token 增加，
模型准确回忆其中信息的能力会下降**——这个现象在所有模型上都出现。

结论是上下文必须被当作**有限资源**对待，而且它的边际收益是递减的。因此
「把能装的都装进去」是错的。正确的问法是 Anthropic 给出的那句话：找到
**最小的高信噪比 token 集合**。

对本项目意味着两件事：

- 预算不是「上限提示」，是**要被执行的约束**。一个可以被静默违反的预算
  是 bug 温床。
- 裁剪要有**优先级**。最新的内容最重要，最早的用户诉求（原始学习目标）
  也不能丢。

### 2. 长期记忆：什么值得记

短期记忆（会话）解决的是「这次对话的连续性」；长期记忆解决的是「这个学习者
是谁」。后者的难题不是存储，是**判断什么值得存下来**。

三个条件，缺一不可：

1. **归属**——是关于**谁**的？
2. **耐久**——下次会话还成立吗？
3. **可覆盖**——它属于哪一类事实？

第 3 条最容易被忽略，但它决定了记忆系统的形态。如果「水平从初级变成中级」表现
为「多了一条记忆」，那么画像里就会同时存在两个互相矛盾的水平——**模型看到
矛盾的记忆时，会怎么选？** 没有人知道答案，也没有人能调试。

所以本项目的记忆有唯一键 `(主体, 类型, 类别, 作用域)`，写入时按键 upsert：
新事实**取代**旧事实。副作用是「这条记忆被改过」而不是「多了一条」。

#### 噪声的三道闸

| 闸 | 谁做 | 做什么 |
|---|---|---|
| 抽取提示词 | 模型 | 「没有值得记的就返回空列表」——**空列表是被期望的答案** |
| 准入策略 | 确定性代码 | 内容非空、置信度达标、长度不超标、类别在词表内 |
| 去重与覆盖 | 确定性代码 | 同内容不重复写；同键直接取代 |

第二道闸最重要：**模型说了不算**。把「这条算不算噪声」交给模型判断，等于把
系统的确定性交给了一个不可复现的组件——同一个模型两次判断可能不同，判断本身
就成了新的噪声源。

而且抽取噪声的主要来源不是「模型判断错了」，而是「模型总会给你点什么」。所以
第一条闸必须把「没有」写成一个被鼓励的答案。

#### 召回噪声同样有害

写进去一条无关记忆，它会在每次召回时被注入上下文——占位置、干扰推理。所以
「没有匹配就不返回」是硬要求，不是优化。

召回方式的选择也来自这个系统的性质：学习者的长期记忆是**结构化**的（几十到
几百条，每条带类别与主体），绝大多数召回是「给我这个学习者的弱点」——那是
**筛选**，不是相似度检索。因此本项目用结构化筛选 + 确定性关键词相关度，
不用向量检索：不需要嵌入服务、离线可测、结果可解释。

向量检索适合的是「从一堆非结构化文档里找相关的」——那是 RAG 的问题（Day 11～
12），不是学习者记忆的问题。**把 RAG 的手段用在记忆上，是把两个问题混了。**

### 3. 分层记忆与召回时机

「什么时候召回」比「怎么存」更难。

三种时机，各有代价：

| 时机 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **每轮全量注入** | 打开就把记忆全塞进去 | 模型不用决定要不要用 | 占窗口；无关内容造成干扰 |
| **按需检索** | 模型自己调用工具去取 | 「just in time」，只在需要时占窗口 | 多一次往返；模型可能不取 |
| **预检索 + 按需混合** | 常用的预先给，其余让模型自己取 | 兼顾速度与灵活性 | 边界要人工划 |

Anthropic 描述的「just in time」策略值得特别注意：它不预先加载全部数据，
而是维护**轻量标识符**（文件路径、查询词、链接），让模型在运行时用工具动态
加载。

这个模式对本项目的压缩设计有直接影响：**保留标识符，丢掉内容**。压缩后的
工具结果长这样——

```
「已读取 notes/闭包.md，需要时重新读取。」
```

——模型知道这个文件存在、知道怎么再取，但这一轮不必背着它的全文。这正是
Anthropic 所说的「the safest lightest touch forms of compaction」。

#### 工具描述也是上下文

容易被忽略的一点：**工具定义本身占上下文**，而且每次请求都要重发。

Anthropic 指出「bloated tool sets」是常见失败模式——工具太多、描述重叠，
模型在「选哪个工具」上就出了错。这个项目在 Topic 07 已经处理了这件事：
**无权的工具不给模型看**（`allowed_specs`）。那条权限检查顺带解决了一个
上下文工程问题——可见性过滤减少了上下文里的噪声。

#### 草稿本不是记忆

`ExecutionContext.state`（草稿本）是运行时的内部工作区，**模型看不到**。

这看起来像损失，其实相反：工具可以往里写中间结果（「已经问过用户哪些问题」、
「学习计划草稿」），运行时可以随时读，但这些内容不占模型的注意力预算，也不
会干扰推理。

LangGraph 的 state 设计是同一个思路的更完整版本：state schema 里 `messages`
字段暴露给模型，其余字段隔离起来，只在需要时选取。

**判断标准**：一段内容该放哪，看「谁需要它」。

- 模型这一轮推理要用 → 上下文。
- 应用层或工具要用 → 草稿本。
- 跨会话还要用 → 长期记忆。

### 4. RAG 的检索质量瓶颈

> 本节属 Day 11–12（`11-rag-基础` / `12-rag-and-tool-extension`），此处仅留
> 提纲。

RAG 的瓶颈几乎从来不是「生成」——模型拿到检索到的片段后，生成质量通常不是
问题。瓶颈在**检索**：

- **切分**：按什么边界切？按固定长度切会把一个概念劈成两半。
- **召回**：相关的内容没进 top-k。
- **排序**：进来的内容里，真正有用的排在后面——而模型对上下文位置的敏感度
  并不均匀。
- **来源**：没有引用的检索结果，模型无从判断可信度。

LangChain 引用 Windsurf 的一段话值得记住：

> *Indexing code ≠ context retrieval.*

索引与检索是两件事；把「能索引」当成「能检索好」是常见误判。

### 5. 评估检索而非只评估生成

> 本节属 Day 11–12 与 Day 28（`28-retrieval-evaluation`），此处仅留提纲。

端到端评估（「最终答案对不对」）无法定位问题出在哪一环。要能改进，就必须
**分层评估**：

1. **检索层**：该召回的召回了吗？排名对吗？（recall@k、MRR）
2. **上下文层**：召回的内容进了窗口吗？被裁剪误伤了吗？
3. **生成层**：拿到正确上下文后，答案对吗？

第 2 层是本项目特有的关注点——**裁剪策略会误伤检索结果**。一条被召回的、
恰恰是最相关的那段，可能因为「不是最近的」而被滑窗丢掉。这个问题只有把
「裁剪前」和「裁剪后」都看才能发现，因此 `ContextView` 记录原始与最终 token
数与丢弃条目数不是装饰。
