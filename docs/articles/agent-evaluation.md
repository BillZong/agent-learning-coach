## 正文

### 1. 为什么 LLM-as-judge 不够

LLM-as-judge 是当下最常见的 Agent 评估方案：让另一个模型给回答打分。它有
真实价值——在开放式任务上，人工标注太贵，判官至少能给个排序。但把它当
**门禁**，会立刻遇到三个问题：

**判官本身不确定。** 同一个回答，两次评分可能不同。用一个不确定的东西去验证
另一个不确定的东西，得到的结论也只能是不确定——「这次评估没通过」到底说明
代码退步了，还是判官心情变了？

**判官不可回归。** CI 需要「同一份代码，结论固定」。判官做不到，因此它只能
做监控，不能做门禁。

**判官偏向表面。** 它容易被措辞、长度、格式影响，而不是判断「机制对不对」。
一个把工具错误吞掉、直接编一个答案的系统，在判官眼里可能比诚实地说「工具坏
了」得分更高。

这不是说判官没用，而是说**它需要锚点**：人工标注、任务特定评分表、可对照的
参考答案。Phase 0 没有这些——没有真实教学场景，没有用户反馈，没有标注预算。
所以本项目把语义质量评估**推迟**到 Phase 2，而不是用一个不可靠的判官假装
完成了它。

### 2. 任务集与评分设计

Phase 0 能评估的是**行为**，而且行为可以被精确断言：

```
脚本化的模型响应  +  期望的行为契约  →  通过 / 失败
```

一条用例包含三部分：

| 部分 | 例子 |
| ---- | ---- |
| 输入 | 用户 prompt + 脚本化的模型响应序列 |
| 期望 | 停止原因、工具调用序列、失败工具、输出子串 |
| 断言 | 逐条比对，给出「期望 vs 实际」 |

**为什么脚本化而不是真实模型**：断言要可复现。脚本化之后，「模型做了什么」变成
输入的一部分——用例失败时，失败原因只可能来自运行时，不来自模型的随机性。
这让失败定位从「猜」变成「读」。

**为什么不打 0～1 分**：单个分数会把「哪个断言失败」藏起来。评估的价值在一次
失败时最大，而分数恰恰在那时候最没用。本项目选择让 `EvalResult.failures`
逐条输出：

```
工具调用：期望 ['另一个工具']，实际 ['echo']
```

**期望值要覆盖失败路径。** 一个只包含成功用例的数据集会给你 100% 的绿色，什么
也证明不了。Phase 0 的数据集必须包含：未知工具、工具抛异常、步数兜底、
原地打转、连续失败。测试里有一条专门的断言钉住这个覆盖要求。

### 3. 非确定性系统的回归策略

非确定性不能靠「多跑几次取平均」解决门禁问题，只能**分层**：

| 层 | 确定性 | 用作 | 判据 |
| ---- | ---- | ---- | ---- |
| 机制层 | 完全确定（脚本化模型） | 门禁 | 用例必须全绿 |
| 轨迹层 | 确定（工具调用序列、停止原因） | 门禁 | 同上 |
| 真实模型层 | 不确定 | 监控 | 通过率区间、抽样、趋势 |
| 语义质量层 | 不确定 | 人工/判官 | Phase 2 再做 |

**门禁只放确定性层。** 真实模型层的评估有价值，但它的结论是「最近好像变差了」，
不是「这次提交不能合并」。把两者混在一起，结果通常是门禁被关掉。

**每发现一种新的失败，就补一条用例。** 这是评估集生长的唯一健康方式：不是
为了覆盖率而写用例，而是为了让「下次同样的问题能被抓住」而写。本项目的用例
清单直接来自停止原因表——每一种 `stop_reason` 都有一条对应用例。

### 4. 把评估接进 CI

三层门禁，从快到慢：

```
pytest（机制 + 数据集）  →  examples/reliability_report.py（评估套件，非零退出）  →  make check
```

**数据集是代码资产。** 它住在仓库里（`evals/`），进版本控制，随代码一起评审。
改一条用例就是改一个受审的契约——而不是改一个只有某台机器上存在的表格。

**不随包发布。** `evals/` 属于仓库，不属于 wheel：评估数据集与具体实现版本
绑定，把它装进用户环境只会造成版本混乱。

**CI 不能检查什么**：真实模型的行为、语义质量、线上因果。这些要靠监控与人工
评审，不要让 CI 假装它们被覆盖了。

评估的最终目的不是「拿到一个分数」，而是**在改动之后，仍然知道自己没有退步**。
这个标准下，一个能定位失败的断言集，比一个平滑上升的评分曲线有用得多。
