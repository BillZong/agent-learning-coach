## 正文

### 1. Agent Loop 的本质

写 Agent 最容易犯的错，是把它当成「更聪明的提示词」。实际上 Agent 的能力来自
**信息流的形状**：

```
模型 ──请求工具──> 系统 ──执行──> 结果 ──回填──> 模型
```

这个循环里没有魔法。它做的是把「模型的猜测」换成「模型看到的事实」。

拆开看，每一轮只有三件事：

| 阶段 | 做什么 | 谁负责 |
| ---- | ------ | ------ |
| Thought | 把对话与工具清单交给模型 | `LLMClient` |
| Action | 执行模型请求的工具 | `ToolDispatcher` |
| Observation | 把结果回填给模型 | 运行时 |

三个阶段各自可替换——换模型只改第一段，换工具来源只改第二段。这不是设计上的
洁癖，而是它让「工具可以来自远端 MCP Server」这件事几乎不需要额外成本。

**循环的终止条件是分层的**，这一点比终止条件的数量更重要：

- **主路径只有一个**：模型不再请求工具。只有模型自己知道任务是否完成。
- **兜底有若干**：步数、工具调用数、token、成本、连续失败、重复调用。

把预算当成「目标」而不是「兜底」，就会写出「工具失败就终止」这类过早收敛的
逻辑——模型能自愈的错误被中断掉了。

### 2. 工具调用与状态管理

工具系统（`core/tools`）与运行时（`core/agent`）的分工是清晰的：

- 工具系统回答「有哪些工具」「怎么执行」「结果长什么样」；
- 运行时回答「什么时候调」「调完之后状态是什么」「什么时候停」。

运行时不重复实现校验、超时与归一化——它调用 `ToolDispatcher`，因此本地工具
与远端 MCP 工具的**行为完全一致**。这不是巧合，是有意的：契约一致意味着模型
不需要知道工具来自哪里。

**状态只有一份**，记在 `ExecutionContext` 里：执行身份、事件历史、步数、
草稿本、用量、成本、最终产物。运行时不另设状态，因此「运行发生了什么」只有
一个答案——上下文里的事件序列。

事件比扁平对话列表多出两点：**谁说的**、**什么时候说的**。这两点让历史可以审计
与回放，是「可复现」的技术前提。

草稿本（`state`）是运行时的内部工作区，**模型看不到**。这一点在 OpenAI Agents
SDK 的文档里被写成了一句 NOTE：「Contexts are not passed to the LLM. They're a
way to pass dependencies and data to code you implement」。模型看到的是事实，
不是内部状态——把内部状态塞进提示词只会浪费窗口并干扰推理。

### 3. 上下文窗口的工程约束

上面这套机制有个直接后果：**上下文是有限预算，而事件流在增长**。

每轮工具调用都会往上下文里追加内容——模型的输出、工具的结果、工具结果的
错误信息。跑上十几轮，一个中等复杂度的任务就能把窗口吃掉。

因此上下文管理不是「以后再说」的优化项，而是 Agent 能不能长期运行的前提。
需要回答的问题：

- 什么时候裁剪？按步数、按 token 预算，还是按事件的重要性？
- 裁剪掉什么？工具结果通常是最大的头——但它往往正是后续推理需要的。
- 裁剪后如何保持「每条 `tool_call` 都有对应 `tool_result`」这条不变量？

本项目当前**没有实现**裁剪，事件原样保留并返回。这是已知的最大缺口。

### 4. 失败处理与恢复

失败分三类，处理方式完全不同：

| 类别 | 例子 | 处理 |
| ---- | ---- | ------ |
| 模型能自愈 | 参数不合法、工具报错、工具不存在、远端会话关闭 | 归一化成错误结果回填，循环继续 |
| 运行时失败 | 超时、模型调用失败、预算耗尽 | 返回结果 + 停止原因，**保留已完成的部分** |
| 编程错误 | 客户端实现有 bug、配置矛盾 | 抛异常，不包装成运行结果 |

第一条是「过早收敛」的主要防护：模型能读懂错误并调整下一步，直接抛异常会
中断整个循环。

第二条容易被忽略。**运行时失败不丢弃已完成的成果**——超时与模型失败都返回
部分结果（步数、累计用量、完整对话记录），调用方据此决定是否重跑。最初的
实现里模型失败直接抛异常，与超时的处理不一致，调用方拿到的东西取决于失败
发生在第几步。

第三条的边界要清楚：非 `LLMError` 的异常是编程错误，把它包装成「运行失败」
会让 bug 变成安静的失败。

最后是尚未解决的一半：**恢复**。当前一次运行是原子的——中途失败不会留下可
续接的检查点。断点续跑需要更强的事件模型（可回放的状态机），那是后续议题。
