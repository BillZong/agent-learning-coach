## 正文

### 1. 不可靠的来源

Agent 的不可靠有四个来源，它们的处置方式完全不同。把它们混成一句「模型不稳定」
是工程上最贵的误解。

**模型本身的非确定性。** 同一个输入，两次可能给出不同的工具调用。这一层无法
消除，只能约束：停止条件、预算、以及「模型只能请求、不能决定」的权限模型。
本项目里模型从不直接执行动作——它发工具调用，执行边界在 `ToolDispatcher`。

**工具与外部世界。** 网络会断、文件会变、API 会限流。这一层的处置是
**归一化**：调用级失败不抛异常，而是变成 `ToolOutcome(status="error")` 回填给
模型，让它换参数、换工具或直接回答。工具错误终止整个运行，是可靠性设计里最
常见的错误。

**状态丢失。** 上下文丢了、进度丢了、审批丢了。这一层靠「唯一状态源」解决：
运行的全部状态都在 `ExecutionContext` 里，会话检查点保存恢复所需的全部字段。
少存一样，恢复出来的就不是原来那个运行。

**预算失控。** 循环不收敛、上下文无限增长、成本无声上涨。这一层靠预算兜底——
但预算的定位是**兜底**，不是主路径。

四层里，后三层都能做到确定性；第一层只能被约束。因此「可靠性」不是「让模型
不出错」，而是「**让出错有边界、有痕迹、可恢复**」。

### 2. 失败模式与防御纵深

本项目把失败分成三级，每级只有一个拦截点：

```
调用级失败   → ToolDispatcher 归一化成结果，回填给模型自愈
运行级失败   → AgentRuntime 停止循环，返回已完成的部分结果 + 停止原因
会话级中断   → SessionContext 检查点，恢复后继续
```

**为什么每级只有一个拦截点**：多一个拦截点就多一条「新增路径忘了检查」的
fail-open 漏洞。这个原则在工具权限上体现得最清楚——权限检查放在 Dispatcher
而不是 Runtime，因为 Dispatcher 是唯一的执行边界（本地工具、MCP 工具、
结构化输出的 `final_answer` 全经过它）。Runtime 只负责**可见性**：无权的工具
模型根本看不到，不浪费轮次去试。

**纵深不等于重复。** 纵深是「不同层拦截不同问题」；重复是「同一层检查两遍」。
后者不会更安全，只会让两处判断慢慢分叉。

一个具体的例子：工具失败的处置分三步——失败归一化（Dispatcher）→ 连续失败
计数（Runtime）→ 超阈值停止并上报 `consecutive_errors`（Runtime）。三步各管
一件事：**归一化**让模型有机会自愈，**计数**发现「自愈失败」这件事本身，
**停止**防止继续烧预算。

### 3. 重试、超时与熔断

**默认不重试。** 这是本项目一个明确的取舍：重试的决定需要知道「这次运行值不
值得重跑」，而那是调用方的知识，不是框架的。一个已经花掉三步与两万 token 的
运行，重跑的成本可能比失败更高。运行时只保证**部分结果不丢**——失败时照常
返回已完成的事件、步数与用量。

**超时有两层**：运行级覆盖模型调用与工具执行在内的全部时间；工具级是单次执行
的上限，用 `asyncio.timeout` 实现——它会真正取消挂起的协程，而不是放弃等待。
后者很重要：放弃等待但协程继续跑，等于泄漏一个还在改状态的任务。

**熔断由预算承担，但顺序有讲究。** 步数、工具调用数、token、成本在**步之间**
检查——当前步的调用全部执行完，保证每条 `tool_call` 都有对应的 `tool_result`；
否则转录断裂，多数厂商 API 会拒绝后续请求。连续失败与重复调用在**步之后**
检查，它们指向模型行为，因此比「预算耗尽」更具体，优先上报。

计数住在执行上下文里，不是循环的局部变量。否则「暂停-恢复」可以重置它们，
从而绕过停止条件——这是一个容易被忽略的绕过路径。

### 4. 可观测性与告警

**Trace 是投影，不是第二套事件系统。** 运行已经把事实记在事件与步记录里；
再开一条 trace 缓冲，等于把同一个事实记两遍，两份迟早对不上。`build_trace`
只读运行结果，因此可以事后重放、离线分析、不需要在运行时里插桩。

唯一的例外是模型调用耗时：它无法从已有事实推导，所以运行时把它记在
`AgentStep.think_ms` 里。一次运行的时间去向只有两个来源——模型耗时与工具耗时
（`ToolOutcome.duration_ms`）。**能用推导解决的，就不新增记录。**

**指标用来比较，不用来宣称。** 成功率、停止原因分布、工具失败率、步数与耗时
百分位，这些数字回答的是「这次改动是不是让它更容易失败」。十次以下的运行，
p95 基本等于最大值；拿它去宣称「性能达标」是在自欺。

**诊断只给证据。** 停止原因一定对应一种检查方向，证据从 Trace 里取：哪个工具
失败、错误是什么、哪个动作被重复了几次。说「模型可能需要更多上下文」这种话，
和没说一样。

**现在不接 OpenTelemetry。** 不是因为不需要分布式追踪，而是因为**顺序**：
先有可解释的数据，再谈导出。一个导出到 Jaeger 但字段含义没人说得清的 trace，
不比一张打印出来的表格更有用。接入时 Trace / Metrics 的类型不变，只多一个
导出器。

#### 这套机制管不到什么

- **跨进程的因果**：MCP 子进程内部发生了什么，主进程看不到。
- **语义质量**：回答是否讲清楚，指标答不上来。
- **告警阈值**：需要先积累基线，阈值不在框架内。
- **工具内部的重试与缓存**：除非工具把它们写进 `ToolOutcome.metadata`。
