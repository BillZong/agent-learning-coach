# 产品范围（Product Scope）

> 状态：草稿  
> 版本：V1.0

## 1. 产品定义

Agent Learning Coach 是一个面向成年学习者的 AI 学习教练（AI Learning Coach）。

产品围绕学习者的目标，组织知识体系、制定个性化学习计划、提供针对性教学、设计练习与评估，并根据学习者的实际表现动态调整学习路径。

核心学习闭环：

**Diagnose → Plan → Learn → Practice → Evaluate → Adapt**

产品的核心价值不是简单地回答学习问题，而是持续理解学习者的知识状态，管理完整的学习过程，并通过学习证据推动学习效果改善。

产品愿景、定位和完整需求以 [`prd.md`](./prd.md) 为准。本文档主要约束当前项目的实现范围。

## 2. 目标用户（Target Users）

### 2.1 目标用户

面向希望通过系统化方式掌握新知识、提升专业技能的成年学习者，主要包括：

- 希望系统学习新技术的技术人员。
- 希望提升专业能力的软件工程师。
- 希望转型或拓展技术方向的职业学习者。
- 希望通过实践和反馈持续提升能力的自主学习者。

### 2.2 首期目标用户

首期聚焦成年技术学习者，以 Agent Engineering 作为首个学习主题。

项目开发者本人同时作为首位真实学习者，通过实际学习过程验证产品的学习闭环、个性化能力和工程可靠性。

## 3. 核心能力范围（Core Capability Scope）

项目按照以下阶段逐步交付。

| 阶段 | 核心范围 | 主要交付内容 |
|---|---|---|
| Phase 0 | Agent Engineering Foundation | 建立可靠的 Agent Runtime 工程基础 |
| Phase 1 | Learning Domain & Planning | 学习领域、知识结构、学习目标、诊断与学习计划 |
| Phase 2 | AI Tutor & Learning Context | AI 教学、课程知识检索、学习上下文管理 |
| Phase 3 | Practice & Assessment | 练习、作业评估、掌握度分析 |
| Phase 4 | Adaptive Learning | 学习状态建模、学习路径调整、自适应计划 |
| Phase 5 | Productization & Delivery | API、界面、可观测性、评估、文档和演示 |

### 3.1 Phase 0：Agent Engineering Foundation

建立支撑产品运行的 Agent Engineering 基础设施。

主要范围：

- LLM 接入与模型调用抽象。
- Tool Calling 与工具执行机制。
- Agent Runtime 与执行生命周期管理。
- Session 与状态管理。
- Memory 与 RAG 基础能力。
- 任务执行可靠性与异常处理。
- Human-in-the-Loop（HITL）。
- 工具权限控制与安全策略。
- Agent Observability。
- Agent Evaluation。

**阶段定位：** Phase 0 属于工程基础建设，不是独立的用户可见产品功能。

### 3.2 Phase 1：Learning Domain & Planning

建立学习领域模型和基础学习规划能力。

主要范围：

- 学习领域管理（Learning Domain）。
- 知识结构与知识点管理（Knowledge Structure）。
- 知识点之间的依赖关系。
- 学习目标管理（Learning Goal）。
- 学习者基础信息管理（Learner Profile）。
- 学习能力诊断（Learning Diagnosis）。
- 个性化学习计划生成（Learning Plan）。
- 学习计划的结构化存储与管理。

阶段目标：学习者能够明确学习目标，理解需要掌握的知识，并获得可执行的学习计划。

### 3.3 Phase 2：AI Tutor & Learning Context

建立具有学习上下文的 AI 教学能力。

主要范围：

- 课程资料管理与知识索引。
- 基于课程资料的 RAG。
- 检索结果引用与来源追踪。
- 学习上下文管理。
- 结合学习目标和知识状态进行个性化教学。
- 支持直接讲解、引导式提问等教学方式。
- 学习 Session 管理。
- 教学过程中的上下文与记忆管理。

阶段目标：AI Tutor 不只是回答孤立问题，而是能够结合学习计划、课程知识和学习者状态开展连续教学。

### 3.4 Phase 3：Practice & Assessment

建立练习、评估与知识掌握度分析能力。

主要范围：

- 根据学习目标和知识点生成练习。
- 练习任务与提交记录管理。
- 结构化评估标准（Rubric）。
- 基于规则和 LLM 的作业评估。
- 学习结果反馈与错误分析。
- 知识点掌握度评估（Mastery Estimation）。
- 学习者知识薄弱点识别。
- 评估结果持久化。

阶段目标：系统能够根据学习者的实际练习表现形成学习证据，而不是仅凭学习时长或对话次数判断学习效果。

### 3.5 Phase 4：Adaptive Learning

建立基于学习者状态的动态学习调整能力。

主要范围：

- 学习者知识状态建模。
- 知识点掌握度持续更新。
- 知识依赖关系分析。
- 学习薄弱点与能力缺口分析。
- 学习计划动态调整。
- 学习路径优化。
- 学习计划版本管理。
- 复习任务与间隔复习调度。
- 学习调整原因解释。
- 学习者参与和控制计划调整。

阶段目标：系统能够根据学习者的真实表现调整后续学习安排，实现从静态学习计划向自适应学习过程的转变。

### 3.6 Phase 5：Productization & Delivery

完成产品化交付，形成可演示、可评估、可持续迭代的工程项目。

主要范围：

- 对外 API。
- 必要的异步任务执行接口。
- 基础 Web UI。
- 学习计划与进度展示。
- 学习者状态展示。
- Agent 执行过程与关键事件追踪。
- 系统评估与可靠性测试。
- 安全性检查。
- 部署与运行文档。
- 项目架构和设计文档。
- 完整端到端演示场景。

阶段目标：交付一个能够完整运行学习闭环的 AI Learning Coach，而不是仅有 Agent Demo 或孤立的技术组件。

## 4. 核心产品边界（Core Product Boundaries）

以下原则用于约束功能设计和技术实现。

### 4.1 学习管理不是完整 LMS

产品聚焦个人学习过程管理，不建设完整的 Learning Management System。

不以课程发布、教师管理、班级管理、组织管理等传统 LMS 能力为目标。

### 4.2 AI Tutor 不是普通 Chatbot

AI Tutor 必须能够利用学习目标、知识结构、学习计划、课程资料和学习者状态。

教学过程应具备上下文连续性，而不是将每次对话视为独立任务。

### 4.3 学习评估不能只依赖一次 LLM 判断

学习评估需要结合：

- 明确的评估标准。
- 学习者的实际练习结果。
- 可追踪的学习证据。
- 必要的规则校验。
- LLM 辅助分析。

关键学习状态应通过可解释、可复现的工程逻辑管理。

### 4.4 自适应学习必须保留学习者控制权

系统可以根据评估结果提出学习计划调整建议，但不能将所有学习决策完全交给 LLM。

学习者应能够理解调整原因，并在必要时确认或修改计划。

### 4.5 Agent Engineering 必须具备工程可靠性

Agent 不能只是一个能够调用工具的 LLM 循环。

需要重点关注：

- 执行状态管理。
- 任务生命周期管理。
- 异常恢复与重试。
- 工具权限和安全边界。
- 状态持久化。
- 可观测性。
- 评估与测试。
- Human-in-the-Loop。

### 4.6 业务逻辑与 Agent Runtime 解耦

学习领域模型和核心业务流程不应依赖某一个 Agent 框架或模型供应商。

遵循以下原则：

- LLM 负责理解、生成、分析和概率性判断。
- 确定性业务逻辑负责状态流转、权限控制、数据一致性和关键约束。
- Agent Runtime 提供通用执行能力。
- Learning Domain 负责学习业务规则与状态管理。

## 5. 明确不做的事情（Non-Goals）

当前项目不包含以下范围。

### 5.1 产品功能方面

- K12 教育产品。
- 教师、学校、班级管理系统。
- 完整 LMS。
- 企业培训与员工管理平台。
- 在线课程交易市场。
- 社交学习与社区功能。
- 多租户 SaaS 平台。
- 支付、订阅和商业化系统。
- 独立移动 App。
- 复杂的推荐算法系统。

### 5.2 Agent 工程方面

- 将 Multi-Agent 作为当前阶段的必要架构。
- 训练或微调自有基础模型。
- 自研 LLM。
- 同时支持所有 Agent Framework。
- 通用自主电脑操作 Agent。
- 无约束的工具调用和自主执行。
- 为追求技术复杂度而引入不必要的基础设施。

上述内容不代表产品未来永远不会涉及，而是明确不属于当前项目的承诺范围。

## 6. 项目验收标准（Project Acceptance Criteria）

项目最终应能够通过一个真实学习场景完成端到端验证。

### 6.1 产品能力验收

一个成年技术学习者能够：

- [ ] 创建学习目标。
- [ ] 查看和理解对应的知识结构。
- [ ] 完成初始学习能力诊断。
- [ ] 获得个性化学习计划。
- [ ] 使用 AI Tutor 学习指定知识。
- [ ] 基于学习内容完成练习。
- [ ] 获得结构化评估结果和反馈。
- [ ] 查看知识点掌握情况。
- [ ] 识别自己的知识薄弱点。
- [ ] 根据实际学习表现获得动态学习计划调整。
- [ ] 查看学习进度和历史学习记录。
- [ ] 完成一次完整的学习复盘。

### 6.2 工程能力验收

- [ ] Agent 执行过程具备明确的生命周期管理。
- [ ] 关键业务状态能够持久化。
- [ ] 任务执行具备必要的异常处理与恢复机制。
- [ ] 工具调用具备权限控制和安全边界。
- [ ] 关键 Agent 执行过程能够追踪和观测。
- [ ] 核心 Agent 能力具备可复现的评估方式。
- [ ] 核心业务逻辑不依赖单一 LLM 或 Agent Framework。
- [ ] 系统具备必要的测试、部署和运行文档。

### 6.3 项目交付验收

- [ ] 提供清晰的系统架构文档。
- [ ] 提供必要的架构决策记录（ADR）。
- [ ] 提供关键工程设计与安全文档。
- [ ] 提供可运行的项目代码。
- [ ] 提供端到端演示场景。
- [ ] 能够清晰说明关键技术方案、设计取舍和工程挑战。

## 7. 范围管理原则（Scope Governance）

为了避免项目在开发过程中不断扩大范围，所有新增需求和技术方案应遵循以下原则：

1. **优先服务核心学习闭环。** 新增功能必须能够明确说明其对 Diagnose、Plan、Learn、Practice、Evaluate、Adapt 中某个环节的价值。
2. **优先解决真实工程问题。** 技术引入应有明确的业务或工程需求，不能仅因为某项技术流行就引入。
3. **控制架构复杂度。** 优先选择能够满足当前需求的最简单可靠方案。
4. **区分长期愿景和当前承诺。** PRD 中描述的长期产品能力，不代表当前阶段都必须实现。
5. **明确评估范围变更。** 新增或调整功能前，应评估其对项目目标、开发周期和现有架构的影响。
6. **保持文档一致性。** 范围发生变化时，应同步更新本文档及相关计划。

项目文档职责如下：

| 文档 | 职责 |
|---|---|
| `prd.md` | 定义产品愿景、定位、用户需求和长期产品能力 |
| `product-scope.md` | 定义当前项目范围、阶段边界和明确不做的事情 |
| `OKR.md` | 定义阶段性目标与可衡量成果 |
| `PLAN.md` | 定义具体学习任务、开发任务和执行计划 |
| `architecture/` | 记录系统架构与技术设计 |
| `ADR/` | 记录重要架构决策及其取舍 |
