## 1. 怎么读

| 状态 | 含义 | 处理 |
| ---- | ---- | ---- |
| **已覆盖** | 后续某个主题明确承接 | 不必再管；在对应主题的验收里确认 |
| **部分覆盖** | 主题沾边但没解决问题 | 在该主题的清单里**补一条**，写明要解决什么 |
| **未覆盖** | 后续计划里没有任何主题承接 | **必须插入**——插入点见 §2 |
| **明确推迟** | 有意不排 | 写明理由与**重估时点**，到期必须重新看 |

来源缩写：**P0** = Phase 0 验收报告；**M** = [`mvp.md`](./mvp.md) 的差距清单；
**P1** = Phase 1 验收报告；**ADR-nnnn** = 架构决策记录；**T-nn** = 第 nn 个主题
笔记的未决问题。

#### 【P1-A】学习领域仓储层：目标、进度、诊断、计划版本、题目怎么存

- **来源**：P1 验收 #1「能够创建和管理学习领域」未达标（缺持久化）；P1 验收 #7
  只到「会话级」；ADR-0019「持久化目标写进 ADR 但没有实现……推迟的代价无人评估」；
  ADR-0015「不变量只在内存校验。将来接数据库时，**写入路径必须复用同一套校验**」；
  ADR-0021「题目持久化未实现」；ADR-0025「仓储层与持久化形态留给后续主题」；
  T-17「迁移历史接数据库后是否独立成表，版本号与并发写怎么管」；T-18「进度的
  持久化形态：整体重建 vs 增量更新」；T-19「持久化形态：不可变实体 + 迁移历史
  怎么存」；T-22「诊断证据的持久化形态」；T-24「仓储层与持久化形态」。
- **为什么没被覆盖**：Day 27/35/38/39 各自写了「实现文档 / Session / 题目 / 提交
  持久化」，但那是**各自对象**的持久化，不是**学习领域聚合**的仓储层。ADR-0019
  把仓储层标成「该做但不急」，之后没有任何主题认领。
- **要解决什么**：
  1. 仓储协议（按聚合根读写）与 `to_dict` / `from_dict` 的形状；
  2. PostgreSQL schema 草案（目标、迁移历史、进度、诊断与证据、计划版本、题目）；
  3. **写入路径复用领域层不变量**——否则内存里校验过的数据入库后可以绕过校验；
  4. 不可变实体 + 迁移历史的存储形态（目标状态由历史派生，不存冗余状态）；
  5. 版本号与并发写（乐观锁？ADR-0025 提到「实体不可变意味着更新都是替换」）。
- **已落地**：**Day 25「Persistence Baseline」**（Phase 1.5 · Foundation
  Remediation），紧接 Phase 1 之后、Phase 2 之前。理由：Plan.md 里 Day 27/35/38/39
  都要「持久化」，**先定基线，后面才有一致的做法**；否则每个主题各写一套 JSON
  文件或 ORM 模型。主题笔记见
  [`25-persistence-baseline.md`](../learning/topics/25-persistence-baseline.md)。
- **代价**：一天只够定「形态 + schema + 校验复用」的骨架，具体仓储实现可以摊到
  后面各主题的「持久化」条目里。

#### 【P1-B】应用层编排：诊断 → 进度 → 计划这条链谁来串

- **来源**：P1 验收 #4「能够根据学习者背景开展初始诊断」部分未达标（缺应用层编排）；
  ADR-0020「**判定与进度之间需要应用层显式衔接**。这是刻意的——自动同步会跨聚合
  写」；ADR-0024「计划与诊断可能不同步……领域层不选边」；T-20「诊断与进度的衔接
  由哪个应用层用例负责；多份诊断如何取舍」；T-23「计划与诊断不一致时的报告位置」。
- **为什么没被覆盖**：Phase 1 的领域层全是纯函数（`assess_diagnosis`、
  `generate_plan`、`start_plan` / `revise_plan`），**没有人把它们串起来**。Day 35
  （Learning Session）与 Day 50（Plan Adaptation）沾边但都不是这条链：前者是对话
  会话，后者是自适应策略。
- **要解决什么**：
  1. 用例服务：诊断 → 同步进度 → 生成/修订计划 → 落库；
  2. **诊断与进度不一致时怎么办**（诊断说会、进度说没学会）——领域层故意不选边，
     应用层必须选；
  3. 多份诊断如何取舍（初诊 vs 复诊）；
  4. 一次事务只改一个聚合的写边界怎么守（ADR-0015）。
- **已落地**：**Day 26「Application Services」**（Phase 1.5），紧跟 Day 25。主题笔记见
  [`26-application-services.md`](../learning/topics/26-application-services.md)。
- **注意**：这条不解决，Phase 2 的 Tutor E2E（Day 36）与 Phase 4 的 Adapt 闭环
  （Day 56）都只能测「单个纯函数」，测不出「诊断→教学→计划」的完整链路。

#### 【P1-C】知识结构的数据维护与校验：`requires` 边谁写、怎么保证它对

- **来源**：T-16「先修边由谁维护、如何用学习数据校验」；ADR-0016 未回答；ADR-0024
  「严格的前置闭包可能带进大量内容」——**闭包的大小完全取决于 `requires` 边的质量**，
  而质量目前没有任何保障机制。
- **为什么没被覆盖**：Day 47（Knowledge Dependency）讲的是「怎么表达与查询」，Day
  46 讲「怎么排序」，**没人讲「这些边是谁维护的、错了怎么办」**。
- **要解决什么**：
  1. 谁维护课程知识结构（课程作者？导入？模型生成？）；
  2. 依赖边的质量校验（循环已有；缺的是「过长的链」「与学习数据矛盾的边」）；
  3. 依据学习数据回看依赖边是否合理（例如某个点反复导致阻塞，可能该边过强）。
- **建议插入**：**并入 Day 47（Knowledge Dependency）**——它本就在讲依赖，追加
  「维护流程与数据校验」两项；不必新增 Day。

## 5. Day 插入方案（已落地）

**方案：新增 Phase 1.5 · Foundation Remediation（Day 25–26），原 Day 25–64 顺延为
Day 27–66。**

```
Day 25（新增）Persistence Baseline —— 仓储协议、schema 草案、写入路径复用不变量
Day 26（新增）Application Services —— 诊断→进度→计划→落库的用例编排与一致性处理
Day 27…（原 25）Document Ingestion
…
Day 66（原 64）Documentation & Demo
```

**为什么放在 Phase 2 之前**：Plan.md 里 Day 27/35/38/39 都要「持久化」。先定仓储
基线，后面每一个「持久化」条目才有共同的形状与校验方式；否则 Phase 2–4 会在内存
里跑完，Phase 5 接 API 时统一返工——而 ADR-0015 已经把「写入路径必须复用同一套
校验」列为将来接数据库时的硬要求。

**为什么不塞进 Phase 1**：Phase 1 的领域层已验收（`phase-1-acceptance.md`），
把基础设施债算进 Phase 1 的交付会改写已验收的结论。独立成 Phase 1.5，两条缺口
的归属清楚：**它们是补 Phase 0–1 的账，不是 Phase 1 的新功能**。

**原替代方案（已放弃）**：放在 Phase 5 之前——好处是 Phase 2–4 保持「以学习能力为
主」的节奏，代价是仓储层推迟 30 天，ADR-0019 的推迟成本继续累积，且 Phase 2–4
各自的「持久化」条目会先各写各的。

## 6. 台账维护规则

1. **每个主题开工前**：在本台账里找到它的承接项，把它标成「处理中」，并把 §2 的
   建议插入项抄进该主题的清单。
2. **每个主题收工时**：确认承接项已解决；没解决的写明原因并留在台账里，**不允许
   默默消失**。
3. **阶段验收时**：本台账是该阶段「未覆盖的边界」的展开——验收报告不再单独列
   清单，直接引用本台账的编号。
4. **编号不复用**：一条问题关闭后，编号保留（便于回溯历史决策）。
