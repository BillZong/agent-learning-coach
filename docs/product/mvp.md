# MVP 定义与判断标准

> 状态：已确定 ｜ 日期：2026-11-24 ｜ 关联：`product-scope.md`（§7 范围管理）、`roadmap.md`（M1–M2）、ADR-0013、ADR-0014

## 1. 定义

> **MVP：构建一个能够将用户目标转化为结构化计划，按照依赖关系执行任务，并通过可观测、可评估的反馈机制持续修正用户学习计划的 Agent。**

一句话边界：**MVP 交付的是「计划的生成—执行—修正」闭环，不是完整学习闭环。**
`Diagnose → Plan → Learn → Practice → Evaluate → Adapt` 中的 Learn / Practice /
Evaluate 属于 Phase 2–3，不进入 MVP。

采用这个定义的理由是它**可被证伪**：每一条都能落到一个可执行的检查上（见 §2），
而不是落在「Agent 能不能自己规划、自己反思」这种无法终止的判断题上。

## 2. 四个必要条件

任何功能要进入 MVP，必须同时满足这四条。**它们不是描述愿景，是准入门槛。**

| # | 条件 | 判据（怎么算满足） | 反例（不算满足） | 当前证据 |
| ---- | ---- | ---- | ---- | ---- |
| 1 | **计划是结构化的，不是纯文本** | 计划是对象：稳定任务 id、状态机、依赖、版本历史；能序列化与恢复 | 一段 Markdown 清单；模型「心里有数」 | `core/agent/planning.py`；`tests/test_planning.py` |
| 2 | **执行过程可追溯，不是只有最终结果** | 每次运行产出事件、步记录与 Trace；每条 `tool_call` 有对应 `tool_result` | 只保存最后一轮回答 | `core/agent/observability.py`；`tests/test_observability.py` |
| 3 | **关键决策可评估，不只依赖 LLM 自我判断** | 每个结构性修改带 `rationale` 与可选的 `reflection_id`；决策有版本记录，能事后用证据确认或否定 | 模型说「已经改好了」；反思结论无人校验 | 记录已具备（计划修订 + 反思引用）；**判据仍缺**，见 §6 的 G1 |
| 4 | **系统行为可通过实验验证，不是凭主观感受优化** | 改动前后能用同一组用例回答「是否更好」；门禁可回归 | 调完 prompt 觉得「好像顺了」 | `evals/phase0.json`（7 条）+ `make eval` + CI；**仅覆盖机制层**，见 G2 |

四条里，**条件 1、2 已经交付**；条件 3、4 只有一半——这条差距是本文件最重要的
内容，也是 Phase 1 的主要工作输入。

## 3. 「按依赖执行」的准确含义

定义里的「按照依赖关系执行任务」有两种截然不同的解释，必须选一个：

| 解释 | 含义 | 状态 |
| ---- | ---- | ---- |
| **A. 依赖是强约束** | 系统不允许开始前置未完成的任务；模型在「可以开始」的集合内决定下一步 | **已实现**（`PlanManager` 状态机 + `startable_tasks()`） |
| B. 依赖驱动自动执行器 | 系统自动挑任务、自动执行、自动推进，不需要模型决策 | 未实现，也不属于 MVP |

**MVP 采用 A。** 理由：学习任务不是命令，任务的「执行」本身就是教学交互——那是
Phase 2 的问题；在这一步之前造自动调度器，只会得到一个无法定义「执行成功」的
执行器。

这条解释必须写清楚，否则「让 Agent 更自动」会以「更符合定义」的名义把范围
悄悄拉大。

## 4. 范围

**包含**

- 学习目标 → 结构化计划（`GoalSpec` → `PlanDraft` → `Plan`）。
- 按依赖推进任务；状态机与反混乱约束（id 稳定、内容不可改写、无删除、单一
  进行中、依赖闭合无环）。
- 反思 → 重规划：反思只产出判断，改计划必须引用反思，且受重规划预算约束。
- 计划版本历史与持久化（随会话快照恢复）。
- 执行可观测：Trace / Metrics / 诊断。
- 行为评估：数据集 + 门禁。

**不包含**（列出是为了防止「顺手做了」）

- AI Tutor 教学、练习生成与评分、掌握度模型。
- 基于学习证据的完整自适应（Phase 4）。
- 多 Agent、定时复习调度、Web UI、多租户。
- 确定性任务执行器（见 §3）。

## 5. 新增功能的判断流程

新增需求进入 MVP 前，依次回答四问。**任一答否，不进 MVP。**

1. 它是否让计划更结构化、更可执行？（条件 1）
2. 它是否留下可追溯的执行记录？（条件 2）
3. 它是否让某个关键决策变得可评估？（条件 3）
4. 它是否能被现有或新增的评估用例验证？（条件 4）

三条反膨胀规则：

- **不能回答「它怎么被证伪」的功能不做。** 不是「以后可能会用到」，而是「现在
  能用哪个用例说明它有用」。
- **「更自动」不是理由。** 自动化的每一步都必须先有可评估的判定标准，否则只是
  把不可解释的决策换成不可解释的代码。
- **记录优先于优化。** 条件 3 未满足时，先记录决策与结果，不要先调参。

## 6. 当前差距（诚实清单）

| 编号 | 差距 | 影响 | 下一步 |
| ---- | ---- | ---- | ---- |
| G1 | **决策质量没有判据**：`reflect` 的 `verdict` 由模型给出，程序只记录不验证 | 条件 3 只有「可追溯」，没有「可评估」；「计划修正是对是错」答不上来 | 先定义离线判据（如计划完成率、阻塞率、重规划后回退次数），用历史修订数据跑对照，再考虑接入预算 |
| G2 | **真实模型与计划质量未验证**：评估集只覆盖机制层（脚本化模型） | 条件 4 只能回答「机制有没有坏」，不能回答「计划变好没有」 | 真实模型抽样回归（允许通过率区间）；计划质量用例（人工标注少量对照） |
| G3 | 评估集规模小：7 条用例 | 覆盖有限，新失败模式可能漏掉 | 每发现一种失败补一条用例（已在 `evaluation.md` 定为规则） |
| G4 | 依赖执行只有约束，没有调度器 | 不是缺陷，是 §3 的选择 | 保持，除非出现明确的自动执行需求 |

G1 与 G2 是本 MVP 定义下**最有价值的两个未解问题**——它们同时决定了「Phase 1
能否说计划能力被验证过」。

这四条差距的**覆盖情况与建议插入点**见
[遗留问题台账](open-issues.md)：G1 由 Day 63 承接（计划完成率 / 阻塞率 / 重规划
回退次数），G2 由 Day 46 与 Day 62/63 承接（真实模型抽样回归与容差区间），G3 由
Day 62 承接（失败案例回流为回归用例），G4 是有意的选择、不排期。
