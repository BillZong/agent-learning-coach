## 1. Engineering Question

苏格拉底式怎么实现？提问、追问、回答理解、教学模式切换怎么做？两种模式的效果怎么比？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **教学引导 = Assessment + Orchestration + Elicitation** 三阶段 ✓✓。
  - **现有 LLM 在学习者困惑时常常给不出有效的适应性支架**——它们是「通用教练」而不是

  - **渐隐支持**：支持强度要随熟练度递减 ✓（是模式切换的另一个理由 ✓）。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  引导要根据学习者状态调整；不能只讲答案；提示要备好；支持要递减。
- **哪些观点存在分歧？**
  - **苏格拉底式该不该是默认**。本项目让**学习者明确要求时切回直接教学** ✓；
    而「苏格拉底式更有效」的说法在本项目**没有证据** ✓——脚本化模型给不出 ✓。
  - **一次调用还是两次**。本项目**分两次**（问一次、判一次）✓；一次调用更省延迟，
    但没有回答时模型也在判 ✓。
- **分歧来自应用场景、设计目标还是技术演进？**
  来自**优先级**（延迟 vs 判断质量）与**证据不足**（哪种模式更好没证据 ✓）。
- **哪些结论缺少充分证据？**
  - **模型能不能做好 Assessment**——GuideEval 说常常不行 ✓✓；本项目只能把结构固定
    下来，**不能保证判断准** ✓；
  - **两种模式哪个对学习者更好**——要真实学习者 ✓；
  - **两次调用的延迟代价**——没量过 ✓。
- **哪些观点不适用于当前项目？**
  - **behavior-guided finetuning**（GuideEval 的训练方案）：本项目不训练模型 ✓。
  - **多代理 / 多轮引导的完整干预设计**：Phase 5 之后 ✓。

## 5. Engineering Practice

- **实现了什么？**

    答案 / 卡住 / 答对可深挖 / 答非所问 / 用自己的话答对）✓。
  - **`tests/test_socratic.py`**（新增）：14 个用例。
  - **`examples/socratic_teaching.py`**（新增）：四段演示。
  - **文档**：ADR-0036、ADR 索引、`domain.md` §4.8、roadmap、Topic 34 笔记、
    Day 34 记录。
- **为什么这样设计？**
  - **三阶段分开**——引导的核心是**判断与调整**，不是语气 ✓✓；
  - **两次调用**——判断需要回答 ✓；
  - **提示是必填字段**——不给答案，但必须给出路 ✓；
  - **切换判据写死**（reveal → direct；明确要求 → direct）✓。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 一个调用同时问与判 | 没有回答时也在判；判断质量下降 ✓ |
  | 把苏格拉底式写进「指令」就完事 | 那是 Day 33 的一半；引导的另一半（判断与调整）没做 ✗ |
  | 追问到底、永不揭示 | 消耗学习者耐心 ✗ |
  | 提示做成可选字段 | 模型常常不给 → 学习者卡住只能干等 ✗ |
  | 用脚本化模型评估「哪种模式更好」 | 给不出质量结论，只能证明管道通 ✗ |
- **测试结果如何？**
  - `tests/test_socratic.py`：14 个用例（指令禁止给答案、两种指令不同、提问带提示、
    渲染不给答案、回答判断、回答进模型、reveal 切直接、hint 保持苏格拉底、advance
    保持苏格拉底、缺步骤默认追问、学习者要答案就切直接、默认模式、坏用例报错）。
  - 评估实测（8 条用例、脚本化模型）：判断准确率 **0.12**、下一步准确率 0.38、
    模式准确率 0.75 —— **低是意料之中的**：脚本化模型每次答同一个 ✓。
  - 全量：**1025 passed**（+14）；`ruff` / `mypy` 全绿；三十一个示例跑通。
- **实践结果是否支持阅读材料中的观点？**
  支持：**引导需要三阶段** ✓；**判断与调整是难点** ✓（脚本化模型给不出有意义的判断
  准确率 ✓✓）；**苏格拉底式是手段不是目的** ✓（学习者要求就切 ✓）。**修正**一条：
  以为「苏格拉底式的实现」主要是写好指令——**指令是最便宜的一半** ✓✓，难的一半
  （读懂学习者、决定下一步）是模型最弱的地方 ✓。

## 6. Reflection

1. **今天最重要的知识是什么？**
   **「用苏格拉底式的语气问问题」与「在引导」是两件事，而模型弱的是后者** ✓✓。
   GuideEval 的实测说得很直接：LLM 在学习者困惑或需要引导时给不出有效支架——
   因为「读懂学习者现在什么状态」这件事本身就难。所以本项目把力气花在
   **Assessment 与 Orchestration 的结构化**上（状态与下一步都是枚举 ✓），而不是把
   指令写得更有苏格拉底味 ✓。
2. **哪个观点改变或修正了原来的理解？**
   原以为「苏格拉底式 = 少讲多问」。实际上**「什么时候该停止问、改为直接讲」是引导
   的一部分**——渐隐支持意味着支持强度要递减，而**揭示答案就是支持强度归零的那一刻**
   ✓✓。所以「模式切换」不是附加功能，是引导的最后一环 ✓。
3. **当前实现还有哪些局限？**
   **判断质量完全取决于模型**（GuideEval 说它常常不行 ✓）；两次调用的延迟没量 ✓；
   脚本化评估给不出质量结论 ✓；**多轮引导的策略**（追问几轮后揭示）只在指令里、
   没有机制 ✓；与练习（Phase 3）的衔接没做 ✓。
