# Topic: Planning 与 Reflection

> Day 13 ｜ Phase 0 · Agent Engineering Foundation ｜ 主教材：Ch7：7.1～7.4 ｜ 外部参考：Anthropic Evaluator-Optimizer Pattern ｜ 状态：已完成

## 1. Engineering Question

Planner 与 Reflection 的职责如何切分？如何避免反思循环把学习计划越改越乱？

## 2. Primary Reading

- Book: Ch7：7.1～7.4
- Chapter / Section: Ch7 7.1～7.4
- 核心观点：
  - **7.1 ReAct 的局限**：ReAct 一步一决策，没有全局方向；步骤多了容易
    走偏、重复、卡住。人类专家的做法是**先想清楚再动手**。
  - **7.2 规划（Setting direction）**：给 Agent 时间思考；用一个 `create_tasks`
    工具把任务清单显式化。任务有 `content` 与 `status`（`pending` /
    `in_progress` / `completed`），清单**整体重写**——每次调用都提交一份完整的
    新清单，并标好各条的状态。
  - **7.3 反思（Checking and correcting）**：一个 `reflection` 工具，模型写下
    当前状况与下一步方向；`need_replan=True` 表示「当前计划需要修改」。教材给了
    四种使用时机：进展回顾、错误分析、结果综合、答前自检；并明确**不要**每次
    工具调用后都反思（开销过大）。
  - **7.4 整合**：规划与反思解决 ReAct 的不同失效模式；反思的真正价值在
    **失败恢复**（工具失败后换一个思路，而不是重复同一个失败调用）。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  全部一致认为：**规划要在动手之前，反思要在关键节点之后**，而且反思**不该
  每次工具调用都做**（教材明确写了这个「WHEN NOT TO USE」，Anthropic 的
  evaluator-optimizer 也强调循环要有上限）。一致认为**计划要显式**——隐式地
  「模型心里有计划」无法检查，也无法持久化。
- **哪些观点存在分歧？**
  - **反思的权限**：教材的 `reflection(need_replan=True)` 只回显「REPLAN
    NEEDED」，随后模型自己决定要不要改计划——**反思与改计划之间没有强制
    联系**。Evaluator-Optimizer 则要求评估方的结论**直接驱动**下一轮生成。
  - **计划的粒度**：教材是「一份清单 + 三个状态」；本项目是「任务有稳定 id、
    内容不可改写、五个状态、有依赖图、有版本历史」。
- **分歧来自应用场景、设计目标还是技术演进？**
  - 反思权限的分歧来自**设计目标**：教材要的是「演示反思这件事」，所以
    工具越简单越好；本项目要的是「计划不能被改乱」，所以必须给反思**划界**。
    两者其实不矛盾——教材的做法是本项目的**特例**（`reflection` 只回显，不
    约束后续动作），而本项目把边界补上了。
  - 计划粒度的分歧来自**应用场景**：教材的场景是「一次性研究问答」，任务
    清单最多十几条，重写成本可以接受；本项目的场景是**长期学习**，计划会
    跨会话存在几十次修改，重写的累积成本与出错概率都不可接受。
- **哪些结论缺少充分证据？**
  - 「先规划再动手比边做边想更好」——教材没有对照实验。本项目今天也没有：
    `OutcomePlanner`（确定性拆解）与 `LLMPlanner`（模型拆解）**没有做过
    对比评估**，只验证了机制成立。
  - 「Evaluator-Optimizer 适用于有明确评估标准的任务」——这句话本身没有
    错，但它没有回答「**评估标准由谁定**」。本项目的反思结论（`replan` /
    `continue`）由模型自己给，**程序不验证**——这正是当前最大的未验证点。
  - 「同一时刻只能有一个进行中的任务」是本项目的设计选择，**没有实证支持**。
    它来自「计划是单一焦点」的直觉，可能过于严格。
- **哪些观点不适用于当前项目？**
  - 教材 `create_tasks` 的**整份重写**不适用：那是「一次性清单」的写法，长期
    计划必须增量修改。
  - 教材 7.3「不要在每次工具调用后反思」适用于短任务，**本项目采纳并加强**：
    除了「不要频繁反思」，还给了**总量上限与单任务上限**。
  - Evaluator-Optimizer 的完整形态（两个独立的模型调用循环）**现在不适用**：
    Phase 0 的循环是单模型 ReAct，加一个独立的评估器调用会让成本翻倍，且
    本项目还没有「什么算好」的客观标准。

## 5. Engineering Practice

- **实现了什么？**
  - `core/agent/planning.py`：
    - **计划类型**：`Plan` / `PlanTask` / `PlanRevision` / `AppliedChange` /
      `Reflection`；`Plan` 可序列化（`to_dict` / `from_dict`）。
    - **写入接口**：`PlanManager`——`create` / `apply` / `reflect`。
    - **规划器**：`Planner` 协议 + `OutcomePlanner`（确定性拆解，基线）+
      `LLMPlanner`（模型拆解，结果由状态机校验）。
    - **目标契约**：`GoalSpec`——领域无关的目标描述，是领域模型与运行时之间
      的唯一接口。
    - **工具**：`update_plan`（提交增量修改）/ `reflect`（记录判断）。
  - **反混乱约束**（全部由 `PlanManager` 确定性执行）：
    - 任务 id 稳定；**内容不可改写**（要换说法就新建 + 跳过旧的）；
    - **没有删除操作**（移除 = `skipped`，任务仍在计划里）；
    - `skipped` 是唯一终态；
    - 同一时刻只能有一个 `in_progress`；
    - 依赖必须存在且不成环；**进行中的任务，其前置必须已完成**；
    - 每次修改都要有 `rationale`；
    - **整批原子**：一条不合法，整批都不生效。
  - **额度**：`PlanPolicy`——`max_replans`（3）、`max_reflections`（6）、
    `max_reflections_per_task`（2）。**普通推进不消耗重规划预算**，只有结构性
    修改（新增 / 跳过 / 重开 / 改依赖）消耗。
  - **纪律**：反思不改计划；待处理的重规划请求必须被下一次结构性修改引用；
    最新一条反思代表当前意图（避免死锁）。
  - **持久化**：计划存在 `ExecutionContext.state["learning_plan"]`，随会话快照
    一起保存与恢复。
  - **示例**：`examples/learning_plan.py`——目标 → 任务 → 推进 → 反思 →
    重规划的完整闭环，外加五种被拒绝的修改。
  - **测试**：`tests/test_planning.py`（45 个）。
- **为什么这样设计？**
  - **增量而不是重写**：整份重写时，「已完成的任务被漏掉」是机制性故障；
    增量提交没有机会漏掉没提到的任务。
  - **对象而不是文本**：文本没有身份、没有状态、没有历史，因此每次改写都从
    零开始——「越改越乱」的根因就在这里，不在模型。
  - **预算只对结构性修改生效**：正常推进本来就不该被算成「又改了一次计划」。
    两者共用一个额度的话，跑一遍正常的计划就把额度花光了。
  - **反思与改计划分开**：这样「为什么改」永远有出处，模型也不能在没有判断的
    情况下随手改计划。
  - **id 先分配、后校验**：这样同一批修改里「新建 t4」与「让 t2 依赖 t4」可以
    一次写完，与两条在清单里的先后无关。
  - **渲染按依赖排序**：重规划插入的前置任务一定晚于被依赖的任务创建；按创建
    顺序渲染，计划读起来就是乱的。
- **有哪些替代方案？**
  - **照搬教材的整份重写**：最简单，但把「计划越改越乱」当成模型的错。否决。
  - **计划只放在 prompt 里，不建模**：省一个包，但计划无法持久化、无法校验、
    无法审计。与「确定性核心」原则冲突。否决。
  - **把反思做成独立的模型调用（完整的 Evaluator-Optimizer）**：Phase 0 不做，
    理由见第 4 节。
  - **允许删除任务**：实现更简单，但历史会出现空洞，「这个任务去哪儿了」答不上
    来。改为 `skipped`。
- **测试结果如何？**
  - `tests/test_planning.py`：**45 passed**；全量 **575 passed**；ruff / mypy
    全绿。
  - `examples/learning_plan.py` 跑通完整闭环，并演示了五种被拒绝的修改及其
    原因。
- **实践结果是否支持阅读材料中的观点？**
  - **部分支持**。「显式规划有用」在本项目里表现为**可检查**：模型的每次计划
    修改都留下版本与理由，因此可以事后回答「它为什么改成这样」。但「规划
    提升了学习效果」**没有被验证**——本项目还没有学习效果评估。
  - **不支持教材的整份重写**。这不是风格偏好：整份重写下「已完成的任务被漏掉」
    会**机制性**发生，与模型能力无关。
  - **修正了对 Evaluator-Optimizer 的理解**。它强调「评估方驱动下一轮」，但没说
    评估标准从哪来。本项目补上的恰恰是这一段：**评估（反思）与修改（重规划）
    分离**，以及**评估有额度**。

## 6. Reflection

1. **今天最重要的知识是什么？**
   「越改越乱」是**建模问题**，不是模型问题。只要计划是一段可被覆盖的文本，
   每次重写就必然丢信息——丢的不是模型的记性，是结构里根本没有「已完成」这个
   概念。把计划变成带 id、带状态、带历史的对象之后，很多「模型不稳定」的抱怨
   就变成了「这个约束该由程序守」。
2. **哪个观点改变或修正了原来的理解？**
   原来以为「反思」是模型能力的一部分（模型会不会自我怀疑）。读完
   Evaluator-Optimizer 之后明白：**反思是流程里的一个角色，不是模型的属性**。
   它能被工程化成「一条带结论的记录」，因此可以被约束（额度、必须被引用）、
   被审计（谁在什么时候判断了什么）。这条修正直接决定了本项目的做法：
   **反思是数据，不是对话**。
3. **当前实现还有哪些局限？**
   - **反思的质量没人验证**——`replan` 判断对不对，程序不知道。
   - **计划不进上下文预算**——渲染后的计划由应用层塞进 prompt，没有做裁剪；
     任务多了会挤占上下文。
   - **拆解质量没有评估**——`OutcomePlanner` 与 `LLMPlanner` 没有对比实验。
   - **额度是拍脑袋定的**——3 次重规划、6 次反思，没有依据。
   - **依赖只能表达前置，不能表达「并行」**——两个互不依赖的任务在计划里看
     起来一样，但「单一进行中任务」这条约束又禁止并行，因此目前无法表达
     「这两件事可以同时做」。
