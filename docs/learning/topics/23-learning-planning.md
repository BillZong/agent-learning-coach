## 1. Engineering Question

Learning Plan Generator 的输入输出契约是什么？计划任务粒度如何与知识点对齐？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **掌握度是学习计划的单位，不是「任务」的单位。** 掌握式学习（mastery
    learning）的判据是「这个概念会不会」，不是「这个步骤做完没有」。计划任务
    必须能落到一个可判定的掌握对象上，否则「学完了」与「学会了」是两件事。
  - **约束是排程的前提，不是排程的结果。** 每日投入与时间范围是**输入**；先有
    容量，再谈怎么装。没有容量却排出日程，是假精度。
  - **依赖是硬约束，优先级是软偏好。** 先修关系不能违反；同一层里先学哪个只是
    偏好，可以换。
  - **排不下时「少排」比「排不下」更糟。** 丢掉内容会让「要补的地方」凭空消失，
    而补漏的成本远高于多学。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  依赖要遵守；掌握对象要可判定；约束要先于排程；排不下要报不可行；计划应随
  表现调整。
- **哪些观点存在分歧？**
  - **计划的粒度**：多数学习管理系统以「课 / 章节 / 活动」为计划单位（课程级
    调度），本项目以**知识点**为单位。分歧来自**应用场景**——课程级调度面向
    「一学期一门课」，知识点级面向「AI 教练按需排下一步」。在知识点级粒度下，
    「课程活动」这种单位根本无法表达。
  - **单元是否该覆盖多个知识点**：教材倾向「一个活动覆盖一组概念」（便于组织
    教学）。本项目拒绝，因为覆盖多个点就无法回答「这个单元算掌握了哪个点」，
    进度回写会立刻失准。分歧来自**下游约束**：本项目要回写掌握度。
  - **排不下时怎么办**：教科书里常见「延长周期 / 降低目标」的处置建议。本项目
    只**报告**不处置——因为处置涉及用户的目标与时间，属于应用层与用户的事。
    分歧来自**职责边界**，不是技术。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**设计目标**（本项目要可回写、可审计）与**应用场景**（知识点级 vs
  课程级）。
- **哪些结论缺少充分证据？**
  - **估时**：默认 30 分钟/知识点没有任何数据支撑。它让排期看起来精确，而实际
    不准——**这是本主题最大的弱点**。
  - **贪心装箱是否够用**：本项目的装箱只保证「每天不超容量」，不优化「哪一天放
    哪个点」。在等容量、单位等价的设定下贪心即最优，但一旦估时误差变大、或要
    考虑「同一天不要排两个高认知负荷的点」，就需要真正的排程器。
  - **严格前置闭包会不会带进过多内容**：长链结构会让计划远大于目标本身。这符合
    「掌握 k3 就意味着会 k1、k2」，但课程结构过细时体验会差。没有数据说明现实中
    的链长分布。
- **哪些观点不适用于当前项目？**
  - **完整排程算法（CP/ILP）**：Phase 1 的约束只有容量与期限，贪心足够；引入
    求解器是过度设计。
  - **掌握曲线与遗忘曲线驱动的复习排程**：复习调度属于 Topic 52。
  - **多人班级排课**：本项目是单人教练，没有班级。

## 5. Engineering Practice

- **实现了什么？**
  - **`core/learning/planning.py`**（新增）：
    - `LearningUnit`（值对象）：`point_id`、`title`、`reason`、`outcomes`、
      `estimated_minutes`、`depends_on`、`day`。**没有独立 id——知识点就是它的
      身份**。
    - `LearningPlan`（值对象）：`goal_id`、`units`、`days`、`overload`、
      `unmet_prerequisites`、`diagnosis_id`。派生，无状态。
    - `DailyLoad`（值对象）：某天的分钟数、投入上限、是否在期限内、
      `is_overloaded`。
    - `PlanOverload`（值对象）：总量、需要几天、有几天、超出几天。
    - `EffortEstimator` 协议 + `UniformEffort` 实现（默认 30 分钟）。
    - `generate_plan(goal, structure, progress, *, diagnosis=None, estimator=None)`。
  - **`core/learning/bridge.py`**：新增 `to_unit_goal_spec(unit, goal)`——回答
    `bridge.py` 自己留下的「计划任务粒度如何与知识点对齐」：**对齐到知识点，但
    运行时契约不需要扩展**。
  - **`core/learning/diagnosis.py`**：判定引用**映射缺失**的证据时，错误信息从
    「指向 None 的依据」改成「映射缺失的证据不能支撑任何判定」。
  - **`tests/test_learning_planning.py`**（新增）：27 个用例。
  - **`examples/learning_planning.py`**（新增）：五段演示。
- **为什么这样设计？**
  - **单元与知识点一一对应**：进度、判定、依赖都以知识点为单位；粒度不对齐，进
    度就写不回去。
  - **范围 = 目标要求 ∪ 前置闭包 − 已学会**：不带闭包的计划**执行不了**。
  - **目标的前置只报告不进范围**：它是「开始这个目标前必须已经会」的前提，不是学
    习内容。
  - **范围由目标与进度决定，不由诊断决定**：诊断是判断不是事实；两份事实之间选
    边是应用层的事（ADR-0020）。
  - **顺序 = 拓扑序限制到范围**：依赖是硬约束。
  - **排不下报告，不少排**：丢掉单元会让「要补的地方」凭空消失——同 ADR-0023 反对
    的宽松汇总。
  - **没约定每日投入就不排期**：硬排「第 0 天装下全部内容」是假精度。
  - **估时可替换**：领域层定义「需要估什么」，不规定「怎么估」。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 单元覆盖多个知识点 | 回写进度时无法确定「算掌握了哪个点」 |
  | 一个知识点拆成多个单元（学/练/复） | 掌握一个点被拆成跨单元对齐的事实；练习与复习属后续主题 |
  | 计划只含目标要求的点 | 目标要求 k3 而 k3 依赖 k1、k2 时，计划执行不了 |
  | 目标的前置也放进计划 | 把前提当内容学；补前置属于另一个目标 |
  | 范围由诊断决定 | 诊断是判断；两份事实的选边是应用层的事 |
  | 单元有独立 id（像运行时的 `t1`） | 一一对应下 id 是冗余；反而多一处要对齐 |
  | 用 `structure.order()` 直接当计划顺序 | 会带上与目标无关的点（k4） |
  | 自己写拓扑排序 | ADR-0016 已有 `order()`；两份实现必然漂移 |
  | 排不下就少排几个单元 | 「要补的地方」凭空消失 |
  | 排不下就抛异常 | 目标本身自洽，装不下是需要人决定的事实，不是数据坏了 |
  | 没投入也硬排「第 0 天」 | 假精度 |
  | 用 LP/CP 求解器排程 | 约束只有一个容量上限，贪心已足够——过度设计 |
  | 估时写死在领域层 | 换估时口径要改领域模型 |
  | 知识点 id 进 `GoalSpec` | 运行时开始认识学习领域，破坏 ADR-0013 §10 的分层 |
  | 计划做成实体（自带 id 与状态） | 它是派生的：给定输入就能算出来；版本与历史属 Topic 24 |
- **测试结果如何？**
  - `tests/test_learning_planning.py`：27 个用例（范围带闭包、减去已学会、排除无
    关点、全学会时为空计划、前置在前、依赖只含计划内、依赖在计划外被拒、后继排
    在前置之前被拒、三种理由、诊断缺口优先、按容量装箱、没有投入不排期、每天
    负载带上限、单单元超容量被标超载、超载被报告且单元不少、超期天被标、没有时
    间范围不报超载、目标前置未满足被报告、已满足不报、别人的进度被拒、别的课程
    被拒、知识点不在结构里被拒、自定义估时器生效、估时非正被拒）。
  - 全量：**775 passed**；`ruff` / `mypy` 全绿；二十个示例跑通。
  - `examples/learning_planning.py`：k1→k2→k3 三个单元带理由；依赖链 k1 ← k2 ←
    k3；45 分钟/天 → 三个 30 分钟的单元排成三天；30 分钟/天 + 两天窗口 → 超载
    1 天且三个单元一个不少；单元映射成 `GoalSpec`（知识点 id 不出现）。
- **实践结果是否支持阅读材料中的观点？**
  支持三条：**掌握对象要可判定**（单元一对一，理由可写）；**约束先于排程**（没
  容量就不排期）；**排不下要报不可行**（`PlanOverload`）。
  **不支持**「估时可以先用一个占位值」——它让排期看起来精确而实际不准，代价是
  用户会拿它做承诺。这条被写进 ADR 的风险项。

## 6. Reflection

1. **今天最重要的知识是什么？**
   **粒度不是审美问题，是回写问题。** 「一个单元一个知识点」看起来朴素，但它
   是「完成单元 → 更新进度」能成立的前提。粒度一旦不对齐，后面每一次进度回写
   都要先猜「这个单元算掌握了哪个点」——而那次猜测没有权威来源。同一条线索在
   ADR-0023 也出现过：**证据必须指向明确的知识点，否则不可审计**。
2. **哪个观点改变或修正了原来的理解？**
   原以为「计划范围 = 目标要求的知识点」。实际上还要**带上前置闭包**——目标要求
   k3，而 k3 依赖 k1、k2，不带闭包的计划根本执行不了。更意外的是**目标的前置
   （`goal.prerequisites`）反而不进范围**：课程里的 `requires` 是「知识点之间的
   学习依赖」，目标的前置是「学习者层面的前提条件」，两者方向相反——一个是内
   容，一个是前提。
3. **当前实现还有哪些局限？**
   估时是占位值（无实证）；计划不含内容（「这个单元具体怎么学」要 Phase 2 补）；
   每天的负载只是总量，没说同一天内单元的先后（那由依赖决定，与「第几天」无
   关）；计划没有版本也没有存下来（Topic 24）；复习安排不在计划里（Topic 52）；
   贪心装箱不优化「哪天放哪个点」；诊断与进度不一致时领域层不选边（应用层责任）。
