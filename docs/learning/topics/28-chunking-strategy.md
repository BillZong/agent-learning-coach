# Topic: Chunking Strategy

> Day 28 ｜ Phase 2 · AI Tutor ｜ 主教材：—（本阶段无主教材章节） ｜ 外部参考：RAG 的切分实践（LangChain / LlamaIndex 的文本切分器设计）、Markdown 标题结构、代码切分（tree-sitter 的语法树切分）、测试中的性质断言（property-based testing，Hypothesis）、检索质量的分解诊断（先看切分再看召回） ｜ 状态：已完成

## 1. Engineering Question

讲义、代码、习题等不同文档类型，应采用何种切分策略？切分参数如何被测试锁定？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **每类材料有它自己的语义单元**：讲义是段落，代码是函数 / 类，习题是一道题。
    一刀切的策略总有一半材料是错的。
  - **切分参数会变，语义单元的完整性不会**。因此测试锁**不变量**，不锁数字。
  - **结构识别失败要能退**：识别不出来时切得差一点，好过切不出来。
  - **元数据是检索过滤的唯一依据**——课程 id 与知识点关联必须跟着切片走。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  按语义单元切；分隔符/结构可配；切分参数要随语料调；代码要按语法切。
- **哪些观点存在分歧？**
  - **用正则还是语法解析器切代码。** tree-sitter 那种做法更准（能识别嵌套函数、
    字符串里的 `def` 等），但要引入解析器依赖，而且换语言要换解析器。本项目用
    **正则**（顶层定义）——够用、可换语言、零依赖。分歧来自**依赖预算**与**语言
    多样性**的取舍。
  - **测试锁参数还是锁性质。** 「参数 = 500、重叠 = 50」看起来是可断言的规格，但它是
    **实现细节**：改了参数就得改断言，于是断言变成橡皮图章。锁性质则允许参数自由
    调整。分歧来自**断言的用途**——是要锁住规格，还是要防住回归。
  - **块大小按字符还是按 token。** 本项目按字符（ADR-0008：切分器不该依赖分词器），
    但按 token 更贴近模型的实际输入单位。分歧来自**分层**。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**依赖预算**（正则 vs 语法解析器）与**断言的用途**（锁规格 vs 锁性质）。
- **哪些结论缺少充分证据？**
  - **按类型选策略真的让检索更好了吗？** 本主题只证明了「切分边界对了」（不变量），
    **没证明「检索效果更好了」**——那要等 Day 30 的评估集。**这是本主题最大的未
    验证假设。**
  - **参数取值**：800 / 1200 / 1000 没有任何数据支撑。
  - **正则漏判的频率**：非 Python 代码、非标准题号的习题有多少？不知道。
- **哪些观点不适用于当前项目？**
  - **语法树切分**（tree-sitter）：引入解析器依赖。
  - **语义切分**（用模型判断段落边界）：要模型调用，且成本与不确定性都高。
  - **按 token 预算切**：见上。

## 5. Engineering Practice

- **实现了什么？**
  - **`core/rag/chunking.py`**：
    - `CodeChunker`——按**顶层定义**切（正则给出结构）；超限交给兜底切分器。
    - `ExerciseChunker`——按**题号**切；超限交给兜底切分器。
    - `PolicyChunker`——按 `metadata["kind"]` 选策略，取不到用兜底。
    - `default_chunking_policy()`——**唯一一处数字的所在地**。
  - **`core/application/ingestion.py`**：`to_rag_document(course_document)`——课程
    文档 → 带 `kind` / `course_id` / `title` / `point_ids` 的 RAG 文档。
  - **`tests/test_chunking_strategy.py`**（新增）：19 个用例，锁**不变量**。
  - **`examples/chunking_strategy.py`**（新增）：四段演示。
- **为什么这样设计？**
  - **按类型选策略**：每类材料有它自己的语义单元；定长切代码会拦腰截断，递归切
    代码也不对（段落不是代码的语义单元）。
  - **结构由正则给出**：换语言、换教材改正则即可；识别不出来退回兜底。
  - **参数集中一处**：散落的默认值迟早漂移。
  - **锁不变量不锁数字**：数字会变，不变量不会。
  - **元数据跟着切片走**：检索过滤的唯一依据；材料只解析一次。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 所有材料用递归切分 | 对代码不对（段落不是代码的语义单元） |
  | 所有材料用定长切分 | 一刀切的策略总有一半材料是错的 |
  | 按语言各写一个代码切分器 | N 种语言 N 个类；正则就够 |
  | 引入 tree-sitter 做语法切分 | 更准，但要引入解析器依赖，且换语言要换解析器 |
  | 用模型判断语义边界 | 要模型调用；成本与不确定性都高 |
  | 按 token 计块大小 | 切分器依赖分词器（ADR-0008） |
  | 测试锁住具体参数 | 改动变成「改测试」，断言退化成橡皮图章 |
  | 每个切分器各自带默认参数 | 数字散落，迟早漂移；改一处不知道改了什么 |
  | 课程侧与 RAG 侧各解析一次 | 同一份材料解析两次，浪费且可能不一致 |
- **测试结果如何？**
  - `tests/test_chunking_strategy.py`：19 个用例（按种类选策略、种类不认识退回兜底、
    无元数据退回兜底、**讲义不切断句子**、**切片不超上限**、**切片 id 可复现**、
    **类的完整**、
    无定义时兜底、超长定义走兜底、**习题按题号切**、**答案跟着题走**、无题号兜底、
    课程文档 → 可检索文档、**切片带上知识点关联**、定长切分器不变、策略可替换）。
  - 全量：**889 passed**；`ruff` / `mypy` 全绿；二十五个示例跑通。
- **实践结果是否支持阅读材料中的观点？**
  支持三条：**按语义单元切**（代码与习题各自的边界确实对）；**结构可配**（正则）；
  **断言性质而非取值**。
  **未验证**一条：**按类型选策略是否真的提升检索效果**——本主题只到「边界对了」，
  效果要等 Day 30 的评估集。这条已写进 ADR 的风险项。

## 6. Reflection

1. **今天最重要的知识是什么？**
   **锁不变量，不锁数字。** 「块大小 500、重叠 50」看起来是可断言的规格，但它是
   **实现细节**：数字会随模型与语料变化，而一旦参数变了断言就得跟着改——断言从此
   变成橡皮图章。真正该保护的是「**代码不切断顶层定义**」「**习题不切断一道题**」
   这类**语义完整性**：它们不会随参数变化。**测试要锁住的是不会变的东西。**
2. **哪个观点改变或修正了原来的理解？**
   原以为「递归切分」是通用答案。实现时才发现：**递归切分对代码也不对**——它按段落
   切，而段落不是代码的语义单元（一个函数跨段落、一个段落含半个函数）。递归解决
   的是「自然段被截断」，不是「语义单元被截断」。**每类材料有它自己的语义单元。**
   另一处修正：我原以为「按类型选策略」是个优化；实现后意识到它其实是**正确性**
   问题——一刀切不是「效果差一点」，是「一半材料切错了」。
3. **当前实现还有哪些局限？**
   正则的通用性有限（非 Python 代码、非标准题号会退回兜底）；参数没有实证依据；
   **「按类型选策略提升检索效果」这个假设尚未验证**（要 Day 30）；超限兜底切分会
   破坏结构完整性；没有按 token 计预算；没有语义切分。
