学习领域的五个聚合（目标、进度、诊断、计划版本、题目）怎么存？写入路径如何复用领域层的不变量，而不是绕过它？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **不可变聚合 + 迁移历史**决定了存储模型：一行一聚合，内层形状用文档（JSONB），
    跨聚合的引用用列（外键 + 索引）。
  - **只存历史，不存派生状态**。状态由历史派生，存两份就要同步两处，而两处会漂移。
  - **不变量必须在两端都守**：写时构造领域对象，读时再构造一次。只守一端，数据库
    就是一个可以绕过守门人的入口。
  - **并发覆盖必须显式失败**。不可变模型下的「更新」是整体替换，没有版本号时后写
    的会静默盖掉先写的，而且没人会发现。
  - **负载要有版本**。形状会变；不认识的版本要**明确失败**，不能猜。

## 3. Cross References

| 来源 | 核心观点 | 与主教材的关系 |
|---|---|---|
| PostgreSQL 文档：JSONB 与 CHECK | JSONB 适合存结构会变的文档；CHECK 约束表达行级不变量 | 直接支撑「一行一聚合 + JSONB 负载 + CHECK 把列与负载绑死」 |
| PostgreSQL 文档：CHECK 的三值逻辑 | CHECK 在表达式为 NULL 时**通过**（NULL 不是 FALSE） | **实测出来的坑**：直接写 `CHECK (payload->>'id' = id)` 会让缺字段的行全部漏过去；必须 `COALESCE` |
| Repository 模式（Evans） | 仓储是聚合根与持久化之间的抽象，集合语义由仓储表达 | 支撑「端口与实现分开、协议可替换」；本项目更进一步：端口与实现同包（按能力分包） |
| Kleppmann, *DDIA*（并发章节） | 并发控制的两种思路：悲观锁与乐观锁；乐观锁适合冲突罕见的场景 | 支撑 `revision` + `ConflictError`：冲突罕见但不能静默，冲突时重新读-合并-再写 |
| 文档存储 vs 关系库 | 文档模型适合「整体读写、形状多变」，关系模型适合「跨文档查询与引用完整性」 | 直接对应本项目的取舍：**聚合内部用文档、聚合之间用关系** |
| 本项目 ADR-0015 | 不变量只在内存校验；将来接数据库时写入路径必须复用同一套校验 | 本主题的第一约束——并且补上「读侧也要」 |
| 本项目 ADR-0018 | 「每个知识点一个状态」在知识点很多时会很大；进度持久化形态未定 | 本主题给出实测答案：1000 个知识点时整块重写 0.5 ms，不是问题 |

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  不可变聚合适合文档模型；引用完整性要靠关系模型；并发要有明确的失败方式；
  存储粒度要匹配聚合粒度。
- **哪些观点存在分歧？**
  - **端口该放哪。** 严格六边形架构把端口放内层（领域/应用），适配器放外层；本项目
    按能力分包，端口与实现同包（`core.llm`、`core.memory` 都是这样）。分歧来自
    **团队约定**——两种都能工作，混用才痛苦。
  - **进度该整块存还是逐点存行。** 关系模型的惯性会推着人拆表；但那要在存储层引入
    领域层没有的 diff 机制。本项目选整块，代价已实测（ADR-0026 §7）。
  - **乐观锁放在存储层还是应用层。** 应用层也能做「读-改-写前先查版本」，但那样
    每个仓储实现都要自己判断，规则会散。放在存储层（`ensure_writable` 一处）更
    可靠。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**约定**（分包方式）与**设计目标**（领域粒度优先于存储粒度）。
- **哪些结论缺少充分证据？**
  - **整块进度的上限**：实测到 1000 个知识点没问题，但真实课程规模与迁移频率未知。
  - **列 + JSONB 重复的维护成本**：CHECK 约束写漏一条就会漂移，没有工具能发现
    「漏写」。
  - **负载迁移工具**：形状改过两次都靠「还没有真实数据」侥幸过去；真实数据之后
    这条路要补，而工具怎么做没有先例可抄。
- **哪些观点不适用于当前项目？**
  - **事件溯源**：本项目不重放事件（ADR-0025 已定快照式版本）。
  - **分库分表 / 读写分离 / 多租户**：单人教练场景，远未到那个规模。
  - **完整 ORM**：不可变模型 + 迁移历史映射成可变行，映射器两头不讨好。

## 5. Engineering Practice

- **实现了什么？**
  - **`core/storage/codecs.py`**（新增）：七个聚合的 `*_to_dict` / `*_from_dict`，
    `SCHEMA_VERSION = 1`，负载带 `kind`。解码**重跑领域层不变量**。
  - **`core/storage/protocols.py`**（新增）：`Stored[T]`（领域对象 + 存储版本）、
    `ensure_writable`（乐观锁规则，**只写一处**）、六个仓储协议。
  - **`core/storage/memory.py`**（新增）：进程内实现——存**负载字典**，读回时
    `from_dict` 重建，因此写入路径复用不变量、乐观锁是真的。
  - **`core/storage/errors.py`**（新增）：`StorageError` / `DecodeError` /
    `ConflictError`——与领域错误分开。
  - **`migrations/0001_learning_domain.sql`**（新增）：PostgreSQL schema，9 张表。
  - **`tests/test_learning_persistence.py`**（新增）：30 个用例。
  - **`examples/learning_persistence.py`**（新增）：五段演示 + 成本实测。
- **为什么这样设计？**
  - **领域层不碰存储**：保持纯函数与不可变对象（ADR-0015）。
  - **形状在领域模型之外**：同 `bridge.py` 的理由——映射放在外面，模型才干净。
  - **负载带版本**：形状变过两次；不认识的版本明确拒绝，不半懂半猜。
  - **只存历史**：状态由历史派生，存两份就要同步两处。
  - **读时也校验**：只守写的一端，数据库就能被绕过。
  - **乐观锁规则只写一处**：两个实现对同一次并发必须给出同样答案。
  - **进度整块存**：存储粒度与领域粒度一致才不需要 diff 机制；代价已实测。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 领域模型自带 `to_dict` / `from_dict` | 模型被存储细节污染，且版本升级要改模型文件 |
  | 负载不带版本 | 旧数据只能猜着读——半懂半猜比读不出来更危险 |
  | 存派生状态 | 状态与历史各说一套，ADR-0017/0018 已经否掉 |
  | 只在写时校验 | 数据库是绕过守门人的入口；手工改数据、迁移脚本都能写进非法事实 |
  | 进度逐知识点存行 | 存储层要引入领域层没有的 diff 机制（第二份真相） |
  | 每张表各写一套乐观锁 | 两个实现对同一次并发给出不同答案 |
  | 用 ORM 自动映射 | 不可变模型 + 迁移历史 → 可变行，映射器两头不讨好 |
  | 事件溯源 | 本项目不重放事件；复杂度远超收益 |
  | 直接写 CHECK 而不用 COALESCE | **实测**：缺字段的行全部漏过去 |
  | 现在就写 SQL 适配器 | 驱动选型未定，写出来只能是不能测的代码 |
- **测试结果如何？**
  - `tests/test_learning_persistence.py`：30 个用例（七个聚合的往返；派生状态不落库；
    未知版本 / 缺版本 / 缺字段 / 类型不对 / 种类不对都拒绝；迁移历史断链、进度
    历史非法、判定无依据都在**读回时**被拒；乐观锁的新建 / 同版本 / 旧版本 / 记录
    已删四种情形；六个内存实现满足协议；按学习者 / 目标 / 知识点 / 计划线过滤；
    缺记录返回 `None`；进度身份是（学习者, 课程））。
  - **DDL 在真实 PostgreSQL 18 上验证**：干净应用，9 张表；逐条验证 CHECK 与外键
    确实拒绝坏数据（缺 schema_version、缺 id、id 与列不一致、外键指向不存在的
    实体、number 非数字）。
  - 全量：**830 passed**；`ruff` / `mypy` 全绿；二十二个示例跑通。
  - 成本实测（1000 次取均值）：
    | 知识点数 | 负载 | 编码 | 解码 | 一次迁移（整块重写） |
    | -------- | ---- | ---- | ---- | ------------------ |
    | 50 | 13.0 KB | 0.02 ms | 0.17 ms | 0.03 ms |
    | 200 | 51.8 KB | 0.08 ms | 0.64 ms | 0.11 ms |
    | 1000 | 258.8 KB | 0.47 ms | 4.64 ms | 0.51 ms |
- **实践结果是否支持阅读材料中的观点？**
  支持三条：**聚合内部用文档、聚合之间用关系**（CHECK 把两边绑死）；**并发要
  显式失败**（`ConflictError`）；**不可变聚合适合文档模型**。
  **修正**一条：ADR-0018 担心的「知识点很多时进度很大」——实测到 1000 个知识点时
  整块重写只有 0.5 ms，**不构成问题**；而且**读的成本与存储形态无关**（领域对象
  本来就持有 N 个 `PointProgress`），那笔成本被错记在存储头上了。

## 6. Reflection

1. **今天最重要的知识是什么？**
   **只守一端等于没守。** 「写入路径复用领域层不变量」听起来是说写，但只守写的一
   端，数据库仍然是一个可以绕过守门人的入口——手工修数据、迁移脚本、任何直接写
   库的工具都能写进非法事实。**读的时候再构造一次领域对象**，非法数据就永远出不
   来领域层。两端都守，成本只是多一次构造。
2. **哪个观点改变或修正了原来的理解？**
   原以为 ADR-0018 说的「每个知识点一个状态在知识点很多时会很大」是**存储**问题。
   实测之后发现：**读的成本与存储形态无关**——领域对象本来就持有 N 个
   `PointProgress`，重建是领域层的事；存储形态只影响**写**的成本，而 1000 个知识点
   时整块重写也只有 0.5 ms。那笔账被算错了地方。
   另一个修正：**「乐观锁」不是一个功能，是一个契约**——它要求「两个实现对同一次
   并发给出同样的答案」，因此规则必须只写一处，否则内存实现与 SQL 适配器迟早
   漂移。
3. **当前实现还有哪些局限？**
   SQL 适配器没写（驱动选型未定）；负载迁移工具没做（形状改过两次都靠「还没有真实
   数据」侥幸过去）；列与负载的重复靠 CHECK 维持，漏写一条就会漂移且没有工具能发
   现；题目上的 `point_id` 建不了外键（知识点是课程内的）；整块进度的上限只在
   1000 点内验证过；没有备份恢复、没有连接池、没有迁移执行器。
