## 1. Engineering Question

学习领域的五个聚合（目标、进度、诊断、计划版本、题目）怎么存？写入路径如何复用领域层的不变量，而不是绕过它？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **不变量必须住在写入路径上。** 内存里校验过的数据，入库后可以被绕过——如果
    写入路径不重跑同一套校验，数据库就成了一个没有守门人的入口。
  - **不可变实体 + 迁移历史**意味着「更新」是「追加 + 派生」。存储形态必须跟着这
    个模型走，而不是硬塞成「一行一状态」。
  - **仓储层是协议，不是实现。** 领域层只说「按什么取回」，不说「存哪儿」。
  - **先定形态，再谈实现。** 后面每个主题都要「持久化」，没有共同形状就会各写
    各的。

## 4. Compare and Challenge

- 不同资料有哪些一致观点？
  - 聚合根是仓储的边界；不变量在构造期；schema 由领域形状决定。
- 哪些观点存在分歧？
  - **ORM 还是手写 SQL。** ORM 快速但容易把不可变模型映射成可变行；手写 SQL 啰嗦
    但可控。本项目倾向**手写 SQL + 显式映射**，因为领域对象是不可变的、带迁移
    历史的——自动映射器在这两种形状上都不省心。
  - **JSON 文件还是 PostgreSQL。** Phase 0 的会话用的是 JSON 文件存储（ADR-0009），
    它够用且零依赖；但它做不了「按知识点更新进度」这类增量写，也做不了跨会话
    的查询。Phase 2 起要跨会话保留学习状态，JSON 到顶了。
- 分歧来自应用场景、设计目标还是技术演进？
  - 主要来自**设计目标**（不可变 + 历史 + 构造期校验）与**现实规模**（要增量写、
    要跨会话查）。
- 哪些结论缺少充分证据？
  - **进度「整体重建 vs 增量更新」的成本**：知识点很多时（ADR-0018 提到 200 个
    知识点的场景）差多少，没有实测。
  - **迁移历史独立成表 vs 内嵌 JSON 列**：取决于查询需求——「目标为什么变成现在
    这样」要能被查吗？
- 哪些观点不适用于当前项目？
  - **事件溯源**：本项目不重放事件（ADR-0025 已定快照式版本）。
  - **多租户 / 行级安全**：单人教练场景，暂不需要。
  - **分库分表 / 读写分离**：远未到那个规模。

## 5. Engineering Practice

- 实现了什么？
  - 仓储协议（按聚合根读写）+ `to_dict` / `from_dict` 形状
  - PostgreSQL schema 草案（目标 + 迁移历史、进度、诊断 + 证据、计划版本、题目）
  - 写入路径复用领域层不变量
  - 不可变实体 + 迁移历史的存储形态
  - 版本号与并发写（乐观锁）
- 为什么这样设计？
  - **写入路径复用不变量**：否则数据库是没有守门人的入口（ADR-0015）。
  - **状态不落库，只存历史**：状态由迁移历史派生（ADR-0017），存冗余状态就要
    同步两处。
  - **仓储是协议**：领域层不依赖存储实现，测试可以替换。
- 有哪些替代方案？
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 继续用 JSON 文件 | 撑不住增量写与跨会话查询；Phase 2 起要跨会话保留学习状态 |
  | ORM 自动映射 | 不可变模型 + 迁移历史映射成可变行，映射器两头不讨好 |
  | 状态字段落库 | 状态与历史各说一套，ADR-0017 已经否掉 |
  | 仓储层直接返回 dict | 领域对象的不变量就漏在仓储外了 |
  | 每个主题各写一套存储 | Phase 2–4 会开出四套互不兼容的做法 |
