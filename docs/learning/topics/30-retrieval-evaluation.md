## 1. Engineering Question

检索评估集应该如何构建？Recall 与相关性的差异说明了什么？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **相关性的粒度要和「会被改动的东西」错开。** 切片 id 随切分参数变，来源不会——
    评估集必须锚在不会变的那一层。
  - **命中率与召回是两个问题。** 「有没有找到」与「找全了没有」差的是**切分粒度**
    （一份材料切成二十片，只召回一片）。
  - **词面用例是基线，语义用例是量尺。** 两者的差距就是嵌入模型的能力边界。
  - **只给汇总数字的评估没法指导改进**——得看见哪条没中、为什么。
  - **评估的前提是嵌入可信。** 用占位嵌入器做的任何「A 比 B 好」的结论都不成立。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  召回与排序分开测；评估集要覆盖不同查询类型；失败案例要能看；指标用来比较而非宣称。
- **哪些观点存在分歧？**
  - **评估集从哪来。** 常见做法是从文档反推问题（拿每个段落写一个问句）；本项目
    从**知识点**反推（先定知识点，再配材料与问法）。分歧来自**偏差方向**：从文档反推
    的问题必然偏向「文档里有这个词」，测不出语义检索的短板。
  - **Precision 要不要算。** 通用做法在切片粒度上算；本项目**不做**——一份材料切
    成十片，十片都「相关」，但那是同一份材料的十片。分歧来自**相关性粒度**。
  - **评估要不要跑真实模型。** 有的做法直接用真模型 + 真语料；本项目用占位嵌入器 +
    人工语料，理由是**默认套件必须离线可跑**。分歧来自**优先级**：先有可重复的机制
    验证，再有可信的质量结论。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**相关性粒度**与**优先级**（机制先于质量）。
- **哪些结论缺少充分证据？**
  - **「按类型选切分策略真的更好吗」——仍然没验证。** 本主题的诚实结论是「**测不
    出来**」：占位嵌入器偏向大块，语料只有六份。**既不能说它更好，也不能说它更差。**
  - **Recall 的阈值**：多来源的用例该要求几份才算找全？本项目按「全部应命中来源」算。
  - **语料规模**：六份材料、十一条查询，能看出方向，说明不了上限。
- **哪些观点不适用于当前项目？**
  - **nDCG / MAP**：需要「相关程度分级」的标注，成本远高于来源级的二值判断。
  - **LLM-as-a-judge 评估检索**：判官不可回归，不能当门禁（ADR-0014）。
  - **A/B 与线上日志**：没有真实用户。

- **实现了什么？**
  - **`evals/retrieval.json`**（新增）：11 条用例，词面 / 语义 / 多来源三类。
  - **`evals/corpus/`**（新增）：六份材料（讲义 ×3、习题、参考、代码）。
  - **`core/rag/evaluation.py`**：

    - `RetrievalCaseResult`（每条用例的期望、实际、排名、召回）。
    - `RetrievalMetrics.recall`（召回@来源）与 `.results`（详情）。
    - `StrategyRow` / `StrategyComparison` / `compare_strategies`（策略对比）。
  - **`core/rag/retrieval.py`**：新增 `per_source`（按来源去重，默认 1）与
    `oversample`（默认 3）——**据评估结果调整检索**。
  - **`core/rag/store.py`**：修掉 pgvector 的空库路径（见 §关键发现）。
  - **`tests/test_retrieval_evaluation.py`**（新增）：12 个用例。
  - **`tests/test_pgvector_store.py`**：新增「扩展缺失时给出能照着做的错误」。
  - **`examples/retrieval_report.py`**（新增）：四段演示。
- **为什么这样设计？**
  - **来源粒度的相关性**：切片 id 随切分参数变；数据集不能跟着变。
  - **三类用例**：词面是基线、语义是量尺、多来源测召回。
  - **召回与命中率分开**：差值指向切分粒度或近似误差——**这是不同的病因**。
  - **不做 Precision**：切片粒度上的 Precision 会误导。
  - **详情可查**：只知道汇总数字没法定位问题。
  - **按来源去重**：碎片竞争 top_k 名额是评估暴露的真问题；相邻切片高度重叠，一起进
    上下文是浪费。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 从文档段落反推问题 | 偏向「文档里有这个词」，测不出语义短板 |
  | 在切片粒度上算 Precision | 一份材料切十片，十片都「相关」——指标误导 |
  | 只报汇总数字 | 知道「差」不知道「差在哪」 |
  | 不做召回只看命中率 | 找对了但没找全——正是切细之后的真问题 |
  | 检索不按来源去重 | 碎片互相竞争名额，别的材料被挤出去 |
  | 用真模型 + 真语料做默认测试 | 默认套件必须离线可跑；质量结论另找时机 |
  | 直接用真嵌入做策略对比 | 现在没有可用的真嵌入（无凭证），且默认套件不能依赖外部服务 |
  | 让应用运行时建 pgvector 扩展 | `CREATE EXTENSION` 要超级用户权限，应用连接串不该有 |
- **测试结果如何？**
  - `tests/test_retrieval_evaluation.py`：12 个用例（评估集加载、词面与语义都有、多来源
    用例存在、坏评估集报错、缺 query 报错、指标有值、召回与命中率分开、每条用例记着
    期望与实际、按类别分组、空评估集给零指标、策略对比、按类型选切得更细）。
  - 策略对比（真实数字，同一份评估集）：
    | 策略 | 切片数 | hit@1 | hit@3 | hit@5 | MRR | 召回 |
    | --- | --- | --- | --- | --- | --- | --- |
    | 按类型选 | 16 | 0.27 | 1.00 | 1.00 | 0.59 | 1.00 |
    | 全部递归 | 6 | 0.55 | 1.00 | 1.00 | 0.76 | 1.00 |
    | 全部定长 | 6 | 0.55 | 1.00 | 1.00 | 0.76 | 1.00 |
  - **按来源去重前后**（按类型选）：召回 0.77 → **1.00**，hit@3 0.73 → **1.00**，
    MRR 0.51 → **0.59**。
  - 全量：**921 passed**；`ruff` / `mypy` 全绿；二十七个示例跑通。
- **实践结果是否支持阅读材料中的观点？**
  支持三条：**召回与排序分开测**；**失败案例要能看**；**评估集要覆盖不同查询类型**。
  **修正**一条：本来以为「召回低」总是切分太碎。实现后才发现另一半——**名额**问题：
  碎片互相竞争 top_k 名额，修法是按来源去重而不是换嵌入。**指标之间会互相影响，
  先分清是召回问题还是名额问题，再动手。**

## 6. Reflection

1. **今天最重要的知识是什么？**
   **评估的前提是嵌入可信。** 用占位哈希嵌入器做的任何「A 比 B 好」的结论都不成立
   ——它按词重叠打分，**块越大越容易与查询共享词**，所以对比天然偏向大块。本主题
   辛辛苦苦做出了一张对比表，最后诚实的结论是「**测不出来**」。**做出评估容易，
   说出「测不出来」才是评估的价值。**
2. **哪个观点改变或修正了原来的理解？**
   原以为「召回低 = 切分太碎」。实际上另一半原因是**名额**：切细之后一份材料的多个
   碎片互相竞争 top_k 名额，把别的材料挤出去——修法是**按来源去重**，而不是换嵌入
   或改切分。另一个修正：**评估集的大小决定对比有没有意义**——第一版语料太短，三种
   策略切出来完全一样，对比是空的。
3. **当前实现还有哪些局限？**
   评估集是人工合成的，不可外推；占位嵌入器让策略结论不可信；语料只有六份、查询
   十一条；Recall 的多来源阈值是「全部命中」；没有 nDCG 之类的分级指标；没有真实语料
   与真嵌入的评估时机；pgvector 的适配器注册错误信息只覆盖了「扩展缺失」这一种原因。
