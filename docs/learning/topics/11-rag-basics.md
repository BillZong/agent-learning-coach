# Topic: RAG 基础

> Day 11 ｜ Phase 0 · Agent Engineering Foundation ｜ 主教材：Ch5：5.1～5.3 ｜ 外部参考：RAG 代表性论文 ｜ 状态：已完成

## 1. Engineering Question

Chunking 策略如何影响检索质量？Document Loader 到 Vector Retrieval 这条流水线中，哪一环最先失效？

## 2. Primary Reading

- Book: Ch5：5.1～5.3
- Chapter / Section: Ch5 5.1～5.3
- 核心观点：
  - **5.1 用内部数据的问题**：模型参数里的知识是「训练时冻结的」，而内部数据
    （教材、笔记、文档）是活的。RAG 解决的是「把模型不知道的东西变成它能取到的
    东西」。
  - **5.2 搜索方法的类型**：关键词搜索、向量搜索、图搜索、结构化搜索——它们
    解决的问题不同。向量搜索擅长「意思相近」，关键词搜索擅长「精确标识符」。
    这两类**不是替代关系**。
  - **5.3 实践向量搜索**：嵌入 → 切分 → 向量检索三步。5.3.2 的切分是**定长
    切分**（固定长度 + 重叠）；5.3.3 的检索是**余弦相似度**排序取 top-k。
    这是教学用的最小实现，不是生产形态。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  全部一致认为：**切分策略决定检索质量的上限**，且检索质量必须**分层评估**（召回
  与生成分开看），不能只看最终答案。综述、LangChain、pgvector 文档在工程细节上
  互补，但方向一致。
- **哪些观点存在分歧？**
  - **切分要不要保留重叠**：主教材 5.3.2 的定长切分**带重叠**；LangChain 的
    结构化切分通常**不带重叠**（靠更大的块与更聪明的合并）。分歧来自目标不同：
    固定长度切分的场景（网页、日志）里重叠用来补偿硬边界；结构化切分靠边界
    本身保语义，重叠反而引入重复召回。
  - **要不要有「关键词 + 向量」两路**：主教材 5.2 把它们并列成不同方法，暗示
    二选一；综述与工程实践普遍认为混合检索更好。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**应用场景**：教材材料是结构化的 Markdown，网页抓取是扁平的纯文本，
  两者对切分的要求相反。
- **哪些结论缺少充分证据？**
  - 「块大小 500–1000 tokens 最好」这类**具体数值**在各资料里都是经验值，
    没有普适证据。**本项目直接拒绝硬编码它**——块大小是参数，不是常量。
  - 「HNSW 一定比 IVFFlat 好」也缺证据：HNSW 召回率高、内存占用大，IVFFlat
    反之。本项目选 HNSW 是因为**召回率优先**，不是因为它全面更优。
- **哪些观点不适用于当前项目？**
  - 综述里的「生成器变体」「多路召回」「重排」都还太早——本项目连**关键词
    检索**都还没有，混合检索无从谈起。
  - 「查询改写」需要多轮对话的历史上下文，而本项目的 RAG 目前是**单轮**的。

## 5. Engineering Practice

- **实现了什么？**
  - `core/rag/types.py`：`Document` / `Chunk` / `ScoredChunk`——**摄取单位与
    检索单位分开**。
  - `core/rag/loader.py`：`DocumentLoader` 协议 + `TextFileLoader` +
    `DirectoryLoader`；文档 id 由来源哈希推导（**可复现**）。
  - `core/rag/chunking.py`：`Chunker` 协议 + `FixedSizeChunker`（主教材 5.3.2
    的做法）+ `RecursiveChunker`（按段落 → 句子 → 字符递归降级）。
  - `core/rag/embedding.py`：`EmbeddingClient` 协议 + `HashingEmbedder`（离线、
    确定性）+ `OpenAICompatibleEmbedder`（生产，可用 httpx MockTransport 离线
    测试）。
  - `core/rag/store.py`：`VectorStore` 协议 + `InMemoryVectorStore` +
    `PgVectorStore`（建表 + HNSW + 余弦距离 + SQL 下推过滤）。
  - `core/rag/retrieval.py`：`VectorRetriever`——只做「嵌入 → 检索」，过滤条件
    原样下推。
  - `core/text.py`：抽出共享分词（memory 与 rag 共用）。
  - 演示：`examples/rag_pipeline.py`（离线 + `--pg` 两条路径）。
- **Document Loader**
  - 只做一件事：把外部材料读成 `Document`。不切分、不嵌入。
  - **id 由来源推导**：重新摄取不会产生「同一份材料的两份记录」。
  - 读不了 / 空文件被跳过并记录原因——**不让一份坏文件毁掉整批摄取**。
- **Chunking**
  - 定长切分**会**把句子拦腰截断（测试直接观察到）。
  - 递归切分**不**截断自然段（测试直接观察到）。
  - 块大小按**字符**不按 token：切分器不该知道用的是哪种模型。
  - 两者都支持重叠，重叠不小于块大小时报错（否则切分会原地打转）。
- **Embedding**
  - 哈希嵌入用 SHA-256 而非内置 `hash()`——后者每个进程种子不同，「同样文本
    得到同样向量」会失效。
  - 带符号的哈希投影：不同词撞进同一桶时**相互抵消**而不是叠加。
- **Vector Retrieval**
  - 内存实现与 pgvector 实现的**相对顺序一致**（有测试直接验证）。
  - pgvector 的 `<=>` 是**距离**，实现负责换算成相似度。
  - 过滤在 SQL 里做：`metadata ->> %s = %s`，索引能用上。
- **为什么这样设计？**
  - 每个协议两个实现：**离线可测** 与 **能上生产** 是两个不同的目标，一个
    实现同时满足两者会两头不讨好。
  - 检索器刻意很薄：没有重排、没有查询改写、没有多路召回。每加一层就多一个
    「哪一层先失效」的排查对象。
- **有哪些替代方案？**
  | 方案 | 为什么没选 |
  |---|---|
  | ChromaDB（依赖里已有） | 自带的 embedding function 绑定 OpenAI；本项目要自己控制嵌入与过滤下推。且它是参考项目带过来的声明，本项目路线是 pgvector |
  | FAiss / hnswlib（进程内向量索引） | 需要自己管持久化；PostgreSQL 已经能存结构化元数据并下推过滤，少一个组件 |
  | Elasticsearch（BM25 + 向量） | 混合检索确实更强，但要再运维一个服务。当前规模不值得——**这是缺口，不是结论** |
  | 直接把教材塞进上下文 | 材料一多就撑爆预算；且违反「注意力预算」原则（Anthropic） |
  | 按 token 切分 | 精确，但让切分器依赖分词器；token 预算由呈现层负责更合理 |
- **测试结果如何？**
  - `tests/test_rag.py`：**37 passed**（含 2 条真实 pgvector 测试；无数据库时
    跳过而非伪造通过）。全量 **482 passed**，ruff / mypy 全绿。
  - 测试覆盖的关键行为：定长切分**确实**截断句子、递归切分**确实**不截断；
    过滤**确实**下推；两种存储**顺序一致**；维度不一致**确实**报错。
- **实践结果是否支持阅读材料中的观点？**
  - **支持，且强化了**：「切分是检索质量的第一个决定因素」——两个切分器在同一
    段文本上的差别肉眼可见（定长把「尾递归可以被优化成」截断，递归落在段落
    边界）。
  - **修正了**：主教材 5.3.2 的定长切分**不是**通用默认，只是起点。本项目默认
    用递归切分。
  - **补充了**：主教材完全没讲「元数据过滤下推」和「距离 vs 相似度方向」这两件
    会在生产环境直接咬人的事。

## 6. Reflection

1. **今天最重要的知识是什么？**
   「Indexing code ≠ context retrieval」从一句引言变成了本项目的一条设计约束：
   **过滤必须下推到存储层**。在应用层过滤等于把全部向量拉回内存再筛——那
   向量库就退化成一个 JSON 文件，索引白建。
2. **哪个观点改变或修正了原来的理解？**
   原以为「切分就是按长度切，加点重叠」。实际实现完才看到定长切分把句子截断的
   代价——**一半的切片说的是半句话，两半都检索不到完整的意思**。切分不是
   机械操作，它决定「一个能被检索到的最小单位」是什么。
   另外修正了「嵌入 = 语义相似」的默认假设：哈希嵌入是**词汇**相似，两者不是
  一回事，把它当语义模型用会得出错误结论。
3. **当前实现还有哪些局限？**
   - **没有关键词检索**——精确标识符场景不如 BM25。
   - **没有重排、没有查询改写、没有增量更新**。
   - **哈希嵌入是占位级的**，只捕捉词汇相似。
   - **`PgVectorStore` 每次操作开连接**，不适合高并发。
   - **加载器只支持纯文本与 Markdown**，PDF 留给 Day 27。
   - **检索质量还没有被量化**——recall@k / MRR 属于 Day 30 的检索评估 topic，
     现在只能靠人眼看结果。
