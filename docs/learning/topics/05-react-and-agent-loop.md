# Topic: ReAct 与 Agent Loop

> Day 5 ｜ Phase 0 · Agent Engineering Foundation ｜ 主教材：Ch4：4.1～4.2、4.6 ｜ 外部参考：Anthropic Workflow Patterns ｜ 状态：已完成

## 1. Engineering Question

ReAct 循环在什么条件下必须停止？Stop Condition 与 Max Steps 如何配合，既避免死循环，也避免过早收敛？

## 2. Primary Reading

- Book: Ch4：4.1～4.2、4.6
- Chapter / Section: Ch4 4.1～4.2、4.6
- 核心观点：
  - **4.1 think-act 循环**：模型推理（think）后执行动作（act），动作结果回到上下文（observe）供下一轮推理。循环的价值不在「让模型多想一会儿」，而在让模型能**拿到事实**再决定。
  - **4.1.2 从文本解析到工具调用**：让模型「输出 JSON 再自己解析」是脆弱的——解析失败就断链。工具调用把「请求执行什么」变成协议的一部分，参数由结构保证。
  - **4.2.2 信息流是核心设计**：Agent 的价值在于「模型 ↔ 工具」之间的信息流，而不是某个提示词技巧。
  - **4.6.3 step() 方法**：`run()` 是循环，`step()` 是一步。一步 = think + act。分开之后，步数天然成为预算单位。
  - **4.6.4 think() 与 act() 分开**：两个方法各自可替换——换模型只改 think，换工具只改 act。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  - 循环必须有终止条件，且**不能只靠步数**——步数是兜底，模型停止才是主路径。
  - 工具失败应回填给模型让它自愈，而非中断运行。
  - think 与 act 应可分别替换。

- **哪些观点存在分歧？**
  - **单次采样 vs 多次采样投票**：官方指南倾向「简单循环 + 好提示词」，研究结果则显示自洽性（多次采样）能提升准确率。两者对成本的态度不同。
  - **工具调用失败该不该终止**：多数框架选择抛异常终止；本项目选择回填。

- **分歧来自应用场景、设计目标还是技术演进？**
  - **来自应用场景**：自洽性适合「一次性问答、单轮可完成」的任务；学习教练是**多轮交互**——投票没有意义，因为对话还要继续。
  - **来自设计目标**：本项目的第一原则是「模型能自愈的错误就让它自愈」，与「失败即中断」的设计目标直接冲突。

- **哪些结论缺少充分证据？**
  - 「ReAct 优于纯 CoT」的实验多在有明确答案的多跳推理任务上；**开放式教学对话**里收益如何，缺少直接证据。
  - 「并行工具调用降低延迟」的结论成立，但**结果顺序的确定性**与**取消传播**的代价很少被讨论——这两点恰是并发最难的地方。

- **哪些观点不适用于当前项目？**
  - **预编排工作流（prompt chaining / routing）**：适合路径确定的任务；学习教练的路径由学习者的回答决定，运行时才知道下一步该做什么。
  - **自洽性投票**：多轮交互里没有可投票的单次答案。
  - **图/状态机式的循环表达**：LangGraph 的条件边适合需要人工介入、需要检查点的流程；本项目的循环是单一「模型 → 工具 → 回填」的直线，引入图模型是过度设计。

## 5. Engineering Practice

- 实现了什么？
  - 新增 `src/agent_learning_coach/core/agent/` 包（与 `core/llm`、`core/tools` 平级）：
    - `loop.py`：`AgentLoop`——ReAct 循环控制与停止条件
    - `types.py`：`AgentConfig` / `AgentStep` / `AgentRun` / `StopReason`
  - 循环形状：`Think`（模型） -> `Act`（工具） -> `Observe`（结果回填） -> `Think` ...
- Think / Act / Observe
  - 三个阶段各自是独立方法：`_think` / `_act` / `_observe`——不内联在 `run()` 里，因为三者的失败模式不同，混在一起无法单独验证
  - `Think`（`_think`）：构造 `LLMRequest`（对话 + `registry.specs()` 工具清单）交给 `LLMClient`
  - `Action`（`_act`）：`ToolDispatcher.dispatch_safe` 执行模型请求的工具调用——参数校验、超时、结果归一化全部复用工具系统，循环不重复实现
  - `Observe`（`_observe`）：`ToolOutcome.to_message_result` 转成 `ToolResult` 回填进对话记录
  - 一处归属细节：工具调用 id 来自**调用**而非执行结果——`ToolOutcome` 描述的是工具本身，不知道它属于哪一次调用
- Stop Condition
  - 六种停止原因，分三层：**自然结束**（模型不再请求工具，唯一成功路径）、**模型不再前进**（`consecutive_errors` / `repeated_call`）、**预算兜底**（`max_steps` / `max_tool_calls` / `timeout`）
  - 更具体的停止原因优先：`repeated_call` 指向模型行为，`max_steps` 只是预算耗尽
- Max Steps
  - `AgentConfig.max_steps` 是步数硬上限（默认 12）；`max_tool_calls` 是工具调用总预算，**在步之间检查**——当前步内的调用全部执行完，保证每条 `tool_call` 都有对应 `tool_result`
  - 额外加一个 `max_repeated_calls`：检测「同一工具同一参数反复调用」，补上「步数用完才停」的时间浪费
- 为什么这样设计？
  - **循环独立成包**：放进 `core/llm` 会让模型客户端不再纯粹，放进 `core/tools` 则让工具系统知道模型的存在。独立后换模型或换工具来源（本地 / MCP）都不需要改循环
  - **失败回填而非终止**：工具出错一律归一化成错误结果回填给模型，让它换参数、换工具或直接回答。模型能自愈的错误就让它自愈——这是「过早收敛」的主要防护
  - **预算是兜底不是目标**：只有模型自己知道任务是否完成，任何预算都不该替代这个判断
  - **对话记录不变量**：每条 `tool_call` 都有对应 `tool_result`，因此结果可直接作为下一轮对话输入继续
- 有哪些替代方案？
  - 放进 `core/llm/`：与模型客户端同层，但 `core/llm/` 是纯「模型调用」职责，循环引入会破坏它的纯粹性
  - 放进 `core/tools/`：不推荐——工具系统不该知道模型的存在
  - 工具失败直接抛异常终止（参考项目 `ai-agent-from-scratch` 的做法）：简单，但把模型能自愈的错误变成了运行失败
  - 只用 `max_steps` 一个停止条件：够用但不够快——模型可能用满 12 步反复调同一个工具
- 测试结果如何？
  `pytest` 228 passed；`core/agent` 行覆盖与分支覆盖均 100%。
  `ruff format --check` / `ruff check` / `mypy` 全部通过。
  变异验证：分别破坏「不回填工具结果」「去掉重复调用检测」「工具失败直接终止」三处实现，对应测试分别失败 6 / 2 / 5 条——测试确实咬得住行为，而不是只走过场。
- 集成验证：换工具来源不改循环
  - 新增 `examples/agent_loop_with_mcp.py`：真实 MCP 子进程 + 真实协议，把远端 MCP 工具与本地工具放进**同一个注册表**，由**同一个循环**驱动
  - 新增 `tests/test_agent_loop_mcp.py`（7 例）：远端工具经循环调用、两类工具平级共存、模型看到混合工具清单、远端失败回填、远端参数本地校验、示例脚本真实跑通
  - 集成时暴露一条此前只写在文档里的约束：**远端工具的生命周期绑定在会话上**，会话关闭后已接入注册表的远端工具立即失效。适配器改为按 `CONNECTION_CLOSED` 错误码识别，给出明确错误而非含糊的 "Connection closed"
- 异常处理：每类失败都有明确处理
  - 工具级失败（参数不合法 / 工具报错 / 工具不存在 / MCP 会话关闭）→ 归一化成错误结果回填，循环继续
  - 模型调用失败（`LLMError`）→ `stop_reason="llm_error"`，保留部分结果；**非 `LLMError` 的异常照常抛出**（那是编程错误）
  - 初版把「模型失败向上抛出」当成优点，实现后发现它与超时处理不一致——超时返回部分结果，模型失败却丢掉整次运行。统一为「运行时失败返回部分结果」
- 交付物
  - `examples/basic_react_agent.py`：基础 ReAct Agent，纯本地工具、无子进程、无凭证，脚本化模型走完三轮工具调用
  - `examples/agent_loop_with_mcp.py`：同一个循环驱动远端 MCP 工具与本地工具
  - 两个示例并列即可看出「换工具来源不改循环」
- 实践结果是否支持阅读材料中的观点？
  - 支持「Stop Condition 与 Max Steps 要配合」：单靠 Max Steps 只能保证「会停」，不能保证「及时停」；单靠 Stop Condition 又无法兜底病态模型。两者配合才既避免死循环也避免过早收敛。
  - 修正一处直觉：最初以为「工具不存在」是配置错误、该终止；实测把错误回填后，模型会自行改用其它工具并正常完成。终止反而更早地放弃了一个模型能纠正的错误。
  - 反面教材：停止原因的**优先级**必须显式定义。初版里「步数用完」与「原地打转」同时命中时，测试断言失败暴露了歧义——规则定为「更具体者优先」并补了测试。

## 6. Reflection

1. 今天最重要的知识是什么？
   **停止条件的层次比停止条件的数量更重要。** 多数实现把「模型停止」「步数上限」「工具失败」当成三个并列条件，结果是逻辑纠缠、优先级不明。分层之后问题自然消解：主路径只有一个（模型停止），兜底有若干（步数、预算、失败），两者永远不会互相干扰——**预算是兜底，不是目标**。
2. 哪个观点改变或修正了原来的理解？
   原本以为「工具调用失败」要区别对待——参数不合法是模型的问题（回填），工具内部崩溃是系统的问题（中断）。实测发现不必区分：把两者都回填，模型对工具崩溃的应对是「换个工具」或「直接回答」，效果比中断好。统一处理反而更简单，也更符合「模型能自愈的错误就让它自愈」。
3. 当前实现还有哪些局限？
   工具顺序执行不并发（并发需处理取消传播、超时传播与结果顺序的确定性）；上下文不裁剪（记录原样返回，压缩由调用方决定）；模型调用失败向上抛出不重试；一次运行是原子的，无中断与恢复的检查点。
