# Topic: Plan Versioning

## 1. Engineering Question

计划版本化后，如何表达「同一计划的修订」与「全新计划」？查询接口应如何排序与过滤？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **版本号是领域事实，时间戳是环境事实。** 序号由系统在生成时分配，不会补录、
    不会乱序；时间由外部提供，会录错、会乱。**决定顺序的东西应该由决定它的人
    分配。**
  - **「修订」与「重做」是两种不同的活动。** 前者继续同一份东西的历史，后者开
    一份新的。数据模型必须能区分，否则「这份计划从哪来」永远说不清。
  - **变更记录要记「变了什么」与「为什么变」。** 只记最终状态，事后无法回答
    「当初为什么这么排」。
  - **版本要有依据。** 「这一版是基于什么生成的」与「它和上一版差在哪」是两个
    不同的问题，缺一不可。
  - **跨集合的顺序需要显式规则。** 「当前是哪一个」是最常被问的问题，答错的
    代价最高。

## 3. Cross References

| 来源 | 核心观点 | 与主教材的关系 |
|---|---|---|
| Git 提交图 | 提交有稳定的**序号**与**图结构**；`HEAD` 指向当前分支的最新提交；排序靠图结构而不是时间戳 | 直接支撑「同一计划线内按版本号排序」与「当前版本 = 线内最后一个」；也支撑「分支」对应「计划线」——换一条学习路径就是开一条新线 |
| Event sourcing（事件溯源） | 只存**变更事件**，当前状态是重放出来的；快照是可选的加速结构 | 呼应「计划是派生的」：本项目不重放事件，但保留了「输入（依据）→ 输出（内容）」的完整链条——与事件溯源同一种「过程留痕」的精神 |
| 文档修订历史（track changes） | 修订记的是**差异**（谁改了什么），不是最终文本；差异才是审阅的对象 | 直接支撑 `PlanDelta`：新增、移除、重排——**只比排程，不比措辞** |
| 学习者状态追踪（learner modeling / learning traces） | 记录「当时知道什么」比记录「最后一次答了什么」更有用 | 支撑 `PlanBasis` 记**进度快照**（生成时已会哪些点）而不是只记诊断 id |
| 事件溯源里的版本号 vs 时间戳 | 并行写入时的时间戳不可靠，序号才是全序 | 直接支撑本主题的核心决定：**排序不靠时间** |
| 本项目 ADR-0013（运行时计划）/ 0017（目标迁移）/ 0020（诊断） | 运行时有版本历史与状态机；目标的迁移必带理由；诊断有独立身份 | 三条先例分别对应本主题的三个决定：版本历史留痕、理由必填、活动有独立身份 |

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  序号优先于时间；差异比最终态更有审阅价值；过程要留痕；「当前」要有确定
  规则。
- **哪些观点存在分歧？**
  - **存事件还是存快照。** 事件溯源派主张只存变更、重放得出状态；本项目存**版
    本快照 + 依据 + 差异**。分歧来自**需求规模**：本项目的计划是几十个单元的小
    对象，重放的收益抵不上复杂度；而快照让「当时是什么样」可以被直接展示与审
    计。
  - **版本要不要有独立身份。** Git 的提交靠内容哈希天然唯一；本项目给了显式
    的 `PlanVersionId`。分歧来自**存储未定的现实**（ADR-0019 仓储层未实现）——
    显式 id 让「引用某个版本」在存储落地前就能表达。
  - **「当前计划线」怎么选。** 可以按「最近开始的」「版本最多的」「最近改过
    的」。分歧来自**产品语义**：本项目按「最近开始的」，因为一条用旧了的线往
    往版本更多、也常常最近被改过——按那两个规则会选错。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**设计目标**（小对象、可审计、不引入重放机制）与**现实约束**（存储
  未定）。
- **哪些结论缺少充分证据？**
  - **计划线会不会越开越多**：反复「换路径」会留下一堆线，而查询只给「最近开始
    的那条」。没有数据说明现实中会不会发生、发生了怎么清理。
  - **结构指纹够不够**：指纹能回答「结构变没变」，但不能回答「变得影不影响这一
    版」。要回答后者，得比较具体的依赖边，而不是整体指纹。
  - **差异的粒度是否够**：现在只比「有哪些点、排第几天、估时多少」。计划内容
    文字变了不算差异——如果将来计划带「学习建议」文本，这个口径要重新审。
- **哪些观点不适用于当前项目？**
  - **事件重放与完整事件溯源**：本项目的计划规模小，重放收益为负。
  - **分布式版本号分配**（向量时钟、Lamport 时钟）：本项目是单写者场景，领域
    内分配的序号足够。
  - **乐观并发控制与版本冲突合并**：仓储层未定，且当前是单人教练场景。

## 5. Engineering Practice

- **实现了什么？**
  - **`core/learning/versions.py`**（新增）：
    - `PlanVersion`（实体）：`id`、`plan_id`、`number`、`plan`（内容快照）、
      `basis`、`reason`、`at`、`delta`。
    - `PlanBasis`（值对象）：目标、学习者、课程、目标要求的点、**生成时已学会的
      点**、参考的诊断、**课程结构指纹**。
    - `PlanDelta`（值对象）：`added` / `removed` / `changed` + `is_empty`。
    - `start_plan(...)`——全新计划（版本 1，新计划线）。
    - `revise_plan(versions, ...)`——修订（版本号 +1，算出差异）。
    - `plan_versions(versions, plan_id=..., goal_id=...)`——查询。
    - `current_plan_version(versions, plan_id=... / goal_id=...)`——当前版本。
    - `fingerprint_structure(structure)`——课程结构指纹。
  - **`core/learning/domain.py`**：新增 `PlanId`（计划线）与 `PlanVersionId`（版
    本）两类标识。
  - **`tests/test_learning_plan_versioning.py`**（新增）：25 个用例（集成路径：
    目标 → 诊断 → 计划 → 修订 → 查询）。
  - **`examples/learning_plan_versioning.py`**（新增）：五段演示。
- **为什么这样设计？**
  - **`PlanId` 区分修订与全新计划**：少了它，「重新规划」既像新版本又像新计划
    ——无法判定的区分等于没有区分。
  - **目标不充当计划线**：同一目标可以先后有两条线（换了一条学习路径）。
  - **排序按版本号，不按时间**：时间由调用方传入，可能补录、乱序；让它决定顺
    序，「谁是当前版本」就变成了猜。
  - **跨线用「最近开始的那条」**：用旧线的版本往往更多，也常常最近被改过。
  - **依据记输入，不记输出**：输出已在版本里；依据的价值是「当时已经会了什么」。
  - **差异只比排程，不比措辞**：标题与理由是解释不是排程。
  - **首版没有差异**：没有上一版，就不存在差异。
  - **只给领域侧的纯函数，不做 HTTP**：API 框架 TBD、仓储层未实现——在两处都
    未定的时候搭 HTTP 接口，等于把未定的选择固化进代码。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 用目标 id 当计划线 | 换学习路径无法表达；目标不能同时有两条线 |
  | 只有版本号没有计划线 | 「修订」与「全新计划」分不开 |
  | 排序按时间戳 | 补录或乱序时「当前版本」变成猜 |
  | 当前线取「版本最多的」 | 用旧了的线版本往往更多，会选错 |
  | 当前线取「最近改过的」 | 同样会选错旧线 |
  | 事件溯源（只存变更） | 计划规模小，重放收益为负；复杂度显著上升 |
  | 版本只存内容，不存依据与差异 | 「为什么变了」「基于什么生成」永远答不上来 |
  | 差异包含标题与理由 | 每次措辞微调都算「有变化」，差异失去信息量 |
  | 按内容哈希做版本 id | 显式 id 在存储落地前就能表达「引用某个版本」 |
  | 现在就搭 HTTP API | API 框架 TBD、仓储层未定；等于提前固化两处未定的选择 |
  | 给计划内容加状态机 | 计划是派生的；状态属于进度（ADR-0018） |
- **测试结果如何？**
  - `tests/test_learning_plan_versioning.py`：25 个用例（首版无差异、修订版本号
    +1、全新计划版本号从 1 开始、修订要求同一条线、修订要求已有版本、版本号重复
    被拒、依据记录输入/进度快照/结构指纹、指纹随结构变且稳定、差异记录移除与重
    排、无变化时差异为空、按版本号排序、时间乱序时版本号仍然说了算、按计划线与
    目标过滤、当前版本是线内最后一个、当前计划线是最近开始的那条、无匹配时为
    None、理由必填、版本号为正、首版不能带差异、别人的进度被拒）。
  - 全量：**800 passed**；`ruff` / `mypy` 全绿；二十一个示例跑通。
  - `examples/learning_plan_versioning.py`：plan-1 v1 → v2（差异移除 k1）→ plan-2
    v1（新计划线）；依据含目标、要求、已学会、结构指纹；查询按线分组、组内按版本
    号；当前版本 = plan-2 v1。
- **实践结果是否支持阅读材料中的观点？**
  支持三条：**序号优先于时间**（版本号说了算，时间只用来跨线比）；**差异比最终
  态更有审阅价值**（`PlanDelta` 让「计划为什么变了」有答案）；**过程要留痕**
  （依据 + 差异 + 理由三件套）。
  **不支持**「事件溯源是版本化的默认答案」——本项目的计划规模让重放收益为负，
  快照 + 依据 + 差异更划算。这条被写进 ADR 的后果项。

## 6. Reflection

1. **今天最重要的知识是什么？**
   **无法判定的区分等于没有区分。** 「重新规划」有两种含义——进度推进导致的重新
   生成，和换了一条学习路径。少了 `PlanId` 这层区分，两者在数据里长得一样，事后
   谁也说不清。**先把两种含义分开，再谈查询**：如果区分本身是模糊的，查询做得
   再精巧也只是在猜。
2. **哪个观点改变或修正了原来的理解？**
   原以为「当前版本」就是「时间最新的那个」。实际上要分两种情况：同一计划线内
   按**版本号**（时间会补录、会乱序，序号不会），跨计划线才用**时间**（跨线没
   有共同序号）。而且跨线要选的是「**最近开始**的那条」，不是「最近改过」或
   「版本最多」的那条——用旧了的线往往版本更多、也常常最近被改过。
3. **当前实现还有哪些局限？**
   版本集合没有聚合根，「版本号不能跳号」没人检查；结构指纹只能回答「结构变没
   变」，不能回答「变得影不影响这一版」；计划线没有清理策略；差异只比排程，比不
   了计划的说明文字；仓储层与 HTTP 接口都还没做；理由由调用方给，领域层只校验
   它非空。
