## 1. Engineering Question

诊断 → 进度 → 计划这条链谁来串？两份事实不一致时，应用层选哪一边？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **领域层回答「什么是真的」，应用层回答「现在做什么」。** 领域层的每个函数都
    是纯函数、都不做取舍；把它们串成一次业务动作，是应用层的职责。
  - **不一致要被显式处理，不能被默认吞掉。** 诊断说「会」、进度说「没学会」——
    这种矛盾必须有一个明确的处置规则，否则它会在某个分支里悄悄决定结果。
  - **一次事务只改一个聚合。** 跨聚合的写要么拆成多次，要么显式承认它不是原子的。

## 3. Cross References

| 来源 | 核心观点 | 与主教材的关系 |
|---|---|---|
| ADR-0015 | 「一次事务只改一个聚合」 | 应用服务的写边界：一次用例可能触发多次「单聚合写」 |
| ADR-0020 | 「判定与进度之间需要应用层显式衔接。自动同步会跨聚合写」 | 本主题的第一职责：把这条衔接实现出来，并写清不一致时怎么办 |
| ADR-0024 | 「计划与诊断可能不同步……领域层不选边」 | 计划生成的输入来自进度与诊断，两者的矛盾由本主题消化 |
| ADR-0017 第三档 | 「依赖外部事实的判断属于应用层」（是否过期、是否已掌握、是否真的达成） | 用例服务是这些判断的落点 |

## 4. Compare and Challenge

- 不同资料有哪些一致观点？
  - 用例编排属于应用层；领域层保持纯粹；跨聚合写要显式。
- 哪些观点存在分歧？
  - **诊断与进度不一致时，是信诊断还是信进度。** 两种都说得通：诊断是**更新的
    证据**，进度是**系统的事实**。本项目倾向**信进度**（它是系统自己维护的状态，
    不会被一次失败的评估写坏），并把矛盾**报告**出来——但这条要在本主题里用反例
    检验一遍，而不是拍脑袋。
  - **用例是一个大函数还是一堆小函数。** 大函数容易看出全链，小函数容易测。本
    项目倾向「一个用例一个函数，内部调用领域服务」，与 ADR-0015 的「一次事务只
    改一个聚合」对齐。
- 分歧来自应用场景、设计目标还是技术演进？
  - 主要来自**设计目标**（两份事实各自的权威性）。
- 哪些结论缺少充分证据？
  - **不一致发生的频率与影响**：没有真实数据，无法判断该把它当异常还是常态。
  - **多份诊断如何取舍**（初诊 vs 复诊）：Phase 1 没有「复诊」的产品定义。
- 哪些观点不适用于当前项目？
  - **分布式事务 / saga**：单人教练、单进程起步。
  - **事件驱动的最终一致性**：本项目是同步链路。

## 5. Engineering Practice

- 实现了什么？
  - 用例服务：诊断 → 同步进度 → 生成/修订计划 → 落库
  - 诊断与进度不一致时的处置规则（选边 + 报告）
  - 多份诊断的取舍规则
  - 一次事务只改一个聚合的写边界
- 为什么这样设计？
  - **领域层不选边**：ADR-0020/0024 已经把选边推给应用层；不选边是对的——领域
    层没有「此刻哪个更真」的判断依据。
  - **矛盾要报告**：静默吞掉的矛盾会在展示层变成一个看起来正常的结果。
  - **用例粒度对齐业务动作**：一个用例 = 一次业务动作 = 若干次单聚合写。
- 有哪些替代方案？
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 领域层自动同步诊断到进度 | 跨聚合写，破坏「一次事务只改一个聚合」（ADR-0015） |
  | 应用层忽略矛盾，取交集 | 矛盾被吞，报告显示得像是正常的 |
  | 应用层以诊断为准覆盖进度 | 一次失败的评估会抹掉真实掌握状态 |
  | 一个巨大的 use-case 服务类 | 边界不清，难测；与本项目的纯函数风格不符 |
  | 每个领域服务各配一个用例 | 用例的顺序约束散落在多处，容易被绕过 |
