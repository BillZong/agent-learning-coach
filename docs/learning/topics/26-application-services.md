# Topic: Application Services

> Day 26 ｜ Phase 1.5 · Foundation Remediation ｜ 主教材：—（本阶段无主教材章节） ｜ 外部参考：应用层与领域层的边界（DDD，Evans）、事务边界与「一次事务一个聚合」（Richardson 等人《Patterns of Enterprise Application Architecture》）、幂等与重试（Kleppmann《DDIA》）、乐观并发控制、工作流编排与 Saga ｜ 状态：已完成

## 1. Engineering Question

诊断 → 进度 → 计划这条链谁来串？两份事实不一致时，应用层选哪一边？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **领域层回答「什么是真的」，应用层回答「现在做什么」。** 编排（顺序、次数、
    冲突）是应用层的职责，不是领域逻辑的延伸。
  - **一次事务一个聚合**，但**一个用例可以涉及多个聚合**——只要它是多次独立的写。
    把这两件事混为一谈，要么跨聚合写破坏一致性，要么用例被拆得无法使用。
  - **不一致要被显式处置**，而且处置方案受**领域模型的约束**——不是「选一个更可信
    的」，是「选模型允许的」。
  - **幂等是重试的前提**。写顺序能设计成幂等，就能安全重试；不能，重试就是放大
    故障。
  - **半更新状态要显式承认**，不能假装有事务。

## 3. Cross References

| 来源 | 核心观点 | 与主教材的关系 |
|---|---|---|
| DDD（Evans） | 应用层负责用例编排，领域层不含用例逻辑与基础设施 | 支撑「`core/application/` 独立成层」与「应用层不发明业务规则」 |

| 乐观并发控制 | 冲突不是错误而是事实；处理方式是重新读取并重试 | 直接支撑 `ConflictError` 的定位：存储层发现，应用层解决 |

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  编排属于应用层；跨聚合的写要么拆开要么补偿；冲突要显式；重试要幂等。
- **哪些观点存在分歧？**
  - **矛盾时该信谁。** 一般讨论会说「信更可信的证据」（更近的、更严格的）。本
    项目**没有这个选择**——领域模型不提供「已学会 → 未开始」这条迁移，所以「信诊
    断」在代码里根本写不出来。分歧来自**约束不同**：不是策略不同，是可行域不同。
  - **要不要补偿。** Saga 的做法是给每一步配一个补偿动作。本项目这条链只有「写进
    度」「写计划」两步，没有需要补偿的业务语义（进度写进去是**真的**学过了，不该
    撤销）。分歧来自**步骤的性质**：补偿适合「下单」这类需要撤销的动作，不适合
    「记录学习」。
  - **用例该是一个大函数还是一堆小函数。** 大函数看得出全链，小函数好测。本项
    目折中：一个 `LearningWorkflow` 类（用例）+ 若干纯函数（`sync_diagnosis`），
    顺序在类里、规则在函数里。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**可行域**（领域模型允许什么）与**步骤性质**（能不能撤销）。
- **哪些结论缺少充分证据？**
  - **多诊断并发时的合并**：冲突重试是「以最新进度为基准重新同步」，不是「合并两
    份进度」。两次同步基于不同诊断时，先到的那次会被覆盖。没有并发场景的实证。
  - **半更新状态的检测**：目前只能靠重跑，没有机制能自动发现「进度写了、计划没
    写」。
  - **应用层会不会长成第二个领域层**：目前它只做编排，但「什么时候该重规划」这类
    规则迟早会想进应用层。没有机制能挡住。
- **哪些观点不适用于当前项目？**
  - **分布式事务 / 两阶段提交**：单人教练、单库。
  - **完整的工作流引擎**：两步的链条用不着引擎。
  - **事件溯源式的流程追溯**：计划版本已经留了差异与依据。

## 5. Engineering Practice

- **实现了什么？**
  - **`core/application/workflow.py`**（新增）：
    - `sync_diagnosis(diagnosis, progress, *, at)`——**纯函数**：把诊断判定同步进
      进度，返回新进度与同步报告。
    - `SyncReport` / `ProgressConflict`（值对象）：同步结果与矛盾记录。
    - `LearningWorkflow`：用例编排器。三个用例——
      `diagnose_and_plan`（诊断 → 进度 → 计划 → 落库）、
      `record_learning`（学完 → 进度 → 重规划）、
      `current_unit`（当前该学哪个单元，Phase 2 的 Tutor 用）。
    - `WorkflowError` / `NotFoundError`。
  - **`core/application/__init__.py`**（新增）：公开符号导出。
  - **`Diagnosis.at`**（模型变更）：诊断是「一次活动」，活动要有时间——否则「多份
    诊断取哪一份」只能靠标识字典序。7 处构造点同步更新。
  - **`PlanVersionRepository.list_for_goal`**：新增——「当前计划线是哪一条」要靠
    它回答。
  - **`tests/test_application_workflow.py`**（新增）：19 个用例（用例级集成测试）。
  - **`examples/application_workflow.py`**（新增）：四段演示。
- **为什么这样设计？**
  - **先写进度，后写计划**：计划是从进度算出来的；反过来写会写出一份「依据是假的」
    计划。这个顺序还让重试幂等（已学会的点不会重复迁移）。
  - **矛盾：保留进度 + 报告**：不是「信诊断」——领域模型没有那条迁移边（ADR-0018），
    **信诊断在代码里写不出来**。
  - **取最新诊断**：诊断是活动，活动有时间；给了 id 就用 id（调用方说了算）。
  - **内容没变就不写进度**：避免无谓的版本递增；计划则每次都出新版本（变了没有要
    从差异里看得见）。
  - **冲突重读重算再写**：不是盲目重试同一次计算。
  - **写边界是两次独立聚合写**：不是跨聚合事务；半更新状态显式承认。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 领域层自动同步诊断到进度 | 跨聚合写（ADR-0015）；ADR-0020 已把衔接定为应用层的事 |
  | 矛盾时信诊断 | 领域模型没有「已学会 → 未开始」这条边——**写不出来** |
  | 矛盾时抛异常中止 | 进度是事实、诊断是一次测量；停下来不如带着矛盾继续并报告 |
  | 矛盾时静默按进度处理 | 矛盾就永远没人知道——「为什么跳过这个知识点」查不出来 |
  | 多份诊断按标识排序 | 标识字典序不是时间 |
  | 多份诊断合并（逐点取最新） | 需要逐点比较两份诊断；当前场景（同一目标的一次诊断）用不上 |
  | 计划与进度放一个事务 | 跨聚合事务（ADR-0015），且破坏「一次事务一个聚合」 |
  | 先写计划后写进度 | 会写出一份「依据是假的」计划（进度还没落库） |
  | 冲突时盲目重试同一次计算 | 写的还是基于旧版本的结果——冲突会一直存在 |
  | 给每个写步骤配补偿动作（Saga） | 「记录学习过」不需要撤销——补偿用在这里是反模式 |
  | 一个巨大的用例类 | 边界不清、难测；本项目拆成「类管顺序、纯函数管规则」 |
  | 计划每次都出新版本 | 空版本是噪音——`delta` 已经回答了「变了没有」 |
  | 现在就加「来源版本」字段 | `revise_plan` 的基线恒等于 number-1，字段冗余；等回滚 / 并发合并出现时再加 |
- **测试结果如何？**
  - `tests/test_application_workflow.py`：19 个用例（全链跑通；计划排除已判定掌握
    的点；目标/课程/诊断不存在时报清楚；同步 known → 判为已学会且来源 assessed；
    gap → 不动；矛盾 → 保留进度并报告且**不阻断规划**；多诊断取最新；给了 id 用 id；
    跑两次幂等——第二次不改进度但出新版计划；已有计划线是**修订**不是重开；学完
    一个点 → 进度更新 + 重规划；重复完成被领域层拒；当前单元；无计划时为 None；
    **先写进度后写计划**（记录写入顺序）；**乐观锁冲突 → 重读重算再写**）。
  - 全量：**849 passed**；`ruff` / `mypy` 全绿；二十三个示例跑通。
- **实践结果是否支持阅读材料中的观点？**
  支持三条：**编排属于应用层**；**跨聚合的写要拆开并承认半更新**；**冲突要显式
  处理且重试要幂等**。
  **修正**一条：本来以为「矛盾时信谁」是一个可以讨论的策略问题。实现时发现——领域
  模型**已经把可行域划好了**：没有「已学会 → 未开始」这条边，「信诊断」就**不是
  一个可选项**。约束先行，策略就无从谈起。

## 6. Reflection

1. **今天最重要的知识是什么？**
   **很多「策略选择」其实是可行域问题。** 原本以为「诊断与进度冲突时信谁」是一条
   可以讨论、可以权衡的策略；实现时才发现迁移表里**根本没有**「已学会 → 未开始」
   这条边（ADR-0018 刻意去掉），所以「信诊断」在代码里**写不出来**。领域模型先划
   出了边界，应用层只能在边界内选。**先问「模型允许什么」，再问「我该选什么」。**
2. **哪个观点改变或修正了原来的理解？**
   原以为「一次事务只改一个聚合」意味着「一个用例只能改一个聚合」。实现后明白它的
   真实含义是「**不要在一个事务里改两个聚合**」——一个用例完全可以涉及多个聚合，
   只要它是多次独立的写。否则「诊断 → 进度 → 计划」这条链根本没法存在。
   另一处修正：**半更新状态不该被藏起来**。它不是 bug，是「两次独立写」的必然产
   物；能做的只有让重试幂等，并让调用方知道可能只做了一半。
3. **当前实现还有哪些局限？**
   半更新状态没有自动检测机制；多诊断并发时的合并策略缺失（重试会覆盖先到的那
   次）；证据没有时间戳（「学习者什么时候答的」答不上来）；应用层有长成「第二个领域
   层」的风险；用例只覆盖了「诊断 → 进度 → 计划」这一条链，Phase 2 的教学、练习、
   评估都还没有用例；**计划版本不记录「基于哪一版」**——当前冗余（基线恒等于
   number-1），等回滚或并发合并出现时再迭代。
