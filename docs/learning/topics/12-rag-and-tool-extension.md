# Topic: RAG 与 Tool Extension

> Day 12 ｜ Phase 0 · Agent Engineering Foundation ｜ 主教材：Ch5：5.4～5.5 ｜ 外部参考：MCP Resources / Tools ｜ 状态：已完成

## 1. Engineering Question

Citation 如何绑定到具体检索片段？Tool Callback 如何与 HITL 审批组合，而不破坏事务语义？

## 2. Primary Reading

- Book: Ch5：5.4～5.5
- Chapter / Section: Ch5 5.4～5.5
- 核心观点：
  - **5.4 结构化检索**：按文件系统的结构取内容——`unzip_file` 解压、`list_files`
    看目录、`read_file` 读文件。与向量检索**互补而非替代**：结构化检索回答
    「这份材料里有什么」，语义检索回答「哪些内容与问题相关」。
  - **5.5.1 工具回调的动机**：把「执行前要做什么」「执行后要做什么」从工具
    本身里拿出来，成为可组合的横切关注点。教材给出 `before_tool_callbacks`
    与 `after_tool_callbacks` 两个列表。
  - **5.5.2 回调的两种用法**：执行前的回调返回结果就**短路**工具执行；执行后
    的回调返回结果就**替换**工具结果。返回值是 `None` 表示「不干预」。
  - **5.5.3 人工审批**：教材用**执行前的回调** + `input()` 实现审批——返回
    `None` 放行，返回一句话表示拒绝。
  - **5.5.4 压缩检索结果**：用**执行后的回调**把过长的检索结果重新切分、重新
    检索，只留最相关的几段。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  全部一致认为：**检索质量决定 RAG 的上限**，且必须**分层评估**（召回与生成分
  开看）。教材的压缩回调、综述的检索后处理、工程指南的混合检索，方向一致。
- **哪些观点存在分歧？**
  - **审批该做在哪一层**：教材放在**工具回调**里（阻塞式 `input()`）；本项目放在
    **运行时**里（暂停—恢复，可持久化）。
  - **工具回调该放在哪一层**：教材挂在 **Agent** 上（`before_tool_callbacks` 是
    Agent 的构造参数）；本项目挂在 **Dispatcher** 上。
- **分歧来自应用场景、设计目标还是技术演进？**
  - 审批的分歧来自**设计目标**：教材要的是「演示」，本项目要的是「可持久化、
    可恢复、可审计」。一次阻塞在 `input()` 上的审批没法存进会话快照——进程
    重启后，人还没来得及按回车，状态就丢了。
  - 回调的分歧来自**架构原则**：教材的 Agent 直接持有工具列表，回调自然挂在
    Agent 上；本项目有独立的 Dispatcher 作为唯一执行边界，回调挂在那里才能
    覆盖**所有**工具来源（本地、MCP、结构化输出）。
- **哪些结论缺少充分证据？**
  - 「压缩检索结果能提升回答质量」缺少对照实验——本项目的压缩钩子只验证了
    **它按相关度截断且不破坏引用**，没有验证它让回答变好了。
  - 「5.4 的结构化检索比向量检索更适合教材场景」也是断言：教材是结构化 Markdown，
    但**结构化检索的召回率**取决于切分质量，本项目没有做这个对比实验。
- **哪些观点不适用于当前项目？**
  - 教材 5.4 的**文件系统工具**（解压、读图片/音频）不适用于当前阶段——教材材料
    是 Markdown，PDF 与富格式留给 Day 25。
  - 教材 5.5.3 的阻塞式审批**不适用**：与本项目的暂停—恢复并存会产生**两套
    审批**，拒绝路径可能被绕过（回调先短路，运行时根本没机会看到这次调用）。

## 5. Engineering Practice

- **实现了什么？**
  - `core/tools/`：**工具回调机制**——`before_hooks` / `after_hooks` 挂在
    Dispatcher 上；执行前可短路、执行后可替换结果；`ToolOutcome` 直通（工具
    可以直接返回归一化结果：文本给模型、结构给程序）。
  - `core/agent/hooks.py`：`StateCollector`——把工具产出的结构化数据收进执行
    执行上下文的草稿本。通用机制，不认识具体格式。
  - `core/rag/citation.py`：`Citation` / `CitationSet` / `CitationRegistry` /
    `CitationValidator`——引用绑定到切片、标记稳定、可校验。
  - `core/rag/tools.py`：`SearchCourseMaterialTool`（语义检索）与
    `RetrieveKnowledgeTool`（结构化检索）。
  - `core/rag/ingestion.py`：`ingest_directory`——目录 → 向量库，幂等。
  - `core/rag/evaluation.py`：`RetrievalCase` / `RetrievalMetrics` /
    `evaluate_retrieval`——命中率@k、MRR，**按类别分组**。
  - `core/rag/callbacks.py`：`RetrievalCache`（执行前短路）与
    `SearchResultCompressor`（执行后按相关度截断）。
  - `core/rag/store.py`：协议加 `fetch(source)` 与 `sources()`——结构化检索的
    底座。
  - 数据集：`tests/data/materials/`（8 份材料）+ `tests/data/retrieval_cases.json`
    （12 条用例，分词面/语义/干扰三类）。
  - 演示：`examples/rag_citation_agent.py`（摄取 → 检索 → 引用 → 校验闭环）。
- **pgvector 检索**
  - `fetch` 用 `source ILIKE %s` 下推到 SQL——过滤在数据库里做，不在应用层。
  - **来源片段来自用户输入，因此 `%` 与 `_` 必须转义**，否则「100%」会被当成
    「以 100 开头」的模式。
  - `sources()` 用 `SELECT DISTINCT source`。
- **Citation**
  - 绑定到**切片**（`chunk_id` + `source` + `index` + 原文）。太粗读者无法核对，
    太细切片粒度不支持。
  - **标记按切片分配且稳定**：先到先得，同一切片永远同一标记。模型复制 `[1]`
    可靠，复制 `[1a2b3c]` 不可靠——所以用小整数。
  - 三类校验：`unknown_marker`（编造，**错误**）、`unsupported`（不支撑，警告）、
    `missing`（无引用，警告）。**编造比没有引用更严重**：没有引用只是「没有依据」，
    编造引用是「假装有依据」。
- **Tool Callback**
  - 执行顺序：权限检查 → 参数校验 → 执行前钩子 → 工具 → 执行后钩子。
  - **权限检查在钩子之前**：钩子不能绕过权限。
  - **事务语义**：四种回调路径下都是「一条 tool_call 恰好一条 tool_result」。
  - 执行后的钩子失败**不丢弃工具的结果**（工具已经跑完了），错误记进
    `outcome.metadata["callback_errors"]`——代价是转录里看不到，应用层要主动查。
- **HITL 集成**
  - 审批**在回调之前**：被拒绝的调用不触发任何回调；回调无法放行未获批准的调用；
    批准时修改过的参数会经过回调与校验。
  - **只保留一套审批**（运行时的暂停—恢复）。教材式的阻塞回调不采用——两套并存
    会让拒绝路径被绕过。
- **为什么这样设计？**
  - 回调挂 Dispatcher：它是唯一的执行边界，挂在那里才能覆盖所有工具来源。
  - 引用进草稿本：模型看不到、随会话持久化、按执行隔离（钩子调用时取执行
    上下文，不是构造时绑定）。
  - 评估按类别分组：词面用例是流水线基线，语义用例暴露嵌入模型的能力边界，
    **两者的差值就是「换嵌入模型值不值」的判据**。
- **有哪些替代方案？**
  | 方案 | 为什么没选 |
  |---|---|
  | 教材式阻塞审批回调（`input()`） | 阻塞在终端输入上，状态没法持久化，进程重启就丢；与暂停—恢复并存还会绕过拒绝路径 |
  | 引用标记用哈希（`[1a2b3c]`） | 模型复制长标记不可靠；改成小整数更稳，代价是标记只在工具实例内稳定 |
  | 引用存在工具里、应用事后收集 | 能做，但**收集时机不可控**（运行中途拿不到），且不随会话持久化 |
  | 压缩时重新检索（教材做法） | 我们的检索工具返回的已经是排好序的离散切片，重新切分没有必要；按相关度截断更简单，也不会引入额外检索 |
  | 混合检索（向量 + BM25） | 精确标识符仍是弱项，但引入 BM25 要多一个组件——**明确的缺口，不是结论**（Day 28 有了评估数据再定） |
- **测试结果如何？**
  - `tests/test_tool_callbacks.py`（14 例）、`tests/test_citation.py`（13 例）、
    `tests/test_rag_tools.py`（21 例）；全量 **530 passed**，ruff / mypy 全绿。
  - 关键行为都被测试守着：回调的四种路径各自产出恰好一条结果；被拒绝的调用
    不触发钩子；钩子无法放行未获批准的调用；编造的引用被判为错误；两种检索
    工具的分工。
  - **评估数据集的实测基线**：12 条用例，hit@1 0.83 / hit@3 0.92 / MRR 0.88；
    词面类 hit@1 1.00（基线），语义类 hit@1 0.80（哈希嵌入的短板），干扰类
    hit@1 0.50。
- **实践结果是否支持阅读材料中的观点？**
  - **支持**：回调确实是可组合的横切关注点——同一个「执行后」钩子既做引用收集
    又做结果压缩，互不干扰。
  - **修正**：教材把审批放在回调里，是演示的简化。本项目的暂停—恢复更好，而且
    两者**不能并存**——这一点只有实现出来才会发现。
  - **补充**：教材没讲引用。实现时才发现「标记稳定性」比「标记唯一性」更重要，
    以及「编造的引用」必须与「没有引用」区别对待。

## 6. Reflection

1. **今天最重要的知识是什么？**
   「回调可以放哪儿」不是实现细节，是**架构问题**。放在 Agent 上（教材做法），
   回调只覆盖这个 Agent 持有的工具；放在 Dispatcher 上，覆盖所有工具来源——
   因为 Dispatcher 是唯一的执行边界。同样的道理已经在权限检查上用过一次，
   回调是第二次验证这条原则的机会。
2. **哪个观点改变或修正了原来的理解？**
   原以为「人工审批 = 一个 before 回调」。实际上**审批不该是回调**：回调是同步
   执行的一部分，阻塞在里面意味着整个运行挂起——不可持久化、不可恢复、不可
   审计。审批是**运行状态**（待确认的调用 + 人工的决定），因此它属于运行时，
   属于会话状态的一部分。
3. **当前实现还有哪些局限？**
   - **没有混合检索**：精确标识符（函数名、术语）仍是向量检索的弱项。
   - **没有重排**：top-k 直接进上下文。
   - **引用校验是词面的**：「引用是否真的支撑这个说法」要靠人或模型判断。
   - **压缩钩子没验证有效性**：只验证了它按相关度截断且不破坏引用，没验证它
     让回答变好了。
   - **缓存是进程内的单字典**：不支持并发，也不跨进程。
   - **标记在工具实例内稳定**：长期运行且不复位时标记会持续增长。
   - **没有把课程材料暴露成 MCP Resource**：只有工具，没有资源。

- Unresolved Questions:
  - 混合检索值不值得引入？**现在有数据了**：词面类 hit@1 已经 1.00，说明词面重叠
    的查询不需要 BM25；真正的缺口在「语义类」——但那要靠更好的**嵌入**，不是
    靠 BM25。要不要引入 BM25，取决于实际提问里有多少是「精确标识符」型的。

    语义检索；坏处是两套访问路径要各自维护引用标记。
