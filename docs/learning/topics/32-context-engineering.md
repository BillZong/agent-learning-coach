## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **上下文工程不是提示工程**：前者管「送哪些 token」，后者管「怎么说」。
  - **上下文是有限资源，边际收益递减**（context rot）：token 越多，模型准确回忆的
    能力越差。
  - **指导原则**：用**最小的高信号 token 集**，最大化期望结果。
  - **把提示分成若干段并用标记隔开**——分段带来的额外好处是**每段可以单独取舍**。
  - **just-in-time 检索**优于预检索：模型按需取，不把「可能相关」全塞进预算。
  - **注意力预算是共享的**：每个新 token 都在消耗它。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  上下文要当有限资源；要做取舍；系统提示要分段；工具要按需返回（token 高效）；
  compaction 与结构化笔记是长时程的基本手段。
- **哪些观点存在分歧？**
  - **取舍的单位：整段还是逐条**。通用做法是「逐条裁剪」（保住条数，牺牲完整）；
    本项目选「**先丢整段**」。分歧来自**教学场景**：半截的目标陈述会让模型照着
    半个目标教。
  - **状态要不要进上下文**。通用做法是「能塞就塞」；本项目把状态**分段且可丢**。
    分歧来自「状态是背景，不是答案」这一判断。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**应用场景**（教学 vs 通用 Agent）。
- **哪些结论缺少充分证据？**
  - **优先级顺序对不对**——「材料 > 目标 > 进度 > 画像」是推理出来的，**没有真实
    使用数据**（一个学习者都没教过）。
  - **丢掉画像是否可接受**——只是推理（画像最锦上添花），没量过。
  - **token 估算准不准**——`TokenCounter` 的估算与厂商分词有偏差，预算判定是近似的。
- **哪些观点不适用于当前项目？**
  - **子代理架构**：Phase 5 之后再说。
  - **模型侧的长上下文技巧**（位置编码插值等）：不是应用层该管的事。
  - **工具结果清理作为主要压缩手段**：本项目的检索工具本来就返回少量片段
    （`SearchResultCompressor` 已在 Day 12 交付 ✓）。

## 5. Engineering Practice

- **实现了什么？**
  - **`core/application/tutor_context.py`**（新增）：Tutor 上下文构建。
    - `TutorContextRequest`：问题 + 画像 + 目标 + 进度 + 材料（每一项都可空 ✓）；
    - `TutorSection`：段名 / 优先级 / 正文 / token 数；
    - `TutorContext`：装进去的段 + **被丢的段** + 总 token 数；
    - `TutorContextBuilder`：**按优先级丢整段**，问题永不丢。
  - **`core/rag/tools.py`**：`CitationRegistry` 改为**可注入**——上下文与检索工具共用
    一份登记簿，标记因此一致 ✓✓。
  - **`core/learning/progress.py`**：公开 `state_label()`——**状态词汇归领域层所有**
    ✓。
  - **`tests/test_tutor_context.py`**（新增）：16 个用例。
  - **`examples/tutor_context.py`**（新增）：四段演示。
  - **文档**：ADR-0034、ADR 索引、`domain.md` §4.6、Topic 32 笔记、Day 32 记录。
- **为什么这样设计？**
  - **对话历史不进上下文构建**——它是运行时的转录；这里只管**教学状态与依据** ✓；
  - **五段 + 固定优先级**——分段让每段可单独取舍（Anthropic 的建议 ✓）；优先级是
    业务判断，理由写进 ADR ✓；
  - **先丢整段**——半截的目标陈述比没有目标更糟 ✓；
  - **丢了要报告**——「为什么这次变短了」有答案 ✓；
  - **登记簿共享**——否则 Day 31 的门禁与上下文的标记对不上 ✓。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 一个大 system prompt 装全部状态 | 超预算时只能整段丢或截断——没有取舍的余地 ✗ |
  | 逐条裁剪保住条数 | 目标陈述被截半句，模型照着半个目标教 ✗ |
  | 画像与进度不进上下文 | 讲不了解学习者（水平、薄弱点）✗ |
  | 材料预检索进上下文 | 预算被「可能相关」占满（just-in-time 更省）✗ |
  | 优先级做成配置项 | 现在只有一个场景——**过早设计** ✗ |
  | 渲染层自己造状态标签 | 两处说法漂移（"已掌握" vs "已学会"）✗ |
- **测试结果如何？**
  - `tests/test_tutor_context.py`：16 个用例（问题永远在、缺什么少一段、五段齐备、
    材料标记与引用一致、目标/进度/画像的渲染、**超预算先丢画像**、丢了要报告、
    **问题永不丢**、**丢整段不截断**、不限预算不丢、角色分配、优先级顺序、
    渲染可读、**登记簿共享后标记一致**）。
  - 全量：**994 passed**（+16）；`ruff` / `mypy` 全绿；二十九个示例跑通。
- **实践结果是否支持阅读材料中的观点？**
  支持三条：**上下文是有限资源**（预算必须真的当约束 ✓）；**分段**（分段让取舍成为
  可能 ✓）；**just-in-time**（材料仍由工具在运行时取 ✓）。**修正**一条：以为「上下文
  构建 = 通用裁剪策略的组合」——**通用裁剪按时间新旧取舍，教学上下文按重要性取舍**
  ✗，两者是不同的维度 ✓。

## 6. Reflection

1. **今天最重要的知识是什么？**
   **通用裁剪与教学上下文是两种不同的取舍维度**。`core.context` 的裁剪按**时间新旧**
   （最新的留下 ✓）；教学上下文要按**重要性**（问题 > 材料 > 目标 > 进度 > 画像 ✓）。
   把两者混为一谈，会得到「丢掉了学习目标却保住了十轮闲聊」的结果 ✓。
2. **哪个观点改变或修正了原来的理解？**
   原以为「状态进上下文越多越好」；Anthropic 的 context rot 与「最小高信号集」让我
   改成「**状态也要能丢**」——而且要**按优先级丢整段**，不是截断 ✓。另一个修正：
   **ADR-0012 说的「登记簿每个工具实例一份」在上下文也要带材料时不成立**——必须
   共享，否则标记对不上 ✓。
3. **当前实现还有哪些局限？**
   优先级**没有真实使用数据**（一个学习者都没教过）；token 是估算值；丢段可能
   丢错（丢画像时也许正需要「讲简单点」）；`TutorContextBuilder` **没有接进运行时**
   （Day 33 的 Tutor 才接 ✓）；材料段与检索工具的输出格式靠约定保持一致（没有
   共享渲染函数 ✗——下一处要收敛的地方）。
