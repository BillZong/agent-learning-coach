# Topic: Direct Teaching

> Day 33 ｜ Phase 2 · AI Tutor ｜ 主教材：—（本阶段无主教材章节） ｜ 外部参考：worked example effect（Sweller & Cooper 1985）、Renkl 的 worked example 系列、expertise reversal（Kalyuga & Renkl 2010）、正误示例对比（Booth et al. 2013）、MIT Teaching + Learning Lab 的 Worked Examples 综述 ｜ 状态：已完成

## 1. Engineering Question

教学内容怎么生成？解释、示例和渐进式讲解怎么做？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **分步示范 > 让自己试错**（worked example effect）：学习同样的内容，用示范的
    耗时少近六倍、错误更少——机制是**认知负荷**（自己试错时注意力花在试错策略上）。
  - **被动阅读会抵消效果**：要让学习者**自我解释**（self-explanation）。
  - **只记表面会失效**：示例要表面不同、核心相同。
  - **不会独立做**：要**渐隐支持**（faded support）。
  - **熟练者看示范反而学得少**（expertise reversal）：支持强度要随水平变。
  - **错例 + 对比正例**比只给正例更有效。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  分步示范比试错更有效（新手）；必须让学习者主动解释；示例之间要有变化；支持要
  随熟练度递减；错例有教育价值。
- **哪些观点存在分歧？**
  - **什么时候该给示范、什么时候该给练习**。Renkl 主张「渐隐支持」的过渡；
    完全掌握论者主张尽快独立做。分歧来自**学习者的起点**（零基础 vs 已会）✓。
  - **AI tutor 能不能替代 worked example**。本项目把示范交给模型 ✓，而 worked
    example 的效果依赖**示范的质量**（精心设计的步骤 vs 模型生成的步骤）✗——
    **模型生成的示例质量没有研究支撑** ✓（这是本项目的风险，不是结论 ✓）。
- **分歧来自应用场景、设计目标还是技术演进？**
  来自**学习者起点**与**示范的来源**（人设计 vs 模型生成）✓。
- **哪些结论缺少充分证据？**
  - **模型生成的 worked example 有没有效果**——本项目**没有研究支撑**；指令只是把
    研究结论翻译成了要求 ✓。
  - **「示例带引导问题」这个指标**：量的是**形式**，不是效果 ✓——模型可以机械地加一句
    问话 ✓。
  - **渐进式支持**：本项目只落在指令里（"按水平调整"），**没有机制保证** ✓。
- **哪些观点不适用于当前项目？**
  - **人本教学流程里的编排**（谁来设计步骤、谁来批改）：本项目是模型生成 ✓。
  - **expertise reversal 的完整干预设计**：本项目只有「画像里的 level」这一个信号 ✓。

- **实现了什么？**

    - `instructions_for(mode)`：模式只决定**指令**；不认识的模式**报错** ✓；
    - `TeachingCase` / `TeachingCaseResult` / `TeachingMetrics` / `evaluate_teaching`：
      教学评估（量机制 ✓）。
  - **`evals/teaching.json`**（新增）：8 条场景用例（概念 / 关系 / 机制 / 对比 / 定位 /
    建议 / 进阶 / 代码）✓。
  - **`tests/test_teaching.py`**（新增）：17 个用例。
  - **`examples/direct_teaching.py`**（新增）：四段演示。

    Day 33 记录。
- **为什么这样设计？**
  - **教学模式只决定指令**——装配、引用、门禁三种模式共用 ✓（Day 34 只加一段指令 ✓）；
  - **结构化而不是自由文本**——下游要分别处理讲解 / 示例 / 引用 ✓；
  - **门禁查两处引用**（正文标记 + `citations` 声明）——**声明也是承诺** ✓✓；
  - **评估量机制不量质量**——质量要人评（Phase 3 ✓）。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 自由文本 + 事后解析引用 | 解析不可靠；结构化输出是厂商能力 ✓ |
  | 每种教学模式一套代码 | 装配 / 引用 / 门禁会各写一遍，迟早漂移 ✗ |
  | 门禁只查正文标记 | 模型在 `citations` 里声明不存在的标记能溜过去 ✗ |
  | 教学评估量「讲得好不好」 | 要人评与评分标准（Phase 3）；现在做是假装 ✓ |
  | 把渐进支持做成机制（按水平换模板） | 现在只有一个水平信号，过早设计 ✓ |
  | 用真实模型做教学评估 | 默认套件不能依赖外部服务；质量结论另找时机 ✓ |
- **测试结果如何？**
  - `tests/test_teaching.py`：17 个用例（指令覆盖研究要点、模式报错、渲染含讲解 /
    示例 / 引导问题 / 参考文献、指令进模型、结构化输出带回、**声明的编造引用被门禁
    拦下**、通过的答案交付、上下文可见、Mock 驱动整条链路、评估指标、示例缺引导

## 6. Reflection

1. **今天最重要的知识是什么？**
   **worked example 的价值在「步骤」与「自我解释的钩子」，不在「给个例子」**。
   一个精心设计的分步示范让学习者省下试错的认知负荷；一个随手给的例子只是多读一段
   文字。而**引导问题是那个钩子**——Hattie 的元分析说，主动研究示范时效果接近翻倍
   ✓。所以本项目把「每个示例配一个引导问题」写进了指标（**示例带问题 1.00**）✓。
2. **哪个观点改变或修正了原来的理解？**
   原以为「AI 教学习者 = 把材料讲清楚」。实际上**讲清楚不是重点，降低试错成本才是**
   ——教学的组织方式（分步、示例的变化、引导问题）比内容本身更影响学习 ✓。
   另一个修正：**门禁只查正文是个漏洞**——模型在结构化字段里声明的引用也是承诺 ✓。
3. **当前实现还有哪些局限？**
   **模型生成的示范有没有效果没有研究支撑**（指令只是把研究结论翻译成要求 ✓）；
   渐进式支持只落在指令里、没有机制保证 ✓；「示例带引导问题」量的是形式不是效果 ✓；
   教学评估集是人工合成的、模型是脚本化的——量的是管道通不通 ✓；真实模型下的表现
   没测过 ✓。
