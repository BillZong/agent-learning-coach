# Topic: Knowledge Representation

> Day 16 ｜ Phase 1 · Learning Core ｜ 主教材：—（本阶段无主教材章节） ｜ 外部参考：Knowledge Space Theory（Doignon & Falmagne）、课程知识图谱实践 ｜ 状态：已完成

## 1. Engineering Question

Knowledge Point 与 Knowledge Relation 如何建模，才能同时支撑后续的路径计算与薄弱点归因？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - 知识点不是孤立的条目：它在一张**有向图**里，边表示「必须先掌握」或「属于」。
  - **先修关系是偏序**：`a` 需要 `b` 表示 `b` 是 `a` 的前提；它传递、反对称、
    不能成环。成环的课程结构没有任何合法学习顺序。
  - **知识状态对先修封闭**：如果掌握了 `a`，就应当已经掌握 `a` 的全部先修。
    这条性质让「没掌握 `a`」可以直接推出「先检查 `a` 的先修闭包」——这正是
    薄弱点归因的第一层依据。
  - **关系与节点要分开建模**：关系是结构的事实，不是某个节点的属性；否则改一
    条边就要复制节点，且同一事实出现两份。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  先修关系是偏序（传递、反对称、无环）；知识点必须放在图里看，而不是列表里；
  掌握状态要满足「掌握了某点就掌握了它的先修」这条封闭性。
- **哪些观点存在分歧？**
  - **先修的强度**：KST 把先修定义为「所有知识状态」上的全局约束，理论上很强；
    工程实现（教材依赖图、课程 map）通常只保证「推荐顺序」与「开始前校验」，
    并不枚举全部知识状态。本项目采用后者：`requires` 只强制「不能违规开始」，
    不声称能穷举所有合法学习状态。
  - **图的作用域**：KST / ALEKS 倾向一个覆盖多门课程的**全局**知识空间；本项目
    把结构放在课程内。分歧来自**数据规模**：全局图需要跨课程去重与映射，而
    Phase 1 只有单门课的结构与证据。
  - **层级是否单父**：知识图谱实践常允许多父（一个点属于多个主题）；本项目
    限制 `part_of` 一子一父，是为了让「归到哪个主题」有唯一答案。这是**展示与
    归因口径**的选择，不是理论结论。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自应用场景与数据条件：KST 的完整形态需要大规模题库与可枚举的知识
  空间；本项目的目标只是让「顺序」与「归因」有可执行判据，因此选择小图 + 两种
  关系 + 派生查询。
- **哪些结论缺少充分证据？**
  - 「先修边是真实的教学依赖」——当前图由人写死，没有用学习数据校验过；错误
    的先修边会让补课顺序与影响范围都失去意义。
  - 「先补闭包能提升学习效果」——KST 提供了理论动机，但本项目**没有实验**：
    只验证了查询正确，没验证使用这些查询的教学收益。
  - 「`part_of` 单父足够」——没有多主题归属的真实课程数据来检验。
- **哪些观点不适用于当前项目？**
  - 知识空间的完整枚举（`2^n` 个状态）与概率掌握模型：Phase 1 没有数据，也没有
    评估场景。
  - 跨课程全局知识地图：留给 Topic 22。
  - 无向「相关知识点」推荐：没有消费者，且会让校验与去重复杂化。

## 5. Engineering Practice

- **实现了什么？**
  - `KnowledgeStructure`（值对象）：知识点集合 + 关系集合，构造时完整校验。
  - `KnowledgePoint`：`id`、`title`、`summary`；**移除了 `prerequisites`**。
  - `KnowledgeRelation`：`kind`（`requires` / `part_of`）、`source`、`target`；
    值对象、无 id、拒绝自指。
  - 派生查询：`order()`、`entry_points()`、`prerequisites_of()`、
    `prerequisite_closure()`、`dependent_closure()`、`parent_of()`、
    `children_of()`、`point()`。
  - `Course` 改为持有 `structure`，不再直接持有知识点元组。
  - 迁移：`examples/learning_domain.py`、测试与文档全部改用新 API；新增
    `examples/knowledge_structure.py`。
- **为什么这样设计？**
  - **关系外置**：改一条边不需要复制知识点，同一关系只有一份事实。
  - **两种关系分开校验**：`requires` 决定「能不能开始」，`part_of` 决定「归到
    哪个主题」。合并成一种「关联」后，顺序计算无法判断哪条边该阻塞。
  - **闭包按学习顺序返回**：调用方要的是「先补什么」，不是集合；因此结果按
    `order()` 过滤，而不是按发现顺序。
  - **不缓存顺序与闭包**：派生视图缓存会造成「关系改了、顺序没变」。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | ---- | ---- |
  | 保留 `KnowledgePoint.prerequisites` | 改关系要复制点；顺序与闭包每次重新拼图 |
  | 只做一种关系 | 顺序与层级互相污染；`part_of` 被误当成调度边 |
  | 允许 `part_of` 多父 | 「属于哪个主题」没有唯一答案 |
  | `prerequisite_closure` 返回无序集合 | 归因结果无法直接作为补课任务顺序 |
  | 把闭包 / 顺序写回结构 | 结构变成可变派生数据的缓存，一致性无法保证 |
  | 直接做全局知识图谱 | 需要跨课程去重与映射，Phase 1 没有数据与消费者 |
- **测试结果如何？**
  - `tests/test_knowledge_structure.py`：21 个用例，覆盖稳定顺序、起点、直接前置、
    两侧闭包、层级查询、空结构、未知知识点，以及全部不变量（重复 id、端点缺失、
    自指、重复关系、`requires` 成环路径、多父、`part_of` 成环、不可变与值相等）。
  - `tests/test_learning_domain.py`：14 个用例，收敛到聚合与生命周期（分类、身份、
    课程名、目标、边界映射）。
  - 全量：**629 passed**；`ruff` / `mypy` 全绿。
  - `examples/knowledge_structure.py`：顺序 `k1, t1, t2, k2, k3, k4, k5`；
    `k3` 的补课顺序 `k1 → k2`；`k1` 的影响范围 `k2, k3, k4, k5`；四类错误全部
    拒绝并给出定位信息。
- **实践结果是否支持阅读材料中的观点？**
  支持结构层结论：先修确实是偏序，闭包查询让归因有可执行的第一步；关系外置
  让图可以独立校验。**不支持效果层结论**：先修边是否正确、补课闭包是否能提高
  学习效果，都还没有证据。这与前两个主题一致：机制可验证，效果需要实验。

## 6. Reflection

1. **今天最重要的知识是什么？**
   归因不是「猜原因」，而是「按结构收缩候选集」：`prerequisite_closure()` 给出
   必须先补的点，`dependent_closure()` 给出受影响的点。结构正确是归因有意义
   的前提——先修边写错，归因只会更快地给出错误答案。
2. **哪个观点改变或修正了原来的理解？**
   原以为「前置」就是点上的一个列表字段。实际上它是**关系**，属于结构而不属于
   节点：放在节点上会让同一条边有两次表达，改一处就可能不一致；同时列表也
   无法回答传递闭包与影响范围。
3. **当前实现还有哪些局限？**
   先修边没有数据校验；`part_of` 单父是口径选择，未经真实课程检验；闭包只覆盖
   课程内；诊断策略（补到哪一层、能否跳级）尚未定义；不变量仍只在内存校验。
