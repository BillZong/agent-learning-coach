## 1. Engineering Question

当前领域模型是否已经能支撑 Phase 1 的用例？哪些不变量需要用 ADR 固化下来？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **领域模型是「策略」的地基，不是策略本身。** 聚合划的是一致性边界；
    诊断、缺口判定、复习调度这些**判断规则**住在别处。地基够用，不等于房子
    盖好了——验收标准未达标时，先分清是**模型形状**问题还是**策略缺失**问题。
  - **不变量要有出处。** 每条不变量应当能指到一条 ADR；指不到的，说明它只是
    实现的偶然，没有被有意固化。
  - **ADR 会因为前提消失而失效。** 早期 ADR 的决策常常依赖当时的前提（"选型
    未定"、"还没有第二个消费者"）。前提变了，ADR 不会自己更新——必须有人回头
    读。
  - **单聚合测试全绿 ≠ 聚合能协同。** 每个聚合各自测充分，并不能证明它们之间
    的协作成立。
  - **评审要拿代码验证，不能凭印象写总结。** 文档自洽不等于实现正确。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  聚合边界由不变量确定；跨聚合用标识引用；模型与策略分层；模型应当可脱离
  基础设施测试。
- **哪些观点存在分歧？**
  - **「评审」该产出什么。** 纯文字的评审纪要容易被当成已完成的工作。本项目
    的做法是：评审必须**留下可执行的东西**——本轮留下的是一处跨聚合校验修复、
    一个集成测试文件、一条 ADR。纯文档的评审没有约束力。
  - **「持久化边界」何时决策。** ADR-0015 以"选型未定"为由搁置仓储层；选型
    定了之后，这条 ADR 的**理由**失效了，但**决策**（不做仓储）未必失效。
    本评审的处理是分开两件事：选型（已定，记录下来）与实现形态（未定，留待
    后续）——而不是因为理由失效就推翻结论。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**技术演进**：ADR-0015 写于向量库选型之前，之后架构文档与依赖都
  变了。这类「前提漂移」是评审最容易被略过的部分。
- **哪些结论缺少充分证据？**
  - **「领域模型不是 Phase 1 的瓶颈」这个判断本身缺量化对照。** 它基于验收
    标准逐条核对，但没有测过「若换一种模型形状，诊断策略会更容易写吗」。
  - **「集成测试不会固化错误协作」无法证明。** 评审的缓解是只断言跨聚合契约，
    但契约本身也可能定错。
  - **持久化留待后续是「该做但不急」，不是「不该做」**——没有证据说明推迟的
    成本低于现在做。
- **哪些观点不适用于当前项目？**
  - **完整的战术 DDD 工具集**（事件溯源、CQRS、最终一致性）：ADR-0015 已明确
    当前不做多进程与多存储一致性。
  - **领域模型作为沟通工具的团队协作价值**：本项目当前是单人推进，收益不明显。

## 5. Engineering Practice

- **实现了什么？**
  - **ADR-0019**（新增）：评审结论——Phase 1 用例支撑情况、不变量清单（逐条
    标出 ADR 出处）、持久化边界的推进、集成测试的必要性、明确不做的事。
  - **修复跨学习者的完成度缺口**：`goal_completion` 现在同时校验**学习者**与
    **课程**一致。评审用一段验证代码暴露了这个缺口——A 的进度能算出 B 的目标
    完成度。
  - **`tests/test_learning_workflow.py`**（新增）：集成测试，9 个用例，覆盖完整
    链路（画像 → 课程 → 目标 → 诊断 → 学习 → 完成度）、一致性检查在链上真的
    被调用、三个终态路径、失败路径、进度与目标的配对边界。
  - **`examples/learning_review.py`**（新增）：四个聚合协同走一遍的可运行演示。
  - **文档**：ADR 索引、ADR-0015 补充说明、domain.md、架构 §3.3、roadmap Phase 1
    验收标准逐条标注。
- **为什么这样设计？**
  - **评审用代码验证**：跨学习者缺口是写了一段验证代码才暴露的；只读 ADR-0018
    的文字描述看不出问题——**文档自洽不等于实现正确**。
  - **补集成测试而不是重复单测**：现有测试全是单聚合的，四个聚合一起动从未被
    验证过。集成测试只断言**跨聚合契约**（一致性检查被调用、完成度算对、终态
    行为正确、配对被拒绝），不重复不变量，也不绑定实现细节。
  - **持久化只决策不实现**：领域模型昨天才定型（ADR-0018），现在造仓储会立刻
    撞上"不可变实体 + 迁移历史怎么存"这个尚未决策的形态问题。
  - **不为收口改模型形状**：验收标准的缺口逐条核对后，没有一条是模型形状问题。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 评审只写文档 | 没有约束力；下个主题还会讨论同样的问题 |
  | 评审后再加一个聚合（如「学习会话」） | 没有消费者；阶段验收缺口不在模型形状 |
  | 现在就实现仓储层 | 会立刻撞上未决策的持久化形态（不可变实体 + 迁移历史） |
  | 因为 ADR-0015 理由失效就推翻它的结论 | 结论（不做仓储）与理由（选型未定）应分开处理 |
  | 集成测试重复单聚合的不变量 | 冗余；且会随实现细节变化而频繁改动 |
  | 集成测试断言具体协作步骤 | 会把错误的协作方式固化成「期望行为」 |
  | 集成测试只断言跨聚合契约 | 覆盖面小，但不易固化错误 |
- **测试结果如何？**
  - `tests/test_learning_workflow.py`：9 个用例（完整链路与完成度、运行时交接、
    未知知识点被拒、前置封闭性被拒、三个终态、达成后拒绝再推进、跨学习者被拒、
    跨课程被拒、同课不同学习者进度互不干扰）。
  - 全量：**684 passed**；`ruff` / `mypy` 全绿；六个示例跑通。
  - `examples/learning_review.py`：画像（无进度字段）→ 课程顺序与补课闭包 →
    目标草稿→绑定→激活 → 诊断判定已有基础 → 完成度 50% → 封闭性拦截 →
    别人的进度被拒 → `GoalSpec` 交接。
- **实践结果是否支持阅读材料中的观点？**
  支持两条：**「不变量要有出处」**这条检查表立刻见效——十二条不变量逐条对上
  ADR-0015～0018，没有遗漏，也没有需要新 ADR 的。**「单聚合测试全绿 ≠ 能协同」**
  同样得到验证：补集成测试时确实发现了一个跨聚合缺口（跨学习者完成度）。
  **不支持**「评审可以纯靠阅读完成」——那个缺口是跑代码跑出来的。

## 6. Reflection

1. **今天最重要的知识是什么？**
   **评审的产出不是结论，是约束。** 「模型够用」这种结论写下来没有人会执行；
   而「补一处校验 + 加一个集成测试 + 定一条边界」会留下三个下个主题必须绕开
   或继续的东西。评审若不带可执行产物，就只是把话说完。
2. **哪个观点改变或修正了原来的理解？**
   原以为 ADR 写完就稳定了。实际上 **ADR 会因为前提消失而失效**：ADR-0015 的
   「不做仓储层」依赖「数据库选型 TBD」，而选型在向量库那条线上（ADR-0011）
   已经定了，依赖也进了 `pyproject.toml`。理由失效了，但结论未必失效——**理由
   与结论要分开评估**。这比「ADR 是永久的」更实际：评审要回头读早期 ADR 的
   前提，而不是默认它们都还成立。
3. **当前实现还有哪些局限？**
   「能够创建和管理学习领域」仍未达标（缺持久化）；持久化边界只决策不实现，
   需要有人认领；集成测试只断言跨聚合契约，协作方式本身仍可能被固化；评审的
   「模型不是瓶颈」判断没有量化对照。
