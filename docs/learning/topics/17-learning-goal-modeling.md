# Topic: Learning Goal Modeling

> Day 17 ｜ Phase 1 · Learning Core ｜ 主教材：—（本阶段无主教材章节） ｜ 外部参考：Domain-Driven Design（Evans）、状态机模式（State Machine）、SMART 目标 ｜ 状态：已完成

## 1. Engineering Question

学习目标的状态机是什么？目标约束（时间、难度、前置条件）应由领域层保证，还是由应用层保证？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **实体的状态是从历史派生的，不是存储的第二份事实。** 状态机如果同时存
    `status` 字段与迁移历史，两者迟早会说不同的话；让状态成为派生属性，不一致
    在类型上就**无法表达**。
  - **状态机要能回答「为什么变成现在这样」。** 每次迁移留下理由与时间，状态
    变化才是可审计的证据，而不是一次被覆盖的赋值。
  - **约束要能被计算，才能参与决策。** 自由文本（"每周 3 小时"）只能被渲染给
    模型看；结构化值对象（时间范围、每日投入）才能回答「还剩几天」「够不够」。
  - **「应用层的事」不是一个类别。** 需要别的聚合的**已有数据**（纯函数，领域
    服务可做）与需要**外部事实**（时钟、掌握度、证据）不是一回事——后者才必须
    上移。
  - **目标先有范围，再有知识点。** 目标是学习者提的，知识点是诊断之后才定的；
    这要求模型里有「草稿」状态。

## 3. Cross References

| 来源 | 核心观点 | 与主教材的关系 |
|---|---|---|
| Evans, *Domain-Driven Design*（聚合与不变量） | 不变量由聚合自己保证；跨聚合引用只按 id | 支持「目标自己校验聚合内自洽」；本项目把跨聚合的一致性检查做成**领域服务**而非放进聚合，避免目标持有课程 |
| 状态机模式 / UML Statechart | 状态与迁移是显式模型；终态没有出边 | 直接对应 `_TRANSITIONS` 这份数据；迁移表写成数据而不是散落的 `if`，让「哪些迁移合法」可以直接读、可以直接测 |
| SMART 目标（Specific, Measurable, Achievable, Relevant, Time-bound） | 目标要有可衡量的结果与时间边界 | 支持「至少一条可验证的学习结果」与「时间范围」进模型；但 SMART 不区分**搁置**与**放弃**，本项目拆成 `suspended` / `abandoned` |
| 时间盒学习 / 番茄工作法 | 投入时间应该与日程对齐，而不是「大概每周三小时」 | 支持把「每日投入」独立成 `DailyEffort(minutes_per_day)`，与「时间范围」分开 |

| ADR-0015 / ADR-0016 | 跨聚合只按 id 引用；关系外置；派生查询 | 本主题沿用：目标按 id 绑定知识点，不嵌入 `Course` |

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  状态要显式建模、终态不可回退、目标要可衡量且有边界、跨聚合只用标识引用。
  这些在本项目里都成立，且都能落到代码上。
- **哪些观点存在分歧？**
  - **状态该存还是该派生。** 多数状态机教程直接把 `status` 作为字段，切换时
    赋值。本项目选择派生，代价是**每次读状态都要看历史**——换来的是「状态与
    历史不一致」这个 bug 类别消失。分歧来自**审计要求**：ADR-0015 要求回答
    「什么时候、依据什么」，一旦存两份事实，两者迟早分叉。
  - **「非进行中」是一个状态还是多个。** 简单实现只有 `active` 与终态。本项目
    拆出 `suspended`（可逆）与 `expired`（期限已过）。分歧来自**后续消费者**：
    计划调整（Topic 48）与复习调度（Topic 50）需要区分「之后再捡回来」与
    「彻底结束」。
  - **引用完整性归应用层还是领域层。** ADR-0015 写的是「需要应用层或存储层
    保证」。本主题细化为三档：跨聚合一致只需另一个聚合对象，是纯函数，留在领域
    层；只有依赖时钟 / 掌握度 / 证据的判断才上移。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**设计目标**：本项目把「可审计」放在首位，因此愿意接受派生状态的
  读取成本；也因为只有单进程内存模型，跨聚合检查才能做成纯函数。一旦引入多
  存储或分布式，跨聚合检查确实要上移到应用层。
- **哪些结论缺少充分证据？**
  - **六个状态是不是过细。** `suspended` 与 `expired` 目前没有产品侧的强需求
    驱动，等 Topic 48 / 50 检验。没有证据支持「这两个状态必需」，只有「区分它们
    有信息量」。
  - **「能力要求必须指向已有结果」是否过严。** 它堵死了「诊断发现一条新结果」
    的表达路径，改成改目标本身。这是刻意的保守选择，但未经真实用例检验。
  - **每日投入用「分钟/天」而非「每周总小时」。** 便于对齐日程，但一周里有的
    天学得多、有的天不学，这个模型表达不了。没有真实学习者数据支撑这个粒度。
- **哪些观点不适用于当前项目？**
  - **状态机的持久化与版本号**：不可变实体 + 迁移历史在内存里成立，接数据库后
    历史需要独立成表并处理并发写。
  - **SMART 的「Relevant」维度**：价值判断属于应用层与模型，不进领域模型。

## 5. Engineering Practice

- **实现了什么？**
  - **`core/learning/goal.py`**（新增）：
    - 状态机：六个状态（`draft` / `active` / `suspended` / `achieved` /
      `abandoned` / `expired`），迁移表 `_TRANSITIONS` 写成**数据**。
    - **状态由迁移历史派生**：`LearningGoal` 不再有 `status` 字段。
    - `GoalTransition(source, target, reason, at)`：理由必填，时间由调用方传入
      （领域层不读时钟）。
    - 结构化约束：`TimeWindow(start, end)`、`DailyEffort(minutes_per_day)`；
      `TimeWindow.has_passed(now)` 是纯查询。
    - `CapabilityRequirement(point_id, outcome)`：按 id 绑定知识点；`outcome`
      必须出自目标的 `outcomes`（能力要求不另立结果）。
    - 绑定查询：`points_for(outcome)` / `outcomes_for(point_id)`。
    - `bind_requirements`：只在草稿阶段可改绑定；激活后改绑定属于范围变更
      （Topic 48）。
  - **`core/learning/consistency.py`**（新增）：领域服务
    `check_goal_against_course(goal, course)`，返回 `GoalIssue` 列表（不是抛
    异常——一次检查可能发现多个问题）。
  - **`core/learning/domain.py`**：移除 `LearningGoal` 与 `GoalConstraint`；
    `require_text` 提为包内共享校验。
  - **`core/learning/bridge.py`**：`GoalSpec` 契约不变；时间范围、每日投入、
    前置知识点渲染进 `constraints`；能力要求不进入 `outcomes`。
  - **迁移**：`examples/learning_domain.py`、`examples/learning_plan.py`、
    `tests/test_learning_domain.py` 全部改用新 API；新增
    `examples/learning_goal.py` 与 `tests/test_learning_goal.py`。
- **为什么这样设计？**
  - **状态派生**：让「状态与历史不一致」无法表达，而不是靠校验拦住。
  - **约束结构化**：自由文本无法校验、无法计算，只能给模型看。
  - **时间拆成范围与投入**：两者独立变化——范围决定还剩多久，投入决定每天能学
    多少。
  - **难度不建模为目标约束**：难度是知识点的属性（课程侧）；复制到目标会让同一
    知识点在不同目标下难度不同。掌握层次留给 Topic 41。
  - **能力要求不另立结果**：否则同一件事两份说法，映射给规划器会变成重复任务。
  - **保证责任三档**：按「判断需要什么数据」划分，而不是按「哪一层方便」。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | `status` 作为字段存储 | 与迁移历史各说一套；迟早分叉 |
  | 保留自由文本约束 | 无法校验、无法计算；只能渲染给模型 |
  | 目标级「难度」字段 | 把课程事实复制到目标；与 Topic 22 的跨课程身份冲突 |
  | 能力要求可另立结果 | 规划器拆出重复任务（实现中实测：3 结果 + 1 要求 = 4 任务） |
  | 一致性问题抛异常 | 一次只能报一个问题；调用方看不到全貌 |
  | 把 `Course` 传进 `LearningGoal` 方法 | 目标持有另一个聚合，破坏单向引用 |
  | 引用完整性全部交给应用层 | 「需要外部事实」与「需要别的聚合」被混为一谈 |
  | `GoalSpec` 携带知识点 | 运行时开始认识学习领域概念；契约归属 Topic 23 |
- **测试结果如何？**
  - `tests/test_learning_goal.py`：22 个用例，覆盖状态机（迁移、终态、派生状态、
    断链历史、非法迁移）、约束（时间范围、每日投入、重复要求、前置重复、结果
    归属）、绑定（双向查询、跨聚合一致性的三类问题）、边界（`GoalSpec` 映射）。
  - `tests/test_learning_domain.py`：收敛到 7 个聚合与标识用例。
  - 全量：**651 passed**；`ruff` / `mypy` 全绿。
  - `examples/learning_goal.py`：草稿 → 绑定 → 激活 → 暂停 → 恢复全链路；
    四类拒绝（终态回退、草稿暂停、无期限过期、迁移无理由）+ 激活后改绑定；
    跨聚合检查报出 `unknown_requirement_point`；`GoalSpec.constraints` 三条。
  - `examples/learning_plan.py`：迁移后仍是 3 个任务（能力要求不另立结果）。
- **实践结果是否支持阅读材料中的观点？**
  支持两条：状态机写成数据后「哪些迁移合法」确实更好读也更好测；约束结构化后
  「还剩几天」「每天能学多少」第一次变成可计算的问题。**不支持**「六状态是必需
  的」——`suspended` 与 `expired` 的价值要等 Topic 48 / 50 的消费者出现才能
  验证。这与前两个主题一致：机制可验证，效果需要实验。

## 6. Reflection

1. **今天最重要的知识是什么？**
   **「应用层的事」不是一个类别。** ADR-0015 把引用完整性判给应用层，理由是
   「内存里无法校验」——但真正的原因是**判断需要什么数据**，不是它发生在哪一层。
   跨聚合引用完整性只需要另一个聚合对象，是纯函数，可以留在领域层并脱离基础设施
   测试；真正必须上移的是「是否过期」「前置是否已掌握」「是否真的达成」——它们
   需要时钟、掌握度、证据，领域模型看不见。
2. **哪个观点改变或修正了原来的理解？**
   原以为「状态」是实体的一个字段，改一下就行。实际上只要同时存在状态与历史，
   就有两份事实；而派生让不一致**无法表达**——这比「加个校验」强一个量级。
   同理，「能力要求可以另立结果」看起来更灵活，实际制造了重复任务：灵活性换来
   的是两份说法。
3. **当前实现还有哪些局限？**
   `suspended` / `expired` 缺产品侧消费者；「每日投入」表达不了一周内的不均
   衡分配；能力要求只能指向已有结果，堵死了「诊断发现新结果」；迁移历史在实体
   里会随目标变长，接数据库后需要独立成表；不变量仍只在内存校验（ADR-0015 的
   工程债未消）。
