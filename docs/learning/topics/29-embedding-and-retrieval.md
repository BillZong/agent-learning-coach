## 1. Engineering Question

pgvector 的索引方案如何选择？检索的 top-k 与相似度阈值应该由谁决定？

## 2. Primary Reading

- Book: —（本阶段无主教材章节）
- Chapter / Section: —
- 核心观点：
  - **近似最近邻会漏。** ANN 索引用召回换速度——真正相关的切片可能检索不到。语料
    小的时候，精确扫描的召回是 100%，而近似误差不值得付。
  - **过滤要下推到存储层。** 在应用层过滤等于把全部向量拉回内存再筛——那是「索引 ≠
    检索」最常见的误用。
  - **过滤下推之后，语义问题才会暴露。** JSONB 的 `->>` 对数组取出的是数组的**文本**，
    于是「point_ids 含 k1」永远匹配不上。
  - **top-k 与阈值是业务判断**，不是检索器的默认：讲一个知识点要几份材料、低于多少分
    就不算相关，都是产品决定。

## 4. Compare and Challenge

- **不同资料有哪些一致观点？**
  过滤下推；ANN 换召回换速度；召回与排序要分开测；索引参数要按数据规模调。
- **哪些观点存在分歧？**
  - **要不要建 ANN 索引。** pgvector 文档默认推荐 HNSW；本项目的语料规模（一个学习
    者的课程库）其实**精确扫描就够**。分歧来自**规模假设**——文档面向「大规模向量
    检索」，本项目面向「一门课的材料」。
  - **过滤语义该由谁定义。** 通用向量库通常只有「等值过滤」；本项目加了「序列包含
    任一」。分歧来自**元数据形状**：学习领域的知识点关联天生是数组。
  - **阈值放存储层还是应用层。** 放应用层简单（取回后筛）但浪费带宽；放存储层省数据
    但与 ANN 索引有相互作用。本项目选存储层——与「过滤下推」一致。
- **分歧来自应用场景、设计目标还是技术演进？**
  主要来自**规模假设**与**元数据形状**。
- **哪些结论缺少充分证据？**
  - **本项目的语料到底多大。** 「几千片以内」是估计，没有真实课程库的数据。
  - **HNSW 参数（m / ef_construction / ef_search）**一个都没调过——用 pgvector 的默认值。
  - **阈值 0.3 之类的具体取值**：依赖嵌入质量，而占位的 `HashingEmbedder` 产生的分数
    分布没有意义。**换成真嵌入后阈值才可用。**
- **哪些观点不适用于当前项目？**
  - **重排、查询改写、多路召回**：ADR-0011 明确不做。
  - **分布式向量库（Milvus / Qdrant）**：pgvector 已定（架构 §5）。
  - **量化压缩（IVF 的 binary / scalar quantization）**：语料规模用不上。

## 5. Engineering Practice

- **实现了什么？**
  - **`core/rag/store.py`**：
    - 过滤语义按值的类型区分——**标量等值、序列包含任一**；内存实现与 pgvector
      同步（`metadata -> %s ?| %s`）。
    - `min_score` 阈值：内存与 SQL 都支持，**下推到存储层**。
    - 索引方案可选：`none` / `hnsw` / `ivfflat`（建表与建索引语句拆开）。
  - **`core/rag/retrieval.py`**：`VectorRetriever.retrieve` 透传 `min_score`。
  - **`core/application/retrieval.py`**（新增）：`MaterialQuery`（把「教 k1、c1 课」
    翻译成过滤条件 + **决定 top_k 与阈值**）、`MaterialSearch`。
  - **`tests/test_retrieval_filtering.py`**（新增）：13 个用例（离线）。
  - **`tests/test_pgvector_store.py`**（新增）：6 个用例——**需要
    `AGLC_TEST_DSN`，默认跳过**。
  - **`examples/material_retrieval.py`**（新增）：四段演示。
- **为什么这样设计？**
  - **过滤语义由值的类型决定**：同一个 `filters` 字典里标量与序列语义不同；知识点
    关联是数组，等值匹配永远匹配不上。
  - **top-k 与阈值由应用层决定**：它们是业务判断；存储层与检索层提供默认值，但**默认
    值不是决策**。
  - **阈值下推到 SQL**：与「过滤下推」是同一条原则。
  - **索引方案是配置项**：写死一个方案等于把部署决策塞进代码。
  - **集成测试默认跳过**：默认的测试套件不依赖数据库（离线、确定、快）。
- **有哪些替代方案？**
  | 替代方案 | 结果 |
  | -------- | ---- |
  | 过滤一律等值匹配 | 「教 k1 时检索相关材料」根本做不到——数组与标量永远不等 |
  | 把 `point_ids` 存成逗号分隔的字符串 | 等值能匹配了，但「含 k1」变成子串匹配；且与「数组」这个领域形状不合 |
  | 过滤取值语义由调用方显式声明 | 每处调用都要多写一个模式参数；且迟早有人写错 |
  | 阈值在应用层筛 | 等于把全部向量拉回内存——与「过滤下推」是同一条原则的两面 |
  | 存储层自己决定 top-k 与阈值 | 「讲一个知识点要几份材料」不是存储层的默认 |
  | 写死 HNSW | 语料小的时候 ANN 的近似误差与调参不值得 |
  | 一律不建索引 | 语料变大后顺序扫描撑不住 |
  | 只支持序列过滤不支持标量 | 「限定这门课」是最常用的过滤，不能丢 |
  | 把过滤表达式做成 richer 类型 | 现在没有取反与 all-of 的需求；先不做（ADR-0030 边界） |
- **测试结果如何？**
  - `tests/test_retrieval_filtering.py`：13 个用例（标量过滤、序列包含任一、序列不误伤
    标量元数据、多条件组合、阈值筛掉弱命中、不设阈值不筛、top-k 由调用方决定、检索
    器透传、空查询不检索、**「教 k1」翻译成过滤条件**、无约束无过滤、检索用例按翻译
    过滤、应用层决定条数）。
  - `tests/test_pgvector_store.py`：6 个用例——**在真实 PostgreSQL 18 + pgvector 上
    跑通**（建表建索引、非法索引方案被拒、标量过滤、序列过滤、阈值、过滤 + 阈值同时
    生效——**占位符顺序**是最容易错的地方）。
  - 全量：**908 passed**；`ruff` / `mypy` 全绿；二十六个示例跑通。
- **实践结果是否支持阅读材料中的观点？**
  支持三条：**过滤下推**；**ANN 换召回**；**召回与排序要分开看**。
  **修正**一条：本来以为「过滤下推」只是个性能选择。实现后才发现——**下推之后语义
  问题才暴露**：`->>` 对数组取出的是数组的**文本**，于是「point_ids 含 k1」永远匹
  配不上。**内存实现「看起来对」的等值匹配，在数据库里是错的。**

## 6. Reflection

1. **今天最重要的知识是什么？**
   **同一份语义在两层里可能不一样——而只有真跑一遍才看得见。** 内存实现的过滤是
   `metadata.get(key) == value`，看起来完全正确；但下推到 SQL 之后，`->>` 对数组取
   出来的是数组的**文本**（`["k1"]`），于是「point_ids 含 k1」永远匹配不上。**两层的
   语义不一致，而读代码看不出来**——SQL 路径必须在真实数据库上验证（占位符顺序、
   JSONB 算子、类型转换，都是读代码看不出对错的地方）。
2. **哪个观点改变或修正了原来的理解？**
   原以为「ANN 索引是检索的标配」。本项目的语料规模（一个学习者的课程库，几千片以
   内）其实**精确扫描就够**——ANN 用召回换速度，而顺序扫描的召回是 100%。但索引方案
   **仍然是配置项**：写死一个方案等于把部署决策塞进代码。另一处修正：**top-k 与阈值
   不是检索器的参数，是业务判断**——「讲一个知识点要几份材料」只有产品知道。
3. **当前实现还有哪些局限？**
   过滤没有取反与 all-of 语义；HNSW 的参数（m / ef_construction / ef_search）一个都
   没调；阈值依赖嵌入质量，而占位的哈希嵌入器产生的分数分布没有意义；语料规模的
   估计没有真实数据支撑；ANN + 过滤可能少返回，要调 `ef_search`；驱动选型仍未定
   （`psycopg` 只在本地装了来验证，没进 `pyproject`）。
