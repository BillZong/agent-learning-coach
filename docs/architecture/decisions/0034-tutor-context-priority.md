# ADR-0034: Tutor 上下文——分段、优先级与「先丢整段」的取舍

- 状态：已接受
- 日期：2026-11-27

## 背景

Day 32（Phase 2 · AI Tutor）的工程问题是：**这一轮把哪些东西送进模型？**

项目里已经有两块零件，但它们没有合起来：

- `core.context`（Day 8）：**存储与呈现分离**——完整历史留着，呈现受预算约束，
  裁剪策略可替换，结果带可观测信息（ADR-0008）；
- `core.learning`（Phase 1）：学习者画像、学习目标、学习进度——**教学状态**；
- `core.rag`（Day 29–31）：检索与引用——**教学依据**。

缺的是**中间那一层**：把这三类东西装配成「这一轮给模型看什么」，并在预算不够时
**决定丢谁**。

而这不是「把东西都塞进去」的问题——Anthropic《Effective context engineering for AI
agents》把这件事说得很清楚：**上下文是有限资源，且边际收益递减**（context rot：
token 越多，模型从上下文里准确回忆信息的能力越差）。指导原则是「**用最小的高信号
token 集，最大化期望结果**」。

## 研究

### 1. 上下文工程 ≠ 提示工程

提示工程关心「怎么说」；上下文工程关心「**这一轮把哪些 token 送进模型**」——系统
指令、工具、MCP、外部数据、消息历史，全都算。

对本项目的直接含义：**「教学状态要不要进上下文」是一个要回答的问题**，而不是
「反正有就塞进去」。

### 2. Context rot 与注意力预算

模型有有限的「注意力预算」，每个新 token 都在消耗它。因此上下文必须**当作有限
资源**对待——这与本项目「预算不是建议」的既有立场一致（ADR-0008）✓。

### 3. 提示要分段，并用标记隔开

Anthropic 建议把系统提示分成若干段（`<background_information>`、`<instructions>`、
工具指引、输出说明），用 XML 标签或 Markdown 标题隔开。

**这一条直接支撑本项目的「分段」设计** ✓——而且分段带来一个提示工程没有的好处：
**每一段可以单独被取舍** ✓。

### 4. Just-in-time 检索 vs 预检索

预检索（把可能相关的内容都放进上下文）vs **just-in-time**（模型用工具在运行时
按需取）——后者更省预算，也更准。

**本项目本来就是 just-in-time**：材料由 `search_course_material` 工具在运行时取 ✓。
那「教学状态」为什么预置？因为它是**状态**（学习者现在在哪、要朝哪走），不是
「可能相关的内容」——每次都要重新查一遍是浪费 ✓。

### 5. 长时程的三个手段

compaction（压缩）、结构化笔记、子代理——前两个本项目已有（`Compaction` 策略 ✓、
`StateCollector` 的草稿本 ✓）；子代理不做（Phase 5 之后再说）。

## 决策

### 1. 上下文 = 教学状态 + 教学依据；**对话历史不在这里**

对话历史是**运行时的转录**（`AgentRuntime` 的事）。本模块只管「教练知道的背景」。

这与「存储与呈现分离」（ADR-0008）是同一个原则的两面：**对话是存储，教学状态是
呈现** ✓。

### 2. 五段，固定优先级

| 优先级 | 段 | 为什么是这个位置 |
| ------ | -- | ---------------- |
| 0 | **question** | 丢了就没有回答对象——**永远不丢** |
| 1 | **materials** | 教学依据；Day 31 的引用指向它们 |
| 2 | **goal** | 教学要朝它走 |
| 3 | **progress** | 学习者现在在哪 |
| 4 | **profile** | 水平与偏好——最锦上添花 |

**优先级是业务判断，不是技术参数**：讲「材料里怎么写的」时材料必须留；讲通用概念
时目标可能比材料更重要。**本模块把顺序定死，理由写在这里** ✓。

### 3. 取舍：**先丢整段，再谈截断**

预算不够时，**按优先级从低到高丢整段**，而不是把每段截成半截。

**半截的目标陈述比没有目标更糟**——模型会以为学习者只有半个目标，然后照着那个
半截目标教学 ✓。

问题（优先级 0）**永远不丢**：预算再小也得有回答对象 ✓。

### 4. 丢了什么要看得见

`TutorContext.dropped` 记着被丢的段名 ✓——「为什么这次请求变短了」有答案
（与 `ContextView.dropped_items` 同一个立场 ✓）。

### 5. 登记簿可以共享：上下文的 `[1]` 与工具的 `[1]` 是同一段文字

Day 31 的支撑门禁要成立，前提是**模型引用的标记与校验器查的标记是同一个**。
因此 `CitationRegistry` 改为**可注入**：上下文构建与检索工具共用一份登记簿 ✓✓。

（此前登记簿是工具私有的——ADR-0012 记的是「每个工具实例一份」，那在「材料只由
工具产出」时成立；一旦上下文也能带材料，就必须共享 ✓。）

### 6. 角色：材料与状态用 system，问题用 user

材料与状态是「教练知道的背景」，不是学习者说的话 ✓。

## 后果

- 好处：**「这一轮给模型看什么」有了明确答案**；预算不够时的取舍是**确定的**（不是
  「看实现怎么裁」）；**丢了什么看得见**；上下文的 `[1]` 与校验器的 `[1]` 对得上 ✓。
- 代价：**优先级是硬编码的判断**——换个教学场景（备考 vs 项目驱动学习）可能要调。
  把它做成配置项是**过早设计**：现在只有一个场景（ADR-0024 的老规矩）✓。
- 代价：**段落的 token 数是估算**（用 `TokenCounter` 数，不等于厂商的分词）——预算
  判定因此是近似的 ✓。
- 风险：**丢段可能丢错**——比如预算紧张时丢了画像，而学习者正需要「讲简单点」。
  缓解：画像的优先级最低（最常被丢）✓；真正的解法是**按场景调优先级**（待有真实
  使用反馈 ✓）。
- 边界：**对话历史不进这里**（运行时的事 ✓）；**工具定义的裁剪**不在这里
  （`ContextBuilder` 的职责 ✓）；**子代理上下文**不做；**真实模型下这些段的
  有用性**没量过（现在只有结构与取舍的测试 ✓）。

## 补充说明（2026-11-27）

实现中确认的事实：

1. **领域层的词汇不归渲染层所有**。第一版的进度段自己造了一套状态标签
   （"已掌握"），而领域层写的是 "已学会"——**两处说法漂移比多写一个函数糟得多**。
   修法：领域层公开 `state_label()` ✓（补测试时才发现的：领域层的严格校验把
   「能力要求的结果必须在目标的学习结果里」这条不变量挡住了我 ✓）。
2. **测试夹具要过领域层的不变量**。写测试时连续踩到两条：能力要求的结果必须属于
   目标的学习结果；状态迁移必须给出来源、理由与时刻。**不变量在测试里比在文档里
   更硬** ✓。
3. **`PointProgress` 是状态，不是方法**——`point.state`（属性）与
   `progress.state_of(point_id)`（按 id 查）是两回事 ✓。
