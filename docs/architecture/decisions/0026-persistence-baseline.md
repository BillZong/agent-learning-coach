# ADR-0026: 持久化基线——形状、乐观锁与存储粒度

- 状态：已接受
- 日期：2026-11-26

## 背景

Day 25（Phase 1.5 · Foundation Remediation）的工程问题是：**学习领域的五个聚合
（目标、进度、诊断、计划版本、题目）怎么存？写入路径如何复用领域层的不变量？**

Phase 0–1 的验收里，「持久化」是**被推迟了三次**的一条缺口：ADR-0015 写下「将来
接数据库时，写入路径必须复用同一套校验」，ADR-0019 把它标成「该做但不急」，
ADR-0021、ADR-0025 各自留一句「持久化留给后续主题」。遗留问题台账
（`docs/product/open-issues.md` §2.1 P1-A）判定它**在后续阶段无人承接**，因此
排进 Day 25。

Phase 1 已有的相关零件：

- 五个不可变聚合：`LearningGoal`（ADR-0017）、`LearningProgress`（ADR-0018）、
  `Diagnosis`（ADR-0020/0023）、`PlanVersion`（ADR-0025）、`DiagnosticExercise`
  （ADR-0021）；外加 `Course`（聚合根）与 `Learner`；
- **状态由历史派生**：目标状态来自迁移历史，知识点学习状态也来自迁移历史；
- 跨聚合只按 id 引用（ADR-0015）；
- 技术选型：关系型数据库定为 PostgreSQL，「API 框架」仍 TBD。

ADR-0018 留下的未决问题，本主题要回答：**进度的持久化形态是整体重建还是增量
更新**（知识点多时的成本）。

## 决策

**形状、协议、实现三层分开；负载带版本；只存历史；解码重跑不变量；乐观锁规则只
写一处；进度整块存成一个 JSONB 文档。**

### 1. 三层分开，放在 `core/storage/`

| 层 | 位置 | 内容 |
| -- | ---- | ---- |
| 形状 | `core/storage/codecs.py` | 领域对象 ↔ JSON 兼容的负载字典 |
| 协议 | `core/storage/protocols.py` | 仓储端口 + `Stored` 记录 + 乐观锁规则 |
| 实现 | `core/storage/memory.py` | 进程内实现（也是测试用的实现） |

**为什么放在 `core/storage/` 而不是 `core.learning/`**：学习领域层（`core.learning`）
保持纯函数与不可变对象，不认识数据库、文件或网络。**领域层不碰存储**是 ADR-0015
的边界，存储相关的三样东西一起放在存储包里，读代码的人不必在两个目录之间跳。

**为什么端口也放在存储包里**：本项目的惯例是「按能力分包」而不是「按层分包」——
`core.llm` 里有 `LLMClient` 协议与各厂商适配器，`core.memory` 里有 `MemoryStore`
协议与它的文件实现（ADR-0010）。协议与实现同包，与之一致。

### 2. 形状放在领域模型之外

领域模型文件里**没有** `to_dict` / `from_dict`。理由与 `bridge.py` 完全一样：映射
放在外面，领域模型才干净、才能单独测试与持久化（ADR-0015）。领域对象不知道自己
被存过、也不知道自己被编码成什么。

### 3. 负载带 `schema_version`，不认识的版本明确拒绝

每个负载带 `schema_version`（当前为 1）与 `kind`（负载种类）。解码时版本或种类
对不上 → `DecodeError`，**明确拒绝**。

**为什么必须这样**：领域形状**已经变过两次**——ADR-0017 去掉了 `GoalConstraint`
与 `status` 字段，ADR-0023 去掉了 `correct` 与 `basis`。再变是必然。没有版本号，
旧负载只能靠「猜」来读；有了版本号，读不出来的负载要么被显式迁移，要么**明确
失败**，不会半懂半猜地构造出一个半对的领域对象。

约束只钉死「版本存在且是数字」，不钉死具体值——版本升级不需要改 DDL。

### 4. 只存历史，不存派生状态

目标状态由迁移历史派生（ADR-0017），知识点学习状态也由迁移历史派生
（ADR-0018）。因此负载里**只有历史**。存派生值就要同步两处，而两处会漂移。

### 5. 解码重跑领域层的不变量

`from_dict` 通过**领域对象的构造函数**构造对象，因此构造期的校验全部生效。从
存储读回一份被篡改的负载，会在**读回时**就被拒绝——例如迁移历史断链的负载会抛
`DomainError`（「目标 goal-1 的迁移历史断链：……」）。

这就是「写入路径复用领域层不变量」在**读侧**的形态：写进去的是领域对象（构造
时已校验），读出来时再校验一次。**两端都不信任外部数据**。

**领域错误与解码错误要分开**：领域错误说「这个事实不合法」（要修数据），解码错误
说「这份负载的结构不认识」（要迁移）。混在一起，调用方分不清该修数据还是该改
代码。

### 6. 乐观锁：版本号 + 一处规则

领域对象不可变，「更新」是**整体替换**（ADR-0015）。两个进程同时读-改-写同一个
目标时，后写的会把先写的覆盖掉，而且**没有人会发现**——目标的时间范围、每日投入、
绑定关系可能悄悄回退。

因此每条记录带一个 `revision`：

- `revision == 0` 表示**还没有存过**（新建）；
- 保存时携带的 `revision` 必须等于存储里当前的 `revision`，否则抛 `ConflictError`；
- 保存成功后 `revision` 加一。

**规则只写在 `ensure_writable` 一处**，内存实现与未来的 SQL 适配器共用——两份实现
各写一遍，迟早对同一次并发给出不同的答案。

**冲突不是错误，是事实**：调用方拿到冲突后要重新读、重新合并、再写，这属于应用层
的用例编排（Day 26）。存储层只负责**发现**冲突，不负责解决它。

### 7. 存储粒度：身份与外键用列，内层形状用 JSONB

| 表 | 粒度 | 说明 |
| -- | ---- | ---- |
| `learners` / `courses` | 一行一实体 | 列式 |
| `knowledge_points` / `knowledge_relations` | 一行一知识点 / 一关系 | 规范化；会被连接与索引 |
| `learning_goals` | 一行一目标 | 身份与外键列 + JSONB 负载 |
| `learning_progress` | 一行一（学习者 × 课程） | JSONB 负载 |
| `diagnoses` | 一行一诊断 | 身份与外键列 + JSONB 负载 |
| `plan_versions` | 一行一版本 | 主键 (plan_id, number) |
| `diagnostic_exercises` | 一行一题目 | JSONB 负载 |

**身份与外键用普通列，内层形状用 JSONB**：跨聚合的引用（目标属于谁、诊断针对哪个
目标）用列表达，才能建外键与索引；聚合内部的结构（迁移历史、能力要求、判定证据）
用 JSONB，领域形状变了不用改表。

**负载里也有这些值——用 CHECK 约束绑死**：`CHECK (COALESCE(payload->>'id','') = id)`
等。列与负载各说一套是最难查的一类 bug，约束让它进不来。

**进度为什么整块存**（ADR-0018 的未决问题）：

领域层的更新粒度就是**整块替换**（`LearningProgress` 不可变，`start()` / `complete()`
返回新的整体）。存储粒度若比领域粒度细（逐知识点一行），就必须在存储层引入一个
**领域层没有的 diff 机制**——那是额外的一层真相。整块存则读写都是一行，原子性天然
成立（不会读到「半个进度」），代价是每次迁移重写整块（O(N)）。

**代价实测**（`examples/learning_persistence.py`，1000 次重复取均值）：

| 知识点数 | 负载大小 | 编码 | 解码 | 一次迁移（整块重写） |
| -------- | -------- | ---- | ---- | ------------------ |
| 50 | 13.0 KB | 0.02 ms | 0.17 ms | 0.03 ms |
| 200 | 51.8 KB | 0.08 ms | 0.64 ms | 0.11 ms |
| 1000 | 258.8 KB | 0.47 ms | 4.64 ms | 0.51 ms |

**读的成本与存储形态无关**——领域对象本来就持有 N 个 `PointProgress`，重建是领域
层的事。**写的成本与形态有关**，但在 1000 个知识点时整块重写也只有 0.5 ms 量级，
远低于一次网络往返。ADR-0018 担心的「知识点很多时进度很大」在当前规模下**不构成
问题**；真到了需要拆行的规模，那时再引入 diff 机制不迟。

### 8. 一个必须知道的 PostgreSQL 行为

**CHECK 约束在表达式为 NULL 时放行**（NULL 不是 FALSE）。而 `payload ->> 'id'` 在键
缺失时返回 NULL——直接写 `CHECK (payload ->> 'id' = id)` 会让**「负载缺字段」的行全
部漏过去**。

这条是**实测出来的**：第一次应用 DDL 时，「缺 schema_version」的行被成功插入了。
修正的办法是每条 payload 检查都用 `COALESCE` 把「键缺失」变成一个确定的假值。

并已在文件头注明这条规则——**它是约束，不是偶然的写法**。
则——**它是约束，不是偶然的写法**。

### 9. 内存参考实现是**真实现**，不是假实现

`core/storage/memory.py` 存的是**负载字典**，读回时用 `from_dict` 构造领域对象。
它因此同时证明三件事：协议是可实现的；写入路径复用不变量；乐观锁是真的（两个
基于同一版本读出的记录先后写入，第二个被 `ConflictError` 挡住）。

**它让测试不需要数据库**——离线、确定、快。PostgreSQL 适配器是同一套协议的另一
个实现。

### 10. PostgreSQL 适配器本主题不交付

DDL（`migrations/0001_learning_domain.sql`）是**契约**：适配器必须与内存实现对同一
次并发给出同样的答案。但**适配器本主题不写**——驱动选型未定（`psycopg` 还是
`asyncpg`；而「API 框架」在技术选型表里也是 TBD），在没有驱动的情况下写适配器
只能写出**测不了**的代码。

**DDL 已在真实 PostgreSQL 18 上验证**：干净应用，9 张表；并逐条验证了 CHECK 约束与
外键确实会拒绝坏数据（负载缺字段、负载 id 与列不一致、外键指向不存在的实体、
版本非数字）。

## 后果

- 好处：领域层保持纯函数；存储的形状、协议、实现分开；负载的版本与不变量在读
  侧也被强制；并发覆盖被乐观锁挡住；测试离线；DDL 已是可用契约。
- 代价：**多一层间接**。要读懂「一个目标怎么存」，得看 `codecs` → `protocols` →
  `memory` 三处。
- 代价：**领域形状一变，负载版本就要 +1**，旧数据要么迁移要么读不出来。这是刻意
  的（明确失败优于半懂半猜），但**迁移工具还没做**——领域形状改过两次，两次都靠
  「还没有真实数据」侥幸过去。有真实数据之后这条路要补。
- 代价：**SQL 适配器缺席**。存储能力目前只有进程内实现。
- 风险：**列与负载的重复**（id、learner_id、course_id 两处都有）靠 CHECK 约束维持
  一致。约束写漏一条就会漂移——因此每加一张表都要同时改 DDL 与 codec。
- 风险：**进度整块存的上限未知**。实测到 1000 个知识点没问题，但真实课程规模与
  迁移频率未知。
- 边界：**题目上的 `point_id` 建不了外键**——知识点身份是课程内的（ADR-0016，主键
  是 `(course_id, id)`），而题目不记它属于哪门课；只能建索引。这是「知识点仍在课
  程内」这个决定的直接代价。
- 边界：**迁移工具**（谁按顺序执行 `migrations/`）未定；**备份与恢复**未定；
  **连接池与重试**未定。
- 边界：**Day 26 的应用层**要基于这些协议编排用例，并且必须自己处理冲突（重新
  读、重新合并、再写）。

## 补充说明（2026-11-26）

实现中确认的事实：

1. **「写路径复用不变量」必须两边都做。** 只在写的时候校验，数据库仍然是一个
   可以绕过校验的入口——任何直接写库的工具、手工修数据、迁移脚本都能写进非法
   事实。**读的时候再校验一次**，非法数据就永远出不来领域层。
2. **CHECK 约束在 NULL 时放行。** 「负载缺字段」的行全部漏过去——而且**不报错**。
   这条只有真去插一行坏数据才会发现；`COALESCE` 是修正后的写法，已写进 DDL 的
   文件头，避免后来者照抄一个「看起来对」的版本。
3. **存储粒度必须与领域粒度一致。** 领域层整体替换、存储层逐行 → 必须在存储层
   引入 diff 机制，那是领域层没有的第二份真相。整块存的代价（O(N) 写）在实测里
   并不成立为问题（1000 点时 0.5 ms）。
4. **读的成本与存储形态无关。** ADR-0018 担心的「每次读进度都要重建 200 个对象」
   是**领域层**的成本，不是存储层的——无论怎么存，领域对象都要持有 N 个
   `PointProgress`。这纠正了一个把领域成本算到存储头上的判断。
5. **乐观锁的规则必须只有一份。** 内存实现与 SQL 适配器对同一次并发必须给出同样
   的答案；规则写在 `ensure_writable` 一处，两个实现共用。
6. **端口与实现同包是本项目的惯例。** `core.llm`（协议 + 各厂商适配器）、
   `core.memory`（协议 + 文件实现）都是这样；按层分包反而会让读代码的人在两个
   目录之间跳。
