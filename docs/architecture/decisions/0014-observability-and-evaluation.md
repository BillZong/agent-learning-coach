# ADR-0014: 可观测性与评估的边界

- 状态：已接受
- 日期：2026-11-24

## 背景

Phase 0 的最后一个问题是：**如何用 Trace / Metrics 定位 Agent 的失败？阶段
验收需要哪些评估用例？**

在此之前，运行时已经把事实记得很完整：`ExecutionContext.events` 是按顺序追加
的事件，`AgentStep` 是逐步的执行记录（模型响应、工具调用、工具结果），
`ToolOutcome.duration_ms` 是工具耗时。缺的只有两件事：

1. 一个**可读的视图**——「这次运行停在哪、时间花在哪、哪个工具坏了」。
2. 一个**可重复的门禁**——「改完代码，怎么知道运行时行为没退步」。

常见的做法是引入 OpenTelemetry、起一条 trace 管道、再搭一套 LLM-as-judge
评估。这个项目先不这么做，理由写在下面。

## 决策

### 1. Trace 是投影，不是第二套事件系统

`build_trace(result)` 只读运行结果，不写任何东西。事实仍然只有一份，住在
执行上下文与执行记录里。

**为什么**：两份事实迟早对不上。一旦 trace 有了自己的缓冲区，调试时就要先
回答「以哪份为准」，而这个问题在故障现场没有答案。

**唯一的例外是一次性插桩**：模型调用耗时无法从已有事实推导，因此运行时把它
记在 `AgentStep.think_ms` 里。工具耗时则沿用 `ToolOutcome.duration_ms`。一次
运行的时间去向只有这两个来源，Trace 只做汇总。

### 2. Metrics 是有限集合的聚合，不是实时指标管道

`compute_metrics(traces)` 对一个有限集合做统计：成功率、停止原因分布、工具
失败率、步数与耗时的百分位、token 与成本。没有 exporter、没有后台线程、没有
滑动窗口。

**为什么**：Phase 0 要回答的问题是「改了之后是不是更容易失败」，这用一组
运行就能回答。实时管道要回答的是「此刻线上正在发生什么」，那是有了线上流量
之后的问题——提前建管道只会得到一个没人看的仪表盘。

### 3. 诊断只陈述证据，不给没有依据的建议

`diagnose(trace)` 的输出由三部分组成：停止原因、对应的检查方向、从 Trace 里
取出的证据（失败的工具与错误、被重复的动作与次数）。成功与 `pending_approval`
不诊断——后者不是失败，它只是还没结束。

**为什么**：诊断的价值在于「指到具体位置」。说「模型可能需要更多上下文」这种
话，和没说一样；说「`boom` 连续失败 3 次，错误是 xxx」，下一步就能验证。

### 4. 评估断言行为，不断言措辞；用脚本化模型，不用 LLM-as-judge

评估对象是**机制**：工具是否按预期被调用、工具失败是否被归一化回填、停止
原因是否符合预期、最终输出是否交付。用例由三部分组成：脚本化的模型响应、
期望的行为契约（停止原因 / 工具序列 / 失败工具 / 输出子串）、以及一个 JSON
数据集。

**为什么不用 LLM-as-judge**：判官本身不确定。用不确定的东西验证不确定的
东西，得到的结论也只能是不确定。而且判官不可回归——同一份代码两次评估可能
给出不同结论，那就不适合当门禁。

**语义质量评估不是被否决，而是被推迟**：Phase 2 有真实教学场景与人工标注
之后再做，到那时它才有可校准的锚点。

### 5. 现在不引入 OpenTelemetry 依赖

Trace / Metrics 的类型与收集逻辑已经独立于运行时，接入 OTel 时只需要加一个
导出器；但 Phase 0 没有跨进程追踪、采样、与既有 APM 对接的真实需求。

**顺序不能反过来**：先有可解释的数据，再谈导出。一个导出到 Jaeger 但字段
含义没人说得清的 trace，不比一张打印出来的表格更有用。

## 后果

**好处**

- 零依赖：不新增包，不引入必须运维的组件；Trace 可以离线从运行结果重建。
- 可回归：评估用脚本化模型，同一份数据集在同一份代码上结论固定，能进 CI。
- 边界清楚：事实（上下文）、视图（Trace）、聚合（Metrics）、判断（诊断）、
  契约（评估）各在一处，修改其中一个不会顺带改另一个。

**代价**

- 没有分布式追踪：跨服务调用、跨进程关联（如 MCP 子进程内部）看不到。
- 评估不覆盖语义质量：回答是否讲清楚、是否有教学价值，这套机制答不上来。
- 百分位在小样本上只是参考：十次以下的运行，p95 基本等于最大值。
- 工具内部的重试、缓存命中等行为不可见，除非工具把它们写进
  `ToolOutcome.metadata`。

**边界**

- 告警阈值没有内置：需要先用这组指标积累基线，再定阈值。
- 评估数据集是**代码资产**，不随 wheel 发布；`evals/` 属于仓库，不属于包。
- 新增停止原因时，`_STOP_HINTS` 必须跟着补；否则诊断会退回默认提示——这是
  一处需要人工维护的映射。
