# ADR-0020: 诊断——判定、准入条件与与进度的衔接

- 状态：已接受
- 日期：2026-11-25
- 修正：2026-11-25，§2 的 `basis` / `basis_kind` 被
  [ADR-0023](0023-diagnostic-assessment.md) 取代（改为 `evidence` 列表）；三态判定与
  准入条件不变

## 背景

Topic 20 的工程问题是：**诊断流程的输入、输出与准入条件是什么？诊断结果需要
达到何种精度，才足以驱动学习计划生成？**

这是 ADR-0019 评审留下的两条未达标项之一（「能够根据学习者背景开展初始诊断」）。
评审的结论是：缺口在**策略层**，不在模型形状。因此本主题补的是策略的第一块
——**判定与准入**。

Plan.md 的 Day 20 清单：定义 Diagnosis / 定义 Diagnostic Exercise / 定义
Diagnostic Submission / 设计诊断流程 / 编写 Domain Tests / 交付 Diagnosis Model
和 Diagnostic Workflow。

Phase 1 已有的相关零件：

- `LearningProgress`（ADR-0018）：知识点级学习状态，`assess()` 记录「诊断判定
  已有基础」（`not_started → learned`，来源 `assessed`）；
- `KnowledgeStructure`（ADR-0016）：知识点依赖与前置闭包；
- `LearningGoal`（ADR-0017）：目标要求掌握哪些知识点。

**ADR-0018 已经预留了接口**：`assess()` 的存在说明「诊断判定已有基础」这个概念
当时就想清楚了，但**谁来判定、判定什么、判定到什么程度够用**一直空着。本主题
补的就是这一块。

两个前提已经确定：

1. **领域层与运行时单向解耦**（ADR-0013、ADR-0015）。诊断题生成需要 LLM
   （Topic 21），但**判定结构与准入规则是领域知识**，不依赖模型。
2. **学习判断应基于可观察的学习证据**（架构原则 5）。

Phase 1 没有主教材章节，诊断建模由本项目自己定。

## 决策

**诊断是一次活动（实体），产出三态判定；「会」与「不会」必须带依据；准入条件
是「目标要求的每个知识点都有判定」；诊断与进度通过「判定 → 迁移」衔接，不共享
状态。**

### 1. 诊断是一次活动，不是一个状态

`Diagnosis` 是**实体**，有独立的 `DiagnosisId`。

理由：同一个目标可以诊断多次——初诊、复诊、学完一轮再测。每次都是一条**独立
的记录**，带独立的时间与依据。这与 `LearningProgress` 的分片方式不同：进度是
（学习者 × 课程）的**当前状态**，诊断是**一次次事件**。

诊断**不保存进度**。进度由 `LearningProgress` 持有。两者若都存「学习者会哪些
知识点」，就是同一事实的两份副本——本项目已经因为这个吃过三次亏（目标的自由
文本约束、关系的两种归属、已有知识的独立概念）。

### 2. 三态判定：会 / 不会 / 未判定

```python
Verdict = Literal["known", "gap", "unknown"]
```

**为什么不是二态**：二态只有「会 / 不会」，于是「不会」必须同时表示两件不同的
事——「测了，不会」与「根本没测」。这两种在计划生成上完全不同：

- 「测了，不会」= **要教的内容**；
- 「根本没测」= **不知道的内容**。

混为一谈会让计划把「没测过的点」当成「不会的点」，从而重复教已经会的东西。
所以判定是三态，`gap`（缺口）与 `unknown`（未判定）严格分开。

**「会」与「不会」必须有依据**（`DiagnosticVerdict.basis`）：一道题、一次作答，
或者无依据时的显式 `None`（例如结构性推断）。判定的 `reason` 必填。

没有依据的「会」是**不可审计的断言**——它会让计划跳过一个学习者其实不会的
知识点，而且事后查不出为什么。

依据还带**种类**（`basis_kind`）：`exercise`（做题）/ `self_report`（自述）/
`external`（外部给出）。区分种类不是为了评判证据强弱（那是应用层的策略），而是
让「会」这个断言**可追溯**——自述与做题给出的结论，置信度显然不同。

### 3. 准入条件：覆盖完整才够驱动计划生成

这是本主题的核心问题。领域层能给出的答案是：

> **目标要求的每个知识点都有判定**（会或不会），诊断结果才足以驱动计划生成。

规则落在 `LearningProgress` 之外的 `Diagnosis.has_full_coverage(goal)` 与
`DiagnosisPlan.is_sufficient`。

理由很直接：**少判一个点，计划就会漏掉它或凭空假设它**。这不是「精度够不够」
的模糊问题，而是「有没有覆盖到」的可判定问题——因此它属于领域层。

注意「会」与「不会」**不影响准入**：两者都会进入计划，区别只是「要不要教」。
准入只看**有没有判**。

**未判定的点如何处理**是应用层的决定（补诊断、还是保守地当作要教），领域层只
负责把它**标出来**（`DiagnosisPlan.undecided`），不替调用方决定。这与 ADR-0017
「领域服务只报告，不替调用方做决定」是同一条原则。

### 4. 诊断与进度的衔接：判定 → 迁移

ADR-0018 已经定义了 `assess()`，本主题补上判定这一侧：

```
诊断判定「k1 已会」
      ↓ 应用层调用
progress.assess(k1, at=..., reason="诊断 diagnosis-1：答对")
      ↓
进度迁移：not_started → learned，source_kind="assessed"
```

**衔接是应用层的动作，不是领域的自动同步。** 理由：

- 诊断与进度是两个聚合，**一次事务只改一个聚合**（ADR-0015）；
- 「哪些判定要写进进度」是策略（例如「自述的算不算」），属应用层。

因此本模块**不提供**「诊断自动同步进度」的函数——那会跨聚合写，破坏聚合边界。
应用层拿到判定后，逐条调用 `assess()`。

### 5. 诊断题与作答是值对象

`DiagnosticExercise`（题）与 `DiagnosticSubmission`（作答）都是**值对象**：

- 题：考哪个知识点、题面、题目标识；
- 作答：对应哪道题、答了什么、对不对。

**题目的生成不属于本模块**（Topic 21 Structured Generation）；本模块只定义题目
作为诊断输入的**形状**。诊断题有 `id` 而不是引用 `DiagnosticExercise` 对象，
是因为题目由外部（生成器）产生并可能独立存储。

作答**不解释「会哪个知识点」**——那是判定的职责。分开是因为「答了什么」是事实，
「会什么」是判断，两者混在一个类型里会让「谁做的判断」不可追溯。

### 6. 「会」不等于「掌握」

诊断给出的是**离散判定**。掌握程度是连续量（概率、等级），属于掌握度模型
（Topic 43）；薄弱点是**相对概念**（相对目标要求还是绝对阈值），属于 Topic 45。

本主题**刻意不做**这两件事。理由：Phase 1 没有题库、没有学习数据，做不了量化；
而把「会」当成「掌握」会让计划跳过真正需要补的内容。

## 后果

- 好处：诊断的输入（要判定哪些点）、输出（会 / 不会 / 未判定）、准入条件（覆盖
  完整）都有了确定答案，且都在领域层、可离线测试；判定带依据，「会」这个断言
  可追溯；诊断与进度不共享状态，避免双写。
- 代价：**新增第五类标识**（`DiagnosisId`）与一个聚合。Phase 1 现在有五个聚合。
- 代价：**判定与进度之间需要应用层显式衔接**。这是刻意的——自动同步会跨聚合写。
- 风险：**准入条件「覆盖完整」可能过严**。目标要求 20 个知识点时，逐个判定才能
  准入；若诊断成本高，实际流程可能需要「部分覆盖 + 保守假设」的折中。这条折中
  属于应用层策略，但领域层目前**没有**给出「部分覆盖」的口子。
- 风险：**判定质量完全取决于题目质量**。领域层只能保证「有依据」，保证不了依据
  有效——一道测不准的题会让判定失真。这是 Topic 21（题目生成）与 Topic 46
  （评估）的事。
- 边界：题目生成（Topic 21）、诊断结果到知识点的映射与降级（Topic 22）、掌握度
  量化（Topic 43）、薄弱点判定（Topic 45）、题目难度分级都未建模。

## 补充说明（2026-11-25）

实现中确认的事实：

1. **三态不是「多此一举」。** 二态实现起来更省事，但会让「没测过」混进「不会」，
   进而让计划重复教已会的内容。判定的**状态空间必须覆盖「不知道」**，否则
   「不知道」只能靠约定编码。
2. **依据必填这条规则在构造期就拦住了问题**。写测试时发现「已知」判定如果不带
   依据，系统无从追问是谁、凭什么这么判——**没有依据的断言会让「为什么跳过这个
   知识点」永远查不出来**。
3. **准入条件要落在领域层，因为它可判定**。「精度够不够」听起来是经验问题，但
   「目标要求的点有没有都被判过」是**集合覆盖问题**——前者留给实证，后者可以现在
   就实现并测试。
4. **衔接靠现有接口，不新增机制**。ADR-0018 的 `assess()` 已经预留了接口，本主题
   只需提供判定侧；`source_kind="assessed"` 让「这条迁移是诊断来的」在进度里可查。
   不需要「诊断自动同步进度」的新函数——那会跨聚合写。
5. **同一条规则在四个地方都要遵守**：`CapabilityRequirement.outcome` 必须出自
   `LearningGoal.outcomes`（ADR-0017）；本主题的示例第一次写目标时又踩了一次——
   能力要求写了目标没有的结果，直接被构造期校验拒绝。**构造期校验的价值就在
   这里：它把错误挡在了写代码的当下，而不是运行到某个分支时。**

## 补充说明（2026-11-25，Topic 21）

Topic 21 补上了本 ADR 留下的「题目从哪来」一侧。本 ADR 的判定与准入模型不变，
两处接口得到兑现：

1. **`DiagnosticExercise` 补齐三个字段**：`expected_answer`（判定要靠它）、
   `difficulty`（难度是**题目**的属性，不是知识点的——与 ADR-0017 不冲突）、
   `rationale`（让题目可被审阅）。难度取值放在领域模型里，任何来源的题目都受
   同一套约束。
2. **判定与出题严格分开**：出题由 `core.learning.generation` 完成，它**不认识**
   诊断流程——不判断「这次诊断够不够驱动计划生成」。本 ADR 的准入条件仍是唯一
   的那一个。

本 ADR §6 提到的「题目生成」已交付（ADR-0021），但「诊断结果到知识点的映射与
降级」仍未建模（Topic 22）：题目与知识点的对应在生成时已确定（每道题知道自己
考哪个点），但**判定汇总**与**映射缺失时的降级**还没有。

另外，本 ADR §5 的「依据种类」目前只有 `exercise`（做题）真正用得上；
`self_report` 与 `external` 是为后续留的位置，尚无产生它们的流程。
