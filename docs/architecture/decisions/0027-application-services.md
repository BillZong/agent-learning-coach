# ADR-0027: 应用层用例编排——顺序、冲突与写边界

- 状态：已接受
- 日期：2026-11-26
- 修正：2026-11-26，§7 幂等规则——**计划侧也不产生空版本**；§8 计划版本冲突的
  处置由「换一个版本标识」改为「明确报告基线过期」

## 背景

Day 26（Phase 1.5 · Foundation Remediation）的工程问题是：**诊断 → 进度 → 计划
这条链谁来串？两份事实不一致时，应用层选哪一边？**

Phase 1 的领域层全是**纯函数**：`assess_diagnosis` 判、`generate_plan` 排、
`start_plan` / `revise_plan` 留痕。它们不读、不写、不串联——**谁先谁后、冲突怎么
办、什么时候落库，领域层一律不决定**（ADR-0015 的边界；ADR-0020 与 ADR-0024 明
确把选边推给应用层）。

但 Phase 0–1 的验收里，「能够根据学习者背景开展初始诊断」一直只到「领域层有机制」
为止：机制齐了，**没有人把它们串起来**。遗留问题台账（`docs/product/open-issues.md`
§2.1 P1-B）判定它**在后续阶段无人承接**，因此排进 Day 26。

Phase 1 已有的相关零件：

- `assess_diagnosis`（ADR-0023）：判定 + 证据 + 降级报告；
- `LearningProgress.assess()`（ADR-0018）：诊断判定写进进度的唯一入口，迁移表
  **没有**「已学会 → 未开始」这条边；
- `generate_plan`（ADR-0024）：从目标 + 知识结构 + 进度算计划；
- `start_plan` / `revise_plan`（ADR-0025）：计划版本与差异；
- 仓储协议与乐观锁（ADR-0026）：`Stored`、`ensure_writable`、`ConflictError`。

## 决策

**应用层独立成 `core/application/`；先写进度后写计划；矛盾按领域模型允许的迁移处置
并报告；多份诊断取最新；写边界是「两次独立的聚合写」。**

### 1. 应用层是一层，不是领域层的一部分

`core/application/` 目前只有 `workflow.py`，但它是一个**独立层**：它依赖领域层与
存储层，领域层不依赖它。

应用层**不发明业务规则**：判定用领域层的结论，进度迁移用领域层的方法，计划用领域
层的生成器。它只做三件事——**决定顺序**、**决定写几次**、**决定冲突怎么办**。

### 2. 顺序：先写进度，后写计划

```
读目标与课程 → 选诊断 → 同步判定进进度 → **写进度** → 生成计划 → **写计划版本**
```

**为什么是这个顺序**：计划是从进度算出来的。反过来写（先写计划再写进度），会写
出一份**依据是假的**计划——计划声称基于某份进度，而那份进度还没落库。

这个顺序还让**重试是安全的**：进度已同步、计划没写成时，重跑一次同步是**幂等**的
（已学会的点不会重复迁移——`assess()` 只在「未开始」时生效）。

### 3. 同步的处置规则

| 诊断 | 进度 | 处置 | 矛盾 |
| ---- | ---- | ---- | ---- |
| 会 | 未开始 | 同步为「已学会」（来源 assessed） | 否 |
| 会 | 学习中 | 不动 | 否 |
| 会 | 已学会 | 不动 | 否 |
| 不会 / 未判定 | 未开始 / 学习中 | 不动 | 否 |
| 不会 / 未判定 | **已学会** | **不动** | **是** |

「诊断说会、进度说还在学」不动：学习者正在学，诊断也说会——**一致且更保守**，不
急着把它标成已学会。

### 4. 矛盾：保留进度 + 报告，不选边

最后一行的处置不是「信诊断」，而是**保留进度并把矛盾报出来**。

**理由是领域模型给的，不是偏好**：`LearningProgress` 的迁移表**刻意没有**「已学
会 → 未开始」这条边（ADR-0018：回退会让「学过没有」变得不可判定）。因此应用层
**没有「信诊断」这个选项**——领域层不提供那条迁移。

于是能做的只有两件：保留进度；**报告矛盾**（`ProgressConflict` 记下矛盾在哪、两
边各说了什么、怎么处置的）。要不要安排复习是**另一个用例**的事（复习调度属
Topic 52），应用层不自动做。

**矛盾不阻断流程**：进度是事实，诊断是一次测量。带着矛盾继续规划，并把矛盾交给
调用方，比停下来更合理。

### 5. 多份诊断：取最新的一份

**给了 `diagnosis_id` 就用它**——调用方说了算。没给则取该目标**最新**的一份，按
诊断发生的时间；时间相同则按标识（保证确定性）。

**为此给 `Diagnosis` 加了 `at` 字段**（调用方提供，领域层不读时钟，与
`GoalTransition.at`、`PlanVersion.at` 同一个约定）。这是本主题唯一的模型变更，
理由：**诊断是「一次活动」，而活动有时间**。没有时间，「多份诊断取哪一份」就只
能靠标识的字典序——那不是时间。

**负载版本仍是 1**：版本号跟踪的是**已发布**的形状，不是每次编辑。还没有真实数据
时改形状不 bump 版本；等有数据了，形状一变就是 2（ADR-0026 的迁移工具届时要补）。

### 6. 写边界：两次独立的聚合写

流程里写了两次——进度一次、计划版本一次。它们是**两次独立的聚合写**，各带各的
版本号，**不是跨聚合事务**。

ADR-0015 的「一次事务只改一个聚合」在这里的含义是「不要在一个事务里改两个聚
合」，而不是「一个用例只能改一个聚合」——后者会让「诊断 → 进度 → 计划」这条链无
法存在。

**中间失败会留下半更新状态**（进度写了、计划没写成）。这被**显式承认**而不是藏
起来：重跑是安全的（§2），而计划版本的 `basis` 记着生成它时的进度快照，事后能
看出计划是基于哪一份进度。

### 7. 幂等：内容没变就不写（进度与计划都是）

进度同步后**内容没变就不写**——避免无谓的版本递增（每写一次都要占一个版本号）。

计划侧**同样**：算出来的计划与当前版本**完全相同**时，返回当前版本、**一个字都不
写**。空版本是噪音——它不回答「计划变了没有」（``delta`` 已经回答了），只在历史里
堆出一串内容相同的记录，还让人怀疑是不是出了 bug。

比较的是**整个计划内容**（含 ``diagnosis_id``）：同一份诊断 + 同样的进度 ⇒ 相同
⇒ 不出版本；换了诊断即使结果一样也出版本，因为**依据变了**——那是有信息量的。

### 8. 乐观锁冲突：重读、重算、再写

进度写入遇到 `ConflictError` 时，**重新读一次进度、基于新读到的进度重新同步、再
写**（最多 3 次）。不是盲目重试同一次计算——那样写的还是基于旧版本的结果。

计划版本写入的冲突**不重试**，但**要说清楚**：它意味着「期间有人改动了计划，我
的基线过期了」。因此应用层把它翻成一句人话（「基线已过期——请重新读取当前计划后
重试」），而不是让底层那句含糊的「存储中的版本是 1，与携带的版本 0 不一致」直接
冒到调用方脸上。

**为什么不重试**：重试要基于**新的基线**重算，那需要先重读当前计划——这是调用方
的决策（要不要合并），不是存储层能替它做的。

### 9. Phase 2 的接口

| 接口 | 回答 |
| ---- | ---- |
| `current_unit(goal_id)` | 当前该学哪个单元（当前计划版本的第一个单元） |
| `record_learning(goal_id, point_id, ...)` | 学完一个知识点 → 进度更新 → 重新规划 |

`record_learning` 里，「学完了」蕴含「学过」：领域模型要求「开始 → 学完」两步
（没有「未开始 → 已学会」那条边——否则「学过没有」与「本来就会」分不开），因此
知识点还没开始时，用例先补上「开始学习」这一步。

## 后果

- 好处：Phase 1 的领域能力第一次**串成一条可执行的链**；矛盾有明确的处置与报告；
  多份诊断的取舍有确定规则；重试安全；Phase 2 的 Tutor 有现成的接口可用。
- 代价：**半更新状态是可能的**（进度写了、计划没写成）。缓解是幂等重跑，但调用
  方仍要知道「可能只做了一半」。
- 代价：**应用层多了一层**。读「一个目标怎么存、怎么判、怎么排」现在要跨三个包。
- 代价：**诊断的模型变了**（加 `at`），7 处构造点要跟着改；负载的形状也变了。
- 代价：**重试的合并策略是「以最新进度为基准重新同步」**，不是「合并两个进度」。
  若两次同步基于**不同的诊断**，先到的那次会被覆盖——这在单诊断场景下无所谓，
  多诊断并发时是个缺口。
- 风险：**应用层会慢慢长成「第二个领域层」**。目前它只做编排，一旦开始自己判断
  「该不该学这个点」，就会与领域层抢规则。守住的办法：应用层不出现新的业务概念。
- 风险：**计划版本与进度的一致性靠顺序保证**，不靠约束。中间失败留下的半更新状
  态，没有机制能自动发现——只能靠重跑。
- 边界：**复习调度**（矛盾之后要不要安排复习）属 Topic 52；**计划调整策略**属
  Topic 52/48；**API 与 UI** 属 Phase 5；**跨诊断的合并策略**目前没有。
- 边界：**证据没有时间戳**——「学习者什么时候答的」答不上来，因此「哪份诊断更
  新」只能靠诊断自己的 `at`。这条留给后续主题。

## 补充说明（2026-11-26）

实现中确认的事实：

1. **矛盾的处置不是偏好，是领域模型给的。** 原本以为「诊断与进度不一致时信进度」
   是一条可以讨论的策略；实现时才发现迁移表**根本没有**「已学会 → 未开始」这条
   边（ADR-0018 刻意去掉），所以**「信诊断」根本不是一个可选项**。领域模型先划出
   了边界，应用层只能在边界内选。
2. **「学完了」蕴含「学过」。** `complete()` 只在「学习中」时合法。Tutor 报「学完
   了」时，若还没记录「开始学」，用例得自己补上这一步——否则领域层的两段式迁移
   会挡住一次合法的完成。
3. **先写进度后写计划，让重试变成幂等。** 反过来写会留下一份「依据是假的」计划；
   正过来写，中途失败后重跑不会重复迁移（`assess()` 只在「未开始」时生效）。
4. **「取最新的一份诊断」需要诊断有时间。** 诊断原本没有 `at`——于是「多份诊断取
   哪一份」只能靠标识字典序，那不是时间。加一个字段比加一套排序启发式便宜。
5. **版本号跟踪的是已发布的形状，不是每次编辑。** 诊断加了 `at`（负载形状也变
   了），但负载版本仍是 1——因为还没有真实数据。等有数据时，形状一变就是 2，那
   时才需要迁移工具（ADR-0026 已记下这个缺口）。
6. **半更新状态被显式承认，而不是藏起来。** 「一次事务只改一个聚合」意味着这
   条链上是两次独立的写；中间失败就可能只做了一半。顺序（先进度后计划）让重跑
   安全，但**调用方仍要知道这件事**。
7. **空版本是噪音，不是历史。** 最初的设计是「计划每次都出新版本」，理由是「变了
   没有要从版本里看得见」——但 ``delta`` 已经回答了这个问题，空 delta 的版本什么
   也没说。于是改为：**内容没变就不产生新版本**（§7 的修正）。改完之后，整个工作
   流才**真幂等**：同样的诊断 + 同样的进度 ⇒ 什么都不写，返回同一个版本。
8. **「基于哪一版」现在还是冗余信息。** 复核时发现 ``revise_plan`` 的基线永远是
   该线的最大版本号，因此基线恒等于 ``number - 1``——显式记录它不携带新信息。它
   的真实价值在三个还没到的场景：**回滚后重新修订**（基线 ≠ number-1 的第一个场
   景）、**基线过期检测**、**多诊断并发时的合并**。因此本阶段**不加**该字段，等
   场景出现时再迭代（字段设计成可选的，旧负载不需要迁移）。
