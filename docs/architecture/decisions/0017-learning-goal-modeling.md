# ADR-0017: 学习目标的建模——状态机、结构化约束与保证边界

- 状态：已接受
- 日期：2026-11-24

## 背景

Topic 17 的工程问题是：**学习目标的状态机是什么？目标约束（时间、难度、前置
条件）应由领域层保证，还是由应用层保证？**

ADR-0015 建了目标这个聚合，但只给了最简形态：

```python
LearningGoal(id, learner_id, course_id, statement, outcomes, constraints, status)
GoalStatus = Literal["active", "achieved", "abandoned"]
GoalConstraint(kind="time" | "prerequisite" | "preference", text="每周 3 小时")
```

三个问题让它撑不住 Phase 1 的真实流程：

1. **状态机太粗，且不留下痕迹。** 只有 `active → achieved / abandoned` 两条边，
   没有「目标还没诊断」「目标被搁置」「目标过了期限」这些真实状态；状态是**直接
   存的字段**，不是从历史派生的，于是「目标为什么变成现在这样」没有答案——
   这与 ADR-0015 自己写的审计要求（"目标是否达成…都要能回答「什么时候、依据
   什么」"）矛盾。
2. **约束是自由文本，无法校验，也无法参与计算。** `text="每周 3 小时"` 回答不了
   「每天能学多久」「这个期限还剩几天」「投入时间够不够」。它只能被渲染成一段
   文字给模型看，领域层拿它做任何事都做不了。
3. **目标与知识点的绑定没有建模。** ADR-0015 明确把这件事留给 Topic 17：
   "`LearningGoal` 没有 `knowledge_point_ids`——目标绑定知识点是 Topic 17 的
   建模内容"。没有绑定，目标就只是「一句想学的话」，无法回答「这个目标要掌握
   哪几个知识点」「哪些前置必须先会」。

同时，本主题的第二个问题——**约束该由哪一层保证**——在 ADR-0015 里只留了半句
话："`LearningGoal` 的引用完整性（learner / course 是否存在）在内存里无法校验
——需要应用层或存储层保证"。这句话把「内存里无法校验」等同于「应用层的事」，
但这两件事并不等价：**需要别的聚合的数据**和**需要外部事实**是两种不同的需求，
落点也不同。

Phase 1 没有主教材章节，状态机与约束的建模由本项目自己定。

## 决策

**目标建模为一个显式状态机（状态由迁移历史派生）；约束从自由文本升级为结构化
值对象；目标按 id 绑定知识点；保证责任按「判断需要什么数据」分三档。**

### 1. 状态机：六个状态，迁移表写成数据

| 状态 | 含义 | 可迁往 |
| ---- | ---- | ------ |
| `draft` | 草稿：已提出，尚未绑定知识点 | `active`、`abandoned` |
| `active` | 进行中 | `achieved`、`abandoned`、`suspended`、`expired` |
| `suspended` | 已暂停（可恢复） | `active`、`abandoned`、`expired` |
| `achieved` | 已达成（终态） | — |
| `abandoned` | 已放弃（终态） | — |
| `expired` | 已过期（终态） | — |

迁移表写成 `_TRANSITIONS: dict[GoalStatus, frozenset[GoalStatus]]` 这份**数据**，
而不是散落在方法里的 `if`。理由：状态机的价值在于「哪些迁移合法」有一个可以
直接读、可以直接测的地方；散落的 `if` 让这张表只能靠读代码重建。

**`suspended` 与 `abandoned` 分开**是这一节的核心判断：搁置（出差、换项目）
是可逆的，放弃是终态。把两者合并成「非进行中」会丢掉「之后还能不能捡回来」
这个信息，而后续的计划调整（Topic 50）与复习调度（Topic 52）都要用到它。

**`draft` 的存在**来自真实流程：目标是学习者提的，知识点是诊断之后才定的
（Topic 20）。草稿状态让「先有目标、后有范围」有地方放，而不是逼着系统在
还不知道学什么的时候先造一个空目标。

**`expired` 与「时间范围」绑定**：没有时间范围的目标不存在过期。

### 2. 状态由迁移历史派生，历史是唯一事实来源

```python
@property
def status(self) -> GoalStatus:
    if not self.transitions:
        return "draft"
    return self.transitions[-1].target
```

`LearningGoal` **不再存 `status` 字段**。如果同时存 `status` 和 `transitions`，
就会出现「状态说一套、历史说另一套」——这正是 ADR-0013 批评的「计划是一段可以
被整体覆盖的文本」的同一个病。派生只有一条路，不存在不一致。

每次迁移留下一条 `GoalTransition`：

```python
GoalTransition(source, target, reason, at)
```

**理由必填**：没有理由的状态变化无法解释。ADR-0015 要求「什么时候、依据什么」，
`reason` 给「依据什么」，`at` 给「什么时候」。

**时间由调用方传入**（`at: float`），领域层不读时钟。这与 ADR-0015 一致：
领域模型不认识外部世界，「现在几点」是应用层的事。

### 3. 约束：结构化值对象替代自由文本

| 旧 | 新 |
| -- | -- |
| `GoalConstraint(kind="time", text="每周 3 小时")` | `TimeWindow(start, end)` + `DailyEffort(minutes_per_day)` |
| `GoalConstraint(kind="prerequisite", text="函数与作用域")` | `prerequisites: tuple[KnowledgePointId, ...]` |
| `GoalConstraint(kind="preference", text=...)` | 删除（学习偏好是 `Learner` 的属性，ADR-0015 已如此建模） |

三个决定：

1. **时间拆成「范围」与「投入」两个值对象**。「每周 3 小时」既没说清从哪天到
   哪天，也没说清每周哪几天——拆开之后才能分别回答「还剩多少天」「每天能投入
   多久」，也才能算出「总量够不够」。
2. **前置条件用知识点 id，不用文本**。前置条件说的是「要先会哪个知识点」，
   文本版本没法校验「这个知识点存不存在」，也没法和知识结构的前置闭包
   （ADR-0016）对照。
3. **难度不建模为目标约束**。难度是**知识点的属性**（课程侧），目标侧表达的是
   「掌握哪些知识点」「达到什么结果」；掌握层次属于掌握度模型（Topic 43）。
   在目标上加一个「难度」字段，会让同一门课里同一个知识点在不同目标下有不同的
   难度——那是把课程的事实复制到目标上。

**`TimeWindow.has_passed(now)` 是纯查询**：调用方给出「现在」，领域层不自己读
时钟。

### 4. 目标绑定知识点：能力要求

```python
CapabilityRequirement(point_id: KnowledgePointId, outcome: str)
```

「哪个知识点」+「它支撑目标的哪一条学习结果」。知识点是 `Course` 聚合内部的
实体，这里**只按 id 引用**——延续 ADR-0015 的「跨聚合只按 id 引用」。

**能力要求不另立结果**：`outcome` 必须是 `LearningGoal.outcomes` 中已有的一条。
它回答的是「这条结果由哪个知识点支撑」，不是「另一条结果」。如果允许它另立，
同一件事会有两份说法（一条在 `outcomes`，一条在 `requirements`），映射给规划器
时就会变成重复任务——实现过程中确实先踩了这个坑：目标有 3 条结果、1 条能力要求
时，规划器拆出了 4 个任务。

因此 `requirements` **不进入** `GoalSpec.outcomes`；`outcomes` 只映射目标的
学习结果。

绑定关系可双向查询：`points_for(outcome)` / `outcomes_for(point_id)`。

**绑定只能在草稿阶段做**（`bind_requirements`）。激活之后再改绑定是一次**范围
变更**，属于计划调整（Topic 50），不是目标建模。

### 5. 保证边界：按「判断需要什么数据」分三档

这是本 ADR 对 Topic 17 那个问题的直接回答。

| 档位 | 判断依据 | 落在哪里 | 例子 |
| ---- | -------- | -------- | ---- |
| 聚合内自洽 | 只看目标自己的数据 | `goal.py` 构造时校验 | 时间范围结束晚于开始；每日投入为正；能力要求的结果出自 `outcomes`；迁移历史不断链 |
| 跨聚合一致 | 需要另一个聚合的**已有数据** | `consistency.py` 领域服务 | 目标引用的知识点是否存在于目标课程的知识结构中 |
| 依赖外部事实 | 需要时钟、掌握度、学习证据 | **应用层** | 时间窗口是否已过期；前置知识点是否已被学习者掌握；目标是否真的达成 |

三档的理由：

- **第一档必须在领域层**：只看自己的数据就能判断的规则，放到别处就意味着调用方
  可能拿到不自洽的对象。
- **第二档留在领域层**：它是**纯函数**（不读数据库、不调模型、不读时钟），规则
  本身是业务知识（"目标不能引用课程里不存在的知识点"），因此可以脱离基础设施
  单独测试。ADR-0015 把它归给「应用层或存储层」过于粗糙——它需要的只是另一个
  聚合对象，不需要任何基础设施。
- **第三档必须留给应用层**：判断需要领域模型**看不见**的事实。让领域层假装能
  回答「学习者是否已掌握 k1」，等于要在领域模型里塞一个掌握度模型（Topic 43）
  或者读时钟——都会破坏依赖方向。

领域服务**只报告不一致，不替调用方做决定**：

```python
issues = check_goal_against_course(goal, course)
# → GoalIssue(code="unknown_requirement_point", message="…不存在的知识点：k9")
```

一次检查可能同时发现多个问题，因此返回问题列表而不是抛异常。应用层拿到问题后
是拒绝保存、自动修正还是提示用户，取决于用例——这是应用层的决定。

### 6. 目标模型独立成 `goal.py`

`LearningGoal` 与它的值对象从 `domain.py` 拆到 `goal.py`，`domain.py` 保留学习者、
课程与知识结构。原因：目标的状态机、约束、绑定规则加起来接近 `domain.py` 的
体量，混在一起会让两个聚合的规则互相淹没。跨聚合的一致性检查单独放
`consistency.py`。

依赖方向：`consistency.py` → `goal.py` → `domain.py`，单向。

### 7. 映射契约不变

`GoalSpec`（ADR-0013 §10）**不扩展**。能力要求与知识点的对应关系不进
`GoalSpec`——`GoalSpec` 是领域无关的运行时契约，把知识点塞进去会让运行时开始
认识学习领域的概念。「计划任务粒度如何与知识点对齐」是 Topic 23（Learning
Planning）要回答的问题，那里再决定运行时契约是否需要扩展。

映射结果：

| 目标侧 | `GoalSpec` 侧 |
| ------ | ------------- |
| `statement` | `statement` |
| `outcomes` | `outcomes` |
| `time_window` | `constraints`（渲染成文本） |
| `daily_effort` | `constraints` |
| `prerequisites` | `constraints` |
| `requirements` | 不进入 |
| `course_id` | 不进入 |

## 后果

- 好处：状态机有唯一事实来源（迁移历史），「目标为什么变成现在这样」有答案；
  约束可校验、可计算，不再是只能给模型看的文本；目标能回答「要掌握哪几个
  知识点」；保证责任的三档划分明确，领域层、领域服务、应用层各自知道该管什么。
- 代价：**API 迁移**——`GoalConstraint` 与 `GoalStatus` 被移除，`status` 字段
  变成派生属性，`achieve()` / `abandon()` 改为需要 `at` 与 `reason`。所有调用方
  在本主题内完成切换。
- 代价：目标实体变重（带迁移历史）。这是刻意的：审计需求（ADR-0015）要求
  历史不被原地改掉，而不可变实体 + 迁移历史是当前无数据库条件下唯一能保证
  这点的做法。接数据库后需要考虑历史独立成表。
- 风险：**六个状态可能过细**。`suspended` 与 `expired` 目前没有产品侧的强需求
  驱动（复习调度在 Topic 52、计划调整在 Topic 50）。如果那些主题证明不需要
  它们，删掉即可——迁移表是数据，删一个状态不影响其它设计。
- 风险：**能力要求只能指向已有结果**，意味着「诊断发现了一条新结果」不能通过
  绑定来表达，只能改目标本身。这是刻意的保守选择：结果集合的变化是目标范围
  的变化，比绑定更重。
- 边界：掌握度、学习进度、证据型评估、持久化仍未建模；目标与知识点的跨课程
  身份问题仍留给 Topic 22。

## 补充说明（2026-11-24）

实现中确认的事实：

1. **状态派生比状态存储更省事也更安全**：`status` 字段删掉后，「状态与历史
   不一致」这个状态在类型上就不存在了——不是靠校验拦住，而是无法表达。
2. **迁移历史要校验连续性**：只校验「每条迁移合法」不够，还要校验「上一条的
   目标状态等于下一条的来源状态」。否则历史可以是 `draft → active` 与
   `draft → achieved` 两条独立分支，看起来合法，实际讲不出一个过程。
3. **「拒绝的理由」比「错误类型」更有用**：非法迁移的错误信息里带上**当前
   状态与目标状态**（"状态为已达成，不能再变更为已放弃"），调用方不需要再查
   一次当前状态。
4. **能力要求不另立结果是必要的，不是洁癖**：实现中先允许它另立，映射到
   `GoalSpec.outcomes` 后规划器拆出了重复任务（3 条结果 + 1 条能力要求 = 4 个
   任务）。改成「必须指向已有结果」后，重复消失，任务数回到 3。
5. **跨聚合检查用领域服务而不是放进 `LearningGoal`**：把 `Course` 传进目标
   的构造或方法里，等于让目标持有另一个聚合，破坏 ADR-0015 的单向引用。领域
   服务接受两个聚合作为参数，不持有任何一个。
6. **「需要外部事实」与「需要别的聚合」是两件事**：ADR-0015 把引用完整性归给
   应用层，实际上它只需要另一个聚合对象，因此可以留在领域层做纯函数检查。
   真正必须上移的是「是否过期」「是否已掌握」「是否真的达成」。
