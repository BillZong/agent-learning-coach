# ADR-0016: 知识表示——知识点与关系的建模

- 状态：已接受
- 日期：2026-11-24

## 背景

Topic 16 的工程问题是：**Knowledge Point 与 Knowledge Relation 如何建模，才能
同时支撑后续的路径计算与薄弱点归因？**

Topic 15 的初版把「前置」直接挂在知识点上：

```python
KnowledgePoint(id, title, prerequisites=(...))  # 已废弃
```

这在小规模结构里够用，但有两个后续消费者时就不够：

1. **路径计算**需要整张图，而不是逐个点查前置。给它一个「每个点自带前置列表」
   的结构，每次算顺序都要把所有点重新拼起来。
2. **薄弱点归因**需要**传递闭包**——「k3 没掌握，先补哪些」，
   「k1 没掌握，后续哪些受影响」。闭包是图查询，字段里存不下。

此外还有两个具体问题：

- **关系种类被压成了一种。** 初版只有「前置」；实际需要区分「必须先掌握」
  （阻塞学习）与「属于哪个主题」（归属/聚合）。混在一起之后，顺序计算无法
  判断哪条边该参与调度。
- **改关系要复制知识点。** 关系是点上的字段时，增加一条前置就得重建整个
  `KnowledgePoint`；而关系本质上是**结构的事实**，不是点的属性。

Phase 1 没有主教材章节，关系建模由本项目自己定。

## 决策

**知识结构独立成值对象 `KnowledgeStructure`（知识点 + 关系），课程拥有它；
关系外置成 `KnowledgeRelation`，分 `requires` 与 `part_of` 两种；路径与归因
都是派生查询。**

### 1. `KnowledgeStructure` 是值对象，`Course` 拥有它

```python
KnowledgeStructure(points=(...), relations=(...))
Course(id, title, structure=KnowledgeStructure(...))
```

结构没有自己的 id：它是课程的一部分，内容相同就是同一个结构。`Course` 不再
直接持有知识点元组，避免「课程 + 知识点 + 关系」三份数据之间的复制。

### 2. 知识点只描述「是什么」，不描述「依赖谁」

```python
KnowledgePoint(id, title, summary="")
```

前置与归属从知识点上移除。好处：

- 改一条关系不需要复制任何知识点；
- 同一条关系只存在一处，不会出现「点上的列表」与「结构里的边」两份事实；
- 关系可以独立校验（端点、重复、环）。

### 3. 两种关系，语义不同，分开校验

| 关系 | 语义 | 规则 | 消费者 |
| ---- | ---- | ---- | ---- |
| `requires` | `source` 必须先掌握 `target` | 有向、无环、不重复 | 学习顺序、归因闭包 |
| `part_of` | `source` 属于 `target` 这个主题 | 有向、无环、**一子一父** | 主题层级、展示聚合 |

- **`requires` 决定「能不能开始」**，因此顺序计算只认它。
- **`part_of` 决定「归到哪个主题」**，因此它不参与调度。单父约束是为了让
  「这个点属于哪」永远有唯一答案；多父会让归因与展示都变得含糊。
- 两种关系各自成 DAG，互不约束：一个点可以既依赖另一个点，又属于第三个主题。

### 4. 关系是值对象，重复声明是错误

`KnowledgeRelation(kind, source, target)` 没有 id；同一三元组出现两次就是同一条
关系。结构拒绝重复、拒绝自指、拒绝端点缺失。错误信息直接给出问题本身
（`重复的关系：requires k1 -> k2`、`requires 关系引用了不存在的知识点：k9`）。

### 5. 路径与归因都是派生查询

| 查询 | 回答 |
| ---- | ---- |
| `order()` | 先学什么（`requires` 拓扑序，并列按声明顺序） |
| `entry_points()` | 哪些点可以开始（没有前置） |
| `prerequisites_of(id)` | 直接前置 |
| `prerequisite_closure(id)` | 全部传递前置，按学习顺序——**补课顺序** |
| `dependent_closure(id)` | 全部传递后继，按学习顺序——**影响范围** |
| `parent_of(id)` / `children_of(id)` | 主题层级 |

**不持久化顺序与闭包。** 它们每次重算：缓存会让「关系改了、顺序没变」成为
可能。这与 ADR-0013 的「展示顺序不是调度顺序、历史顺序」同一个原则。

### 6. 诊断策略不在本层

`prerequisite_closure` / `dependent_closure` 是**归因原语**，不是诊断结论。
「某点没掌握时该补到哪一层、要不要跳级」属于 Topic 20（Diagnostic Assessment）
的策略；领域层只保证查询本身正确且有序。

### 7. 知识点仍然课程内，不做跨课程共享

Topic 15 把这个决定留给 Topic 16。现在决定：**保持课程内**。理由：

- 归因发生在**一门课**的知识结构与学习证据里；跨课程归因当前没有数据支撑；
- 全局知识点身份需要额外的一层知识地图聚合、去重与合并策略，这不是 Topic 16
  能顺手做掉的；
- 等 Topic 22（Knowledge Mapping）真正需要跨课程视图时，再决定是「全局 id」还是
  「映射表」。

### 8. 暂不做 `related`（无向关联）

没有消费者：顺序只要 `requires`，归因只要 `requires` 闭包，层级只要 `part_of`。
无向边的去重（`(a,b)` 与 `(b,a)`）与对称闭包会把校验复杂度翻倍，却换不来可用
能力。等出现「相关知识点推荐」这类需求再加。

## 后果

- 好处：顺序、补课路径、影响范围、主题层级都有确定答案；关系改动不牵连知识点；
  校验集中在结构构造处；错误信息可直接给模型或用户。
- 代价：**API 迁移**——`KnowledgePoint.prerequisites` 与
  `Course.knowledge_points` 被移除，所有调用方在本主题内完成切换；查询每次
  O(V+E)，没有缓存。
- 风险：单父 `part_of` 可能过严（一个点同时属于「语法」与「函数式」两个主题）。
  放宽它只需要改校验与 `parent_of` 的返回形状，不改存储结构。
- 边界：跨课程归因不可用；`related` 未建模；不变量仍只在内存校验（与
  ADR-0015 同一条工程债）。

## 补充说明（2026-11-24）

实现中确认的事实：

1. **拓扑序的并列项必须稳定**：同一层可开始的知识点按**声明顺序**输出，否则
   同一份结构每次渲染的顺序可能不同，测试与展示都不可复现。`_requires_edges`
   因此按声明下标排序，而不是关系插入顺序。
2. **闭包必须按学习顺序返回**：调用方要的是「先补什么」，不是一个集合。因此
   `prerequisite_closure` / `dependent_closure` 都按 `order()` 过滤，而不是按
   BFS 发现顺序。
3. **成环信息要能直接定位**：`requires 依赖成环：k1 -> k2 -> k1` 比「有环」可
   行动得多。DFS 同时记录路径，输出用 id（唯一）而不是标题（可能重复）。
4. **`part_of` 的环检测更简单**：单父约束下只需沿父链走，遇到重复节点即成环，
   不需要通用图算法；这条简化是单父约束的附带收益。
5. **「起点」包含主题节点**：主题也是知识点，只是没有前置。示例里
   `entry_points()` 会输出主题节点，这是模型的直接结果，不是缺陷；若未来要把
   主题与学习单元分开，那就是 Topic 22 的节点类型问题。
