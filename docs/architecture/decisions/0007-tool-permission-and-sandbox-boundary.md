# ADR-0007: 工具权限检查与沙箱边界

- 状态：已接受
- 日期：2026-11-19

## 背景

Topic 06 交付的 Agent Runtime 已经能执行工具、校验参数、处理超时与失败。但
它对「这个工具该不该被调用」没有任何判断——所有已注册的工具对模型一律可见、
一律可执行。

Topic 07 提出的工程问题是：**Tool 权限检查应放在 Dispatcher 还是 Runtime 层？
Sandbox 的最小威胁模型是什么？**

之所以现在必须回答，是因为本项目的工具来源已经不只有本地函数：远端 MCP
Server 的工具描述（含参数 schema）由对方提供，模型可以在每一轮里请求任意
一个已注册的工具。模型的意图不可信——它可能被诱导，也可能只是幻觉。

同时，在实现 Topic 07 的测试时发现一个**真实缺陷**：工具的参数 schema 本身
不合法时，`jsonschema` 抛出的 `UnknownType` / `TypeError` 等非校验类异常会
逃出 `dispatch()` 的错误归一化，直冲运行时——**一个远端 MCP Server 提供的
畸形 schema 就能让整个 Agent 运行崩溃**。

## 决策

**权限检查放在 Dispatcher（唯一执行边界）；运行时只负责可见性过滤；沙箱作为
后续阶段的设计保留，不在本次实现。**

### 1. 权限检查放在 Dispatcher，不放在 Runtime

Dispatcher 是**唯一的执行边界**：本地工具、远端 MCP 工具、结构化输出的
`final_answer` 工具全部经过 `ToolDispatcher.dispatch`。检查点只有一个，就
不存在「新增一条执行路径忘了检查」这种 fail-open 漏洞。

放在 Runtime 的话，Runtime 必须知道每个工具的来源与危险程度。一旦有人新写
一条执行路径（新的工具来源、新的批量执行入口）而忘了检查，检查就**默认
放行**——这是安全系统里最危险的失败模式。

Runtime 仍然有一份职责，但它是**可见性**而非强制：`AgentRuntime` 给模型的
工具清单来自 `dispatcher.allowed_specs()`，无权的工具模型根本看不见。这是
纵深防御的一层，不是唯一一层。

### 2. 作用域（capability）模型，不是角色模型

工具在 `ToolDefinition.scopes` 里声明所需作用域，策略持有已授予的作用域，
工具所需是授予的**子集**才放行。

选能力模型而非角色模型的理由：角色模型要维护「角色 → 权限」的映射表，还要
处理角色继承与冲突；能力模型只需要「本次运行授予了哪些能力」这一份清单，
且这份清单天然与「本次会话允许做什么」对齐。

作用域**不进 `ToolSpec`**，不会发给模型——它是运行时的授权依据，不是模型的
输入。

### 3. 未声明作用域的工具恒放行

这是声明式授权的固有代价，必须写进文档而不是假装不存在：工具作者忘了声明，
等于默认公开。

因此远端工具由 `discover_mcp_tools` 自动授予 `mcp:<命名空间>` 作用域——
**一个作用域就能关掉整个不可信 Server**。

### 4. 默认放行，但生产应显式给策略

`ToolDispatcher` 的默认策略是 `AllowAllPolicy`，保证不配置权限时行为与引入
权限机制之前完全一致（不破坏既有调用方）。

但 `DenyAllPolicy` 一并提供，理由是**安全默认值**：在不确定该给哪些权限时，
先全部拒绝，再按需放开。

### 5. 权限拒绝归一化成错误结果，不抛异常

被拒绝的调用返回 `status="error"` 的 `ToolOutcome`，回填给模型。这与
Dispatcher「每一步的失败都收敛成 ToolOutcome」的既有约定一致——模型读到
「缺少权限作用域：fs:write」，可以改用别的工具。

代价是模型可能反复尝试同一个被拒的工具；用既有的「连续失败」停止条件兜住。

### 6. 权限检查在参数校验之前

被拒绝的工具连参数都不校验。既不浪费工作，也不把「这个工具的参数应该长什么
样」泄露给无权调用的一方。

### 7. 组合调度器必须保留策略

`AgentConfig.output_model` 设置后，运行时会组合出一个新的调度器（补
`final_answer` 工具）。**策略必须一并带过去**——漏掉就等于给被限制的工具
开了一个后门。这是本次实现中特意加回归测试的一处。

### 8. schema 畸形必须被收敛，不能打断运行

`validate_arguments` 把 `jsonschema` 的构造与遍历都包在保护里，畸形 schema
收敛成 `ToolSchemaError`，由 Dispatcher 归一化成错误结果。

不收敛的代价是：远端 MCP Server 提供一个畸形 schema，就能让客户端的整个
Agent 运行崩溃。这不是「远端服务有 bug」，而是**我们的进程被远端的输入搞挂
了**——信任边界画错了。

### 9. 沙箱是设计，不是本次实现

沙箱隔离的方案、层级与选层规则写在 [`docs/engineering/sandbox.md`](../../engineering/sandbox.md)，
本次不实现代码。理由：沙箱要解决的是「已授权工具的副作用越界」，而这需要
产品先确定是否有代码执行场景（L3）。

**权限模型是沙箱的前置条件，不是替代品**：权限模型能保证「没授权的工具不会
被调用」，但管不了「已授权的工具执行时被注入」。两者都要在。

## 后果

- 好处：工具调用有了显式的授权边界；检查点唯一，不存在绕过路径；模型看不到
  无权工具，不浪费轮次；畸形 schema 不再能打断运行；远端 Server 可以按
  namespace 整体关掉。
- 代价：每个工具都要声明作用域（漏声明 = 默认公开）；默认策略是放行，生产
  配置要显式给策略；权限拒绝会占用「连续失败」预算，模型反复重试会更快触发
  停止条件。
- 边界：作用域只到**工具粒度**，不到**参数粒度**——`read_notes` 拿到了
  `fs:read`，它内部读什么路径不在权限模型的管辖范围内；权限是**运行期**的，
  不做身份认证；未实现沙箱、未实现人工确认、未做上下文来源标记（T6 目标
  操纵仍未缓解）。

## 补充说明（2026-11-19）

实现中确认的事实：

1. **检查点的选择比检查的严格程度更重要**。把检查放 Dispatcher 的真正收益
   不是「拦住了某个调用」，而是「以后新增的执行路径不可能绕过它」。
2. **未声明作用域 = 默认公开**，这是声明式授权绕不开的代价。缓解手段不是
   改成隐式授权（那更糟），而是让声明成为工具契约的显式组成部分，并对远端
   工具自动补上。
3. **校验器不该比 schema 更严格**。JSON Schema 默认允许多余属性；校验器擅自
   收紧就变成了「告诉模型 A、实际按 B 校验」——正是 `core/tools/schema.py`
   模块文档要避免的错位。严格性由 schema 作者用 `additionalProperties: false`
   显式声明。
4. **畸形 schema 是一个真实的 DoS 面**。它此前没有被发现，是因为测试里没有
   「schema 不合法」这一档——这类缺陷只有在把失败路径穷举时才会暴露。
