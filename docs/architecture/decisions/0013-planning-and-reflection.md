# ADR-0013: 计划与反思的职责边界

- 状态：已接受
- 日期：2026-11-24

## 背景

主教材 Ch7 给出两件事：

- **Planning**（7.2）：一个 `create_tasks` 工具，模型把任务清单**整份重写**一遍，
  并在清单上标记 `pending` / `in_progress` / `completed`。
- **Reflection**（7.3）：一个 `reflection` 工具，模型写下当前状况的判断，
  需要重规划时把 `need_replan` 置为 True。

外部参考是 Anthropic 的 Evaluator-Optimizer 模式：一个调用产出结果，另一个
调用评估并给出反馈，两者循环迭代，直到评估方认可或迭代次数用尽。它有效的
前提是**有明确的评估标准**。

Topic 13 的工程问题是：**Planner 与 Reflection 的职责如何切分？如何避免反思
循环把学习计划越改越乱？**

「越改越乱」不是修辞。教材的实现里，计划是**一段可以被整体覆盖的文本**：
每次重规划，模型都要重写整份清单。于是

- 已完成的任务可能被新清单漏掉——进度被抹掉；
- 同一个任务可能被重复添加——清单越滚越长；
- 任务顺序随每次改写漂移——依赖关系不再成立；
- 「为什么要改」无处可查——只有模型自己知道。

根因不在模型，而在于**计划没有被建模**。文本没有状态、没有身份、没有历史，
因此每一次改写都是从零开始。

本项目还有两个额外约束：

1. **确定性核心优先**。学习进度与知识掌握度的判断要基于可观察的证据。计划
   是学习状态的一部分，不能只活在模型的上下文里。
2. **Phase 1 才是学习领域**。当前是 Phase 0，`core.agent` 不应该认识学习
   领域的具体概念（`LearningGoal`、知识点、掌握度），但今天要确定领域模型
   与运行时之间的**交接形状**。

## 决策

**计划是带状态与历史的对象；反思只产出判断，不改计划；改计划是另一步，
且必须引用那条反思。**

### 1. 计划是对象，不是文本

新增 `core/agent/planning.py`。计划的核心类型：

- `PlanTask`：任务。有**稳定 id**（`t1`、`t2`……）、内容、状态、依赖。
- `Plan`：目标 + 任务列表 + **修订历史** + **反思记录** + 重规划计数。
- `PlanRevision`：一次修订。记录改了哪些任务、从什么改成什么、理由是什么、
  由哪条反思触发。
- `Reflection`：一次反思。结论 + 判断依据 + 证据。

计划存在 `ExecutionContext.state` 里，因此**随会话快照一起持久化**，也随会话
恢复一起回来——这是 ADR-0009 的直接推论：少存一项，恢复出来的就不是原来那个
运行。

### 2. 任务身份与内容：id 稳定，内容不可改写

- **id 稳定**：任务一旦创建，id 不变。引用任务靠 id，不靠文字。
- **内容不可改写**：任务文字定下就不改。要换说法就**新建任务并跳过旧的**。
  理由：文字变了，历史里对它的引用就指不准了；「不可改写」把这件事变成
  显式动作（新建 + skip），而不是隐式漂移。

### 3. 不删任务，只跳过任务

没有「删除」这个操作。移除一个任务 = 把它标成 `skipped`，它**仍然留在计划
里**。计划因此只增不减，历史可查；同时模型能看到「这条路我走过、放弃了」。

`skipped` 是**唯一终态**：被跳过的任务不能再回到进行中——想恢复就新建一个
任务。其余状态（`pending` / `in_progress` / `blocked` / `completed`）之间允许
迁移，每次迁移都进版本历史。

### 4. 同一时刻只有一个进行中的任务

模型不能同时推进三件事。这条约束让「计划当前在做什么」永远有唯一答案，
也顺手挡掉了模型把所有任务都标成 `in_progress` 的常见行为。

### 5. 依赖必须闭合且无环

- 依赖只能指向存在的任务；
- 依赖成环会被拒绝（写入时确定性检查，不交给模型）；
- **进行中的任务，其前置必须已完成**——否则「计划」与「现实」立刻脱节。

展示顺序由**依赖**决定，不由创建顺序决定。重规划插入的前置任务一定晚于
依赖它的任务被创建，按创建顺序展示的话前置任务会排在后面，计划读起来就是
乱的。因此渲染时做拓扑排序。

### 6. 结构性修改与普通推进分开算账

- **普通推进**（`pending` → `in_progress` → `completed`）不改变计划的形状，
  **不消耗**重规划预算。
- **结构性修改**（新增任务、跳过任务、重新打开已完成的任务、改依赖）改变
  形状，**消耗**一次重规划预算。

分账的理由：正常推进本来就不该被算成「又改了一次计划」。如果两者共用一个
额度，跑一遍正常的计划就要把额度花光，额度也就失去了约束作用。

### 7. 反思不改计划

`reflect` 工具只记录判断，**不碰计划**。结论有四种：

| 结论 | 含义 |
|---|---|
| `continue` | 进展正常，继续推进 |
| `accept` | 当前目标已完成 |
| `replan` | 需要修改计划 |
| `blocked` | 缺少外部条件，无法继续 |

只有 `replan` 会产生一个**待处理的重规划请求**。此时下一次结构性修改
**必须引用那条反思的 id**，否则被拒绝。

于是「反思 → 重规划」被拆成两个显式步骤：

```
reflect(verdict="replan")        ->  产生待处理请求 r1
update_plan(..., reflection_id="r1")  ->  结构性修改被接受
```

好处有两个：改计划的理由永远有出处；模型不能在没有判断的情况下随手改计划。

**最新一条反思代表当前意图**：如果模型在请求重规划之后又记了一条
`continue`，先前的请求就作废——否则会死锁（模型想改又没改，请求一直挂着）。

### 8. 额度

`PlanPolicy`：`max_replans`（默认 3）、`max_reflections`（默认 6）、
`max_reflections_per_task`（默认 2）。

- 重规划预算用尽 → 结构性修改被拒绝，模型只能继续推进现有任务，或向用户
  说明卡在哪里。
- 反思有总量上限与单任务上限——同一个任务反复反思不会带来新信息，只会
  烧预算。

### 9. 整批原子

一次 `update_plan` 提交的是**一批**修改。任何一条不合法，整批都不生效。

半生效的计划比不改更糟：它既不是模型想的样子，也没有被完整记录——「计划为什么
变成现在这样」就答不上来了。

### 10. 学习目标到学习任务的转换：领域模型负责「是什么」，运行时负责「怎么变」

`core.agent` 不认识学习领域。它只认识 `GoalSpec`——一个领域无关的目标描述：

```python
GoalSpec(goal_id, statement, outcomes, constraints)
```

Phase 1 的 `LearningGoal` 领域模型映射成 `GoalSpec`，再交给规划器：

```
LearningGoal（领域模型）
    -> GoalSpec（运行时契约）
    -> PlanDraft（任务草稿，依赖用下标表示）
    -> Plan（状态机校验后的计划）
```

拆解有两种实现：

- `OutcomePlanner`：**确定性**拆解，一个学习结果一个任务，按顺序串联。它是
  基线——模型拆出来的计划至少不该差于「按结果逐条推进」，同时它让上层在
  没有模型可用时也能拿到一份可执行计划。
- `LLMPlanner`：模型拆解。模型只负责**提出**任务，规则由状态机校验：重复
  内容、越界的依赖下标、空任务列表都会被拒绝。**模型不负责保证计划合法。**

## 后果

- 好处：计划不会越改越乱——有稳定身份、有状态机、有历史、有预算；改计划的
  理由有出处；计划随会话持久化；「为什么变成现在这样」永远有答案。
- 代价：一个包、一层抽象；模型要多学一套约束（内容不可改写、单一进行中
  任务、引用反思 id）；被拒绝的修改会占掉模型轮次（错误会回填给模型，它会
  改，但那要花 token）。
- 边界：**计划不进模型的上下文窗口**——目前靠应用层把渲染后的计划放进
  prompt，没有做上下文预算裁剪；**反思没有独立的质量评估**——`replan` 的
  判断对不对，程序不验证，只记录；**没有任务级的重试策略**——失败的任务由
  模型自己决定是否重开。

## 补充说明（2026-11-24）

实现中确认的事实：

1. **整份重写是问题本身，不是实现细节**：教材的 `create_tasks` 每次都要重写
   整份清单。改成增量提交（只发改动的任务）之后，「已完成的任务被漏掉」这类
   故障从机制上消失了——增量提交没有机会漏掉没提到的任务。
2. **「新建任务」需要能指定 id**：自动分配的 id 模型事先不知道，因此「新建
   一个前置任务，并让另一个任务依赖它」没法在一次提交里写完。允许显式指定
   `new_task_id` 之后，同一批修改里的依赖关系可以一次写完，且与两条在清单里
   的先后无关（id 先分配、后校验）。
3. **约束会互相顶住**：插入一个前置任务时，若被依赖的任务正在
   `in_progress`，「前置必须已完成」这条规则会拒绝这次修改。**这是对的**——
   计划不能一边说「还没开始」一边说「正在做」。但错误信息必须说清怎么改，
   否则模型只会反复重试同样的提交。
4. **管理器不能缓存计划**：同一个执行上下文上会存在多个管理器（应用层一个、
   工具每次调用一个）。缓存副本会让它们各自看到不同的计划——那正是「计划
   越改越乱」的另一种形态。执行上下文是唯一权威，每次重读。
5. **渲染顺序不是创建顺序**：重规划插入的前置任务一定晚于被依赖的任务创建。
   按创建顺序渲染，计划读起来就是乱的。渲染做拓扑排序，创建顺序保留在
   `Plan.tasks` 里供历史查阅。
