# ADR-0009: 会话持久化边界与 HITL 语义

- 状态：已接受
- 日期：2026-11-21

## 背景

Topic 08 交付了基础会话（`SessionContext`），但它只在内存里——进程退出即丢。
一个「学习教练」需要跨天、跨进程地陪伴学习者，因此会话必须能持久化、能恢复。

Topic 09 提出的工程问题是：**Session 的持久化边界在哪里？Pause / Resume 时
哪些状态必须落盘，才能保证中断后可精确恢复？**

同时要解决 Human-in-the-Loop：某些工具（删除、转账、外发）不能由模型直接
执行，必须先经人批准。

参考实现 `ai-agent-from-scratch` 的 Ch6 快照给出了基本形态：`Session` +
`BaseSessionManager` + `PendingToolCall` + `ToolConfirmation`，运行遇到
`requires_confirmation` 的工具时把 `status` 置为 `pending_confirmation` 并返回。

但参考实现在三处与本项目的约束冲突，本项目必须做出不同的选择。

## 决策

**会话状态只有一份权威存储；落盘的是「恢复一个运行所需的全部状态」；人工
批准是运行时的约束，且缺失批准按拒绝处理。**

### 1. 存储只能有一个权威

参考实现的**书本 Listing 6.11** 让 `ExecutionContext.add_event` 把事件写进
`session.events`（有 session 时），而它自己的 `_prepare_llm_request` 读的是
`context.events`。两处不一致，**结果是多轮会话里模型完全看不到历史**：

```
Listing 6.11 写法：
  ctx.events 条数    : 0
  session.events 条数: 1
  发给模型的内容      : []      ← 历史全丢了
```

本项目不接受「会话一份、执行上下文一份」的双存储。`SessionContext` 持有
**一个** `ExecutionContext`，事件只有一份，`contents` 展平的就是它。恢复、
持久化、审计读的都是同一份数据——不存在「两份对不上」的可能。

这是 Day 08「存储与呈现分离」在会话层的延续：**分离的是呈现与存储，不是把
存储拆成两份。**

### 2. 持久化边界

**必须落盘**（缺一项，恢复出来的就不是原来那个运行）：

| 项 | 缺了会怎样 |
|---|---|
| 事件历史 | 模型看不到之前的对话——多轮直接失效 |
| 草稿本 `state` | 工具的中间状态丢失 |
| 用量与成本 | 账目对不上；成本预算失效 |
| `current_step` | 恢复后从头再来，浪费预算 |
| `tool_call_count` | **暂停-恢复可以绕过工具调用数上限** |
| `consecutive_errors` / `call_counts` | **暂停-恢复可以绕过停止条件** |
| 待确认的审批 | 暂停的运行恢复不了 |
| 创建与更新时刻 | 无法回答「这个会话是什么时候的」 |

**不必落盘**：`AgentStep`（逐步明细）。它是单次运行的观测数据；完整过程在
事件历史里。恢复后的 `AgentResult.steps` 覆盖的是**本次运行段落**，这一点在
文档里写明。

### 3. 循环计数住在上下文里

原实现把 `total_tool_calls`、`consecutive_errors`、`call_counts` 放在循环的
局部变量里。那意味着**恢复一次运行就会重置它们**——暂停-恢复成了绕过预算与
停止条件的后门。

因此这三个计数上移到 `ExecutionContext`。它们本来就是运行状态，住在状态容器
里才自洽。

### 4. 整步暂停

一步里模型可能请求多个工具。规则是：**要么全执行，要么全暂停**。

部分执行会让转录里出现「有调用没结果」的断裂——主流厂商 API 会**拒绝整个
请求**，不是降级。整步暂停保证转录在每一个时刻都自洽。

### 5. 没有批准就拒绝（fail closed）

待确认的调用如果没有对应的批准决定，**按拒绝处理**。

缺少批准就执行，等于让「批准」变成默认开启——那就不是批准机制了。OWASP 的
*AI Agent Security Cheat Sheet* 对工具授权中间件的要求也是 "Fail closed for
unknown tools or missing approval requirements"，并要求「检查并消费批准」是
**原子**的一步，防止并发或重放复用同一次批准。

本项目目前的实现是单进程内的，不存在并发复用批准的问题；但「缺失即拒绝」
这条规则先立住，将来换成有并发或多进程的存储时不必重新设计语义。

### 6. 批准是运行时的约束，模型无法绕过

`requires_confirmation` 声明在 `ToolDefinition` 上——工具的静态契约，序列化
后随会话一起落盘。检查点在运行时（`_pending_approvals`），不在模型侧。

模型只能「请求」，不能「批准」。这与 ADR-0007 的权限检查是同一条原则：
**检查点在唯一的执行边界上。**

### 7. 拒绝的理由回填给模型

被拒绝的调用会生成一条失败的工具结果，内容是「用户拒绝执行该工具（理由）。
不要再尝试这个操作，请改用其它方式回答」。

理由回填有两个作用：模型知道为什么做不成；以及**「不要再尝试」**这句话防止
模型换个说法反复重试同一个被拒的操作。

## 后果

- 好处：会话可跨进程恢复；暂停-恢复不能绕过预算与停止条件；转录在每个时刻
  都自洽；批准语义明确且默认安全；持久化边界有清单可核。
- 代价：`ExecutionContext` 变大了（多了计数与待审批）；恢复需要显式调用
  `resume()`；落盘格式与运行时类型耦合（新增字段要同步 `SessionState`）。
- 边界：**没有并发控制**。两个进程同时恢复同一个会话会互相覆盖。生产用需要
  乐观锁或租约。
- 边界：**没有多租户隔离**。`user_id` 只是记录，没有据此做访问控制。
- 边界：**没有审批过期机制**。一条几天前的待批准调用恢复时仍然有效。
- 边界：**`AgentStep` 不落盘**，恢复后的 `steps` 只覆盖本次运行段落。
- 边界：**恢复时整体超时重新计时**。暂停期间的人工作时长不计入运行超时——
  否则人下班了运行就超时了，这显然不对；但这意味着超时不是「端到端」的。

## 补充说明（2026-11-21）

实现中确认的事实：

1. **恢复路径必须自己记账**。初版 `_resolve_approvals` 执行了工具但没更新
   `tool_call_count`，于是「暂停 → 恢复」不消耗任何工具调用预算——一个可以
   无限循环的后门。现在待确认的调用（含被拒绝的）在恢复时同样计数。
2. **被拒绝的调用也要计数**。否则「反复请求-反复被拒」不消耗预算。计数的
   含义因此是「请求数」而不是「成功数」——与普通路径保持一致。
3. **变异的「没被捕获」有时是变异本身没生效**。第一次做变异验证时，去掉
   「暂停的运行不能再 run()」的守卫后，测试**全部通过**——原因是变异脚本的
   替换文本与格式化后的实际代码不匹配，变异根本没发生。给替换加断言之后，
   变异才真正生效——而且暴露出那个测试是**因为错误的原因**通过的（脚本耗尽
   抛的是 AssertionError，不是 AgentError）。加固后它才真的钉住了这条性质。
4. **多轮历史丢失是可以在几行代码里复现的**。Listing 6.11 的不一致不需要跑
   完整 Agent 就能验证：建一个 session、add_event 一次、然后按
   `_prepare_llm_request` 的方式展平 `context.events`——结果是空的。这类缺陷
   在没有真实多轮会话的测试里不会暴露。
