# ADR-0032: 重排、查询改写与多路召回——研究过了，现在不做

- 状态：已接受
- 日期：2026-11-27

## 背景

两处遗留都指向同一个问题：**检索的下一层要不要做**。

- Day 29 遗留：「重排 / 查询改写 / 多路召回要不要做（ADR-0011 说先不做）」——
  那时是**推迟**，不是**研究过**；
- Plan.md 的 Day 30 清单里有一条「**研究 Reranking**」——**这是 Day 27–30 唯一
  没有兑现的计划项**（其余 38 项都已交付）。

所以这篇 ADR 做两件事：**把研究做掉**，并给出**带判据的决策**——不是「以后再说」，
而是「什么条件下才做」。

## 研究结论

### 1. 机制：双编码器（bi-encoder）的信息瓶颈

双编码器把「切片」与「查询」分别编码成向量再算余弦。**切片的那一个向量，必须同时
服务将来会问它的所有问题**——它编码的是「这块大致讲什么」，而不是「它能回答哪类
问题」。于是**标题与主题相近的切片，往往排在「字面上不含查询词、但确实答得上」的
切片前面**。

交叉编码器（cross-encoder）把查询与切片拼在一起做联合注意力，能问「这段文字能回答
这个具体问题吗」。**这就是重排存在的全部理由**。

### 2. 成本：交叉编码器是「每个候选一次前向」

| 方案 | 每个候选的代价 | 量级 |
| ---- | -------------- | ---- |
| 双编码器 + ANN | 一次索引查询 | 1M 切片约 1 ms |
| 交叉编码器（MiniLM-L6） | 一次前向 | 20 个候选约 130 ms；1M 切片暴力要 1.7 小时 |
| LLM 重排（pointwise） | 一次串行调用 | 8.6 s / 查询，约 $2.18 / 1k 查询 |
| LLM 重排（listwise） | 一次调用 | 1.6 s / 查询，约 $2.75 / 1k 查询 |

**代价是线性的、可预期的**——这正是「漏斗」存在的理由：第一段买**召回**（答案活下来
了吗），第二段买**排序**（它在最前面吗）。

### 3. 价值取决于输入的噪声——而本项目的输入噪声最低

实测里最有说服力的一条：**用「照着文档写出来的问题」评估时，重排几乎是白做的**——
第一段已经 0.943 nDCG，MiniLM 只加 0.013 还**掉了召回**；换成「真实用户会怎么问」
的模糊问法，第一段掉 4.4 个点，重排器才把大部分找回来。

**结论：重排的价值与输入噪声成正比。** 而本项目现在的检索输入是：

- 语料是一个学习者的课程库（几千片以内）；
- 查询**全部是人工合成的**，且大多照着材料写；
- 默认的嵌入器是**占位哈希嵌入**（按词重叠打分）。

**这三条恰好是「重排价值最低」的组合**：输入噪声低、嵌入器本身就弱。**在占位嵌入器
上谈重排，是拿一个玩具的排序问题当真问题。**

### 4. 重排可能把事情做得更差

实测里 `jina-reranker-v1-tiny` 把模糊问法的 nDCG 从 0.899 降到 **0.876**——**比不
重排还差**。「加个重排」不是安全默认值，它是一个**必须在自家数据上量过的模型选择**。

另一条相关实证：22 种方法、40 个变体的横向比较显示，**LLM 重排在「熟悉」的查询上
更强，但对训练截止之后才出现的新查询泛化不稳**；轻量模型在效率上相当。本项目现在
**一条真实查询都没有**，全是「没见过的查询」。

### 5. 重排修不了「表示不对」

实测里最能说明问题的一条：某条查询的正确切片排在第 15 位，**四个重排器全都让它更
靠后**（19、24、24、26）——因为切片里根本没有查询词，联合注意力无 attend 可 attend。
真正管用的是**在摄取时给切片前置一句上下文说明**（「这份文档列出的是它用的数据库、
消息队列、集群与机器人传输」）：**排名 15 → 2，而且管道里根本没有重排**。

**这与本项目 Day 30 的发现是同一件事**：评估暴露的问题是「切细之后碎片互相竞争
top_k 名额」——那不是排序问题，是**索引与名额**问题；修法是**按来源去重**，效果是
召回 0.77 → 1.00。**改索引比重排序管用。**

## 决策

**现在不做重排、查询改写与多路召回。** 但不是「以后再说」，而是**写明判据**。

### 为什么现在不做

1. **没有真实查询**——重排的价值与输入噪声成正比，而我们的输入是人工合成的；
2. **占位嵌入器是瓶颈**——重排救不了嵌入，重排的前提是「候选集里有正确答案」；
3. **延迟与成本**——LLM 重排 1.6–8.6 秒 / 查询，与「即时教学」的体感直接冲突；
   交叉编码器要引入外部模型依赖，**破坏「默认套件离线可跑」这条底线**；
4. **多路召回没有可融合的东西**——本项目只有一路向量检索，RRF / 多查询生成是给
   「多路召回」用的，没有第二路就无从融合；查询改写则要 LLM（延迟 + 成本）；
5. **证据指向别处**——本项目自己的评估显示问题在切分与名额，不在排序。

### 什么时候重估（判据要可测）

**同时**满足下面三条，才重新评估：

1. 有**真实学习者查询**（至少数十条，来自真实提问，而不是照着文档写的）；
2. 有**真正的嵌入模型**（不是占位哈希嵌入器）；
3. 评估显示**召回够了但排序差**——具体是：`hit@5` 高，而 `MRR` / 找全率明显低。

第 3 条是关键的：**如果召回也低，那问题在索引与切分，不在排序**——先去修索引。

### 真要做的话，从哪里开始

1. **先做便宜的**：**摄取时的上下文增强**（给每块前置一句「它讲什么」）。实测里
   它比任何重排都有效，且本项目的摄取流水线已经有位置；不需要外部模型也可以先做
   模板版；
2. **再考虑轻量交叉编码器**（不是 LLM 重排）：离线评估用，候选深度取 **recall 曲线
   的拐点**而不是上限（实测里 N=20 是拐点，N=50 只多花 200ms 而质量不动）；
3. **每一步都要在自己的数据上量**——重排器可能让结果更差，这是实测出来的。

## 后果

- 好处：Day 30 计划项「研究 Reranking」**兑现**；「重排 / 查询改写 / 多路召回要不要
  做」从「推迟」变成「有判据的决策」；**上下文增强**被识别为一个低成本、可能高收益
  的候选；本项目的检索管道保持简单（嵌入 → 检索 → 按来源去重 → 呈现）。
- 代价：**排序质量暂时不提升**——若真实查询到来后发现排序确实是瓶颈，要补一段管道。
- 代价：**默认套件仍然拿不到真实质量结论**——占位嵌入器下的任何排序结论都不作数。
- 风险：**「不做」被当成「不用管」**——判据写在这里，重估时点由它决定，不由心情决定。
- 边界：**上下文增强还没做**（本 ADR 只把它记为候选，没实现）；**真实查询与真嵌入**
  待有；**LLM 重排的判官用法**（离线评估）另议（ADR-0014 的「判官不可当门禁」仍然成立）。
