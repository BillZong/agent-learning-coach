# ADR-0030: 检索过滤、top-k 与阈值的归属、索引方案的选择

- 状态：已接受
- 日期：2026-11-26

## 背景

Day 29（Phase 2 · AI Tutor）的工程问题是：**pgvector 的索引方案如何选择？检索的
top-k 与相似度阈值应该由谁决定？**

Phase 0–1 已有的相关零件：

- `core.rag.store`（Day 11）：`VectorStore` 协议、`InMemoryVectorStore`、
  `PgVectorStore`（HNSW 索引 + 余弦距离）；过滤下推到 SQL；
- `core.rag.retrieval`（Day 11）：`VectorRetriever`——刻意很薄，只有「嵌入 → 检索」；
- `core.rag.embedding`（Day 11）：`EmbeddingClient` 协议 + `HashingEmbedder`（占位）
  + `OpenAICompatibleEmbedder`；
- 课程文档与切分（ADR-0028/0029）：切片带着 `kind` / `course_id` / `point_ids`
  三样元数据。

Plan.md 的 Day 29 清单：阅读 Embedding 官方文档 / 阅读 pgvector 文档 / 研究向量
相似度检索 / 实现 Embedding Adapter / 实现 Vector Store / 实现 Vector Retrieval /
实现 Metadata Filtering / 编写 Retrieval Tests / 交付 Vector Retrieval Module。

## 决策

**过滤语义由值的类型决定；top-k 与阈值由应用层决定；索引方案是部署决策（配置项）。**

### 1. 一个具体的坑：过滤语义由值的类型决定

Day 27 把知识点关联写进元数据时，`point_ids` 是一个**数组**。而原来的过滤只会
**等值匹配**：

- 内存实现：`metadata.get(key) == value`——拿数组和字符串比，**永远不等**；
- pgvector：`metadata ->> %s = %s`——`->>` 对数组取出的是数组的**文本**
  （`["k1"]`），与 `'k1'` 不等，**同样匹配不上**。

也就是说：**「教 k1 时检索相关材料」这个最核心的用法，原来的过滤根本做不到。**

修正后的语义：

| 过滤值 | 语义 | 实现 |
| ------ | ---- | ---- |
| 标量 | **等于** | 内存：`==`；SQL：`metadata ->> %s = %s` |
| 序列 | **包含任一** | 内存：`any(item in actual ...)`；SQL：`metadata -> %s ?| %s` |

序列语义取「包含任一」而不是「包含全部」——与 SQL 的 `IN (...)` 一致，也是最常用的
意思（「教 k1 或 k2 时」）。

**已知缺口**：没有「取反」（排除某类材料）与「同时包含」（all-of）。两者都需要更
丰富的过滤表达式，先不做（ADR-0017 的「一致性问题先报告，不假装能做」）。

### 2. top-k 与阈值由**应用层**决定

两者都是**业务判断**：

- **top-k**：「讲一个知识点」要 3 份材料，「总结整章」要 10 份；
- **相似度阈值**：「低于 0.3 分就不算相关」——这是「宁可少给也不给不相关的」这条
  产品判断。

因此它们由**应用层**（``core.application.retrieval.MaterialQuery``）决定，存储层与
检索层**只执行**：它们提供默认值，但**默认值不是决策**。

新增的应用层用例 ``MaterialSearch`` 把学习领域的说法翻译成检索层的条件：

```
「教 k1、c1 课」→ {"point_ids": ["k1"], "course_id": "c1"}
```

### 3. 阈值下推到 SQL

`min_score` 在存储层执行（`WHERE 1 - (embedding <=> %s) >= %s`），而不是取回后
在 Python 里筛——与「过滤下推到存储层」是同一条原则：少传数据、少占内存。

**ANN 索引 + 过滤的坑**：过滤发生在索引扫描**之后**，因此带过滤的查询**可能返回少于
top_k 条**——被过滤掉的结果不占名额。需要更多召回时调大 `hnsw.ef_search`。

### 4. 索引方案是**部署决策**，不是代码常量

| 方案 | 什么时候用 |
| ---- | ---------- |
| `none` | **语料小**（几千片以内）：顺序扫描的召回是 100%，ANN 的近似误差与调参不值得 |
| `hnsw` | **默认**：写入友好、召回高、内存换速度；语料变大时的通用选择 |
| `ivfflat` | 写入极少、只读查询、内存紧张；代价是需要定期 `REINDEX` |

**本项目的语料是一个学习者的课程库——几千片以内，精确扫描就够**，ANN 索引带来的是
近似误差（会漏掉真正相关的切片）与调参负担。但索引方案**仍然是配置项**：
写死一个方案，等于把部署决策塞进代码。

**召回是近似的**：ANN 索引会漏。语料小的时候这个代价不值得付。

### 5. 验证

**SQL 与适配器都在真实 PostgreSQL 18 + pgvector 上验证过**（不是靠读代码推断）：

- 标量过滤、序列过滤（`?|`）、阈值、过滤 + 阈值同时生效——逐条确认；
- **占位符顺序**是最容易出错的地方（SELECT 向量 → WHERE 过滤值 → 阈值向量 →
  ORDER BY 向量 → LIMIT），因此有专门的集成测试。

集成测试**默认跳过**（需要 `AGLC_TEST_DSN` 指向带 pgvector 的库）——**默认的测试套件
不依赖数据库**。

## 后果

- 好处：「教 k1 时检索相关材料」终于能做；top-k 与阈值的归属明确；索引方案可按
  部署调整；SQL 路径有真实验证。
- 代价：过滤语义**由值的类型隐式决定**——同一个 `filters` 字典，值是列表和值是标量
  语义不同。调用方要知道自己传的是什么类型。
- 代价：**没有取反与 all-of**。排除某类材料（「不要只讲别的点的段落」）现在做不到。
- 代价：**ANN 索引 + 过滤可能少返回**，需要调 `ef_search`——这是 pgvector 的固有
  性质，不是本项目的 bug。
- 风险：**没有「排除」语义**。将来若需要，得把过滤表达式升级成 richer 类型（按
  key / 值 / 模式）。
- 风险：**阈值依赖嵌入质量**。占位的 `HashingEmbedder` 产生的分数分布没有意义，
  阈值在它上面只是形式；换成真嵌入后阈值才可用。
- 边界：**重排、查询改写、多路召回**明确不做（ADR-0011 §检索为什么保持很薄）；
  **向量库选型**已定为 pgvector（架构 §5）；**驱动选型**仍未定（本主题只在本地装了
  `psycopg` 验证，未进 `pyproject`）。

## 补充说明（2026-11-26）

实现中确认的事实：

1. **过滤语义由值的类型决定，而不是调用方约定。** 「point_ids 含 k1」是数组，
   「course_id = c1」是标量——同一个 `filters` 字典里两种语义，靠类型区分最省事，
   也最难忘。**已知缺口**是取反与 all-of：两者都要更丰富的过滤表达式，先不做。
2. **在应用层过滤等于把全部向量拉回内存再筛。** 这是「索引 ≠ 检索」最常见的误用，
   所以过滤必须下推到 SQL——而**下推之后语义才暴露**：`->>` 对数组取出的是数组的
   **文本**，与 `'k1'` 不等。**内存实现「看起来对」的等值匹配，在数据库里是错的。**
3. **ANN 索引 + 过滤会少返回。** 过滤发生在索引扫描之后，被过滤掉的结果不占名额。
   要更多召回得调大 `hnsw.ef_search`——这是 pgvector 的固有性质，不是 bug。
4. **top-k 与阈值是业务判断，不该由存储层默认。** 「讲一个知识点要几份材料」「低于
   多少分就不算相关」都是产品判断；存储层提供默认值，但**默认值不是决策**。
5. **索引方案是部署决策。** 本项目的语料（一个学习者的课程库）小到精确扫描就够——
   ANN 索引带来近似误差与调参负担。但它**仍然是配置项**：写死一个方案等于把部署
   决策塞进代码。
6. **SQL 路径必须真跑一遍。** 占位符顺序（SELECT 向量 → WHERE 过滤值 → 阈值向量 →
   ORDER BY 向量 → LIMIT）是最容易错的地方，而读代码看不出来。本地起了一个带
   pgvector 的 PostgreSQL 逐条验证，并留了**默认跳过**的集成测试（需要
   `AGLC_TEST_DSN`）。
