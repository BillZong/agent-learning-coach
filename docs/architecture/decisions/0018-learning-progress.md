# ADR-0018: 学习进度——知识点级的状态、归属与派生查询

- 状态：已接受
- 日期：2026-11-24

## 背景

Topic 18 的工程问题是：**Learner Profile 与 Learning Progress 的区别是什么？
进度应与知识点绑定，还是与计划任务绑定？**

Plan.md 的 Day 18 还要求「区分 Learner State 与 Agent Task State」。

Topic 15～17 已经建好了三个东西，但它们都没有回答「学习者学到哪了」：

| 已有模型 | 回答什么 | 不回答什么 |
| -------- | -------- | ---------- |
| `Learner` | 学习者是谁（背景、偏好） | 学到了哪 |
| `LearningGoal` | 想达成什么（结果、约束、绑定哪些知识点） | 实际达成到哪 |
| `KnowledgeStructure` | 知识点之间怎么依赖 | 每个知识点各自的掌握状态 |

Plan.md 还列了「定义目标时间范围、定义每日投入时间、定义目标能力要求」——这些
在 Topic 17 已经落地（`TimeWindow` / `DailyEffort` / `CapabilityRequirement`）。

两个前提已经确定：

1. **知识点身份是课程内的**（ADR-0016）。跨课程知识地图留给 Topic 22。
2. **运行时与领域层单向解耦**（ADR-0013、ADR-0015）。运行时不认识学习领域，
   领域层不认识运行时。

Phase 1 没有主教材章节，进度建模由本项目自己定。

## 决策

**进度是（学习者 × 课程）的关联聚合，按知识点组织；学习状态是与任务状态
分开的第二套状态机；已有知识用「迁移序列的第一条」表达；与前置的关系是
派生查询，不是存储状态。**

### 1. 画像与进度的区别：归属与变化频率

| | `Learner`（画像） | `LearningProgress`（进度） |
| --- | --- | --- |
| 回答 | 学习者**是谁** | 学习者**学到了哪** |
| 归属 | 学习者自己 | 学习者 × 课程 |
| 变化频率 | 低（改名、换偏好） | 高（每次学习活动） |
| 内容 | 身份、背景、偏好 | 每个知识点的学习状态 |

因此**进度不进 `Learner`**：否则每学一个知识点就要改一次学习者，而且同一
学习者的多个目标会互相污染。这与 ADR-0015「Learner 不持有目标列表」是同一条
论证——**变化频率不同的两类事实，不放在同一个聚合里**。

### 2. 进度按（学习者 × 课程）分片，不按目标分片

知识点身份是**课程内**的（ADR-0016），知识状态（Knowledge Space Theory）也是
学习者在一个知识空间上的状态子集。若按目标分片，同一门课的知识点状态会在
多个目标间重复——**同一事实存两份**，与 ADR-0015 的双写论证同一个病。

因此：

- `LearningProgress` 的身份是 `(learner_id, course_id)` 这一对，**不需要额外
  的进度标识**；
- **目标的完成度是派生查询**（`goal_completion`），不是存储字段；
- 一个目标被放弃后重新建立（新 `GoalId`），进度仍然是同一份——学习过的事实
  不因为目标换了而消失。

### 3. 进度绑知识点，不绑计划任务

这是本主题的核心问题。四条理由：

1. **任务身份不稳定，知识点身份稳定。** 计划任务会被跳过、内容不可改写
   （ADR-0013：「要换说法就新建任务并跳过旧的」）、重规划后可以整条重建。绑定
   到任务上，重规划一次进度就丢一次。而知识点是领域的稳定身份。
2. **「掌握了吗」不由「哪些步骤做完了」回答。** 一个知识点可能由多个任务覆盖
   （讲解 + 练习 + 复习），一个任务也可能覆盖多个知识点。两者的粒度不对齐。
3. **任务状态是执行视角，知识点状态是认知视角。** 任务完成只说明这一步做完
   了，不说明学习者掌握了那个概念。
4. **前置关系只在知识点层存在。** ADR-0016 的 `prerequisite_closure` 回答
   「这一点没掌握，先补哪些」——归因的第一层依据。如果进度绑任务，这个闭包
   就接不上。

结论：进度按知识点组织，**不引用任务 id**。计划任务的状态由运行时持有，两者
之间没有领域层的耦合。

### 4. 学习状态是与任务状态分开的第二套状态机

```python
LearningState = Literal["not_started", "in_progress", "learned"]
```

与运行时的 `TaskStatus`（`pending` / `in_progress` / `blocked` / `completed` /
`skipped`）逐项对照：

| | `TaskStatus` | `LearningState` |
| --- | --- | --- |
| 描述 | 一次执行的**一个步骤** | 学习者对**一个概念**的认知 |
| 归属 | 运行时（`core.agent`） | 领域（`core.learning`） |
| 跳过 | 可以 `skipped`（不做这一步） | **没有「跳过」**——跳过只是不执行那个步骤，知识点状态不变 |
| 受阻 | 可以 `blocked`（缺外部条件） | **没有「受阻」状态**——被阻塞是**派生结果**：前置还没学会 |
| 终态 | `skipped` 是唯一终态 | 无终态（可以复习） |

两条「没有」是刻意的：

- **知识点没有「跳过」。** 「跳过一个知识点」要么是不学（`not_started`），要么
  是不再学（停在 `in_progress`），没有第三种。任务可以跳过是因为任务本来就是
  「一次可丢弃的执行尝试」。
- **知识点没有「受阻」状态。** 前置没学会是**结构事实**，不是知识点自己的
  状态。把它存成状态，就要在每次前置变化时同步更新所有下游点——双写。存成
  派生查询（`blocked_points`），它就永远和当前进度一致。

**状态由迁移历史派生**（与 ADR-0017 的目标状态机同一个原则）：`PointProgress`
不存 `state` 字段，而是从 `transitions` 派生，「状态说一套、历史说另一套」在
类型上无法表达。

### 5. 每条迁移边只有一个操作语义

| 迁移 | 操作 | 含义 |
| ---- | ---- | ---- |
| `not_started → in_progress` | `start()` | 开始学 |
| `not_started → learned` | `assess()` | **诊断判定已有基础** |
| `in_progress → learned` | `complete()` | 学完并验证 |
| `learned → in_progress` | `review()` | 复习（Topic 52 会用它排复习） |

`review()` 与 `start()` 都指向「学习中」，但前提不同——没学过的是开始学，学过
的是复习。实现中第一版允许 `review()` 从 `not_started` 出发，测试发现这会让
「复习」和「开始学」在历史里无法区分，于是改成**每个操作校验自己的来源
状态**。

刻意**不允许** `in_progress → not_started`：放弃一次学习只是不再推进它，状态
停在「学习中」即可；回退会让「学过没有」变得不可判定。

### 6. 已有知识用「迁移序列的第一条」表达

ADR-0015 把「掌握度 / 已有知识」明确留给 Topic 18 与 Topic 20。本主题的
答案是：**不需要额外的「已有知识」概念**。

诊断判定「学习者本来就会这个知识点」，就是该点的**第一条迁移**
（`not_started → learned`），并带 `source_kind="assessed"`。于是：

- 「本来就会」与「本次学会」在迁移序列里区分得开；
- 已有知识与新学到的知识落在**同一份数据**里，不存在两处记录；
- 掌握程度的**量化**（概率、等级）不在本模块——那属于掌握度模型（Topic 43）。

### 7. 与前置的关系是派生查询

三个跨聚合查询，都不存状态：

| 查询 | 回答 |
| ---- | ---- |
| `goal_completion(progress, goal)` | 目标要求几个点，学会几个（**结构性完成度**，不是「目标是否达成」） |
| `ready_points(progress, structure)` | 现在可以开始学哪些点 |
| `blocked_points(progress, structure)` | 哪些点还动不了（前置没学会） |

两个关于知识点的查询遍历的是**知识结构的全部知识点**，不是进度里已记录过的
那些——没记录过的点同样是「没学过」，而且它们往往正是「接下来该学哪个」的
答案。

`goal_completion` 需要同时看到进度与目标，因此是**模块级函数**而不是方法
（与 ADR-0017 的 `check_goal_against_course` 同一形状）。它拒绝比较不同课程的
进度与目标。

### 8. 前置封闭性是跨聚合一致性检查

Knowledge Space Theory 的「知识状态对先修封闭」性质（ADR-0016 已引用）：掌握
了 `p` 就应当已经掌握 `p` 的全部先修。

这条**不是构造期校验**，而是跨聚合检查（`check_progress_against_course`）——
进度是逐次更新的，一次更新看不到全部先修。检查三件事：课程一致、知识点存在、
**已学会的点的直接前置也必须已学会**。

### 9. 进度不进运行时的 `GoalSpec`

`GoalSpec`（ADR-0013 §10）是领域无关的运行时契约，**不扩展**。进度是领域侧的
观测事实，不是规划输入。规划器需要「接下来学什么」时，由应用层用
`ready_points` 计算后再组装，不通过契约传递。

## 后果

- 好处：进度有了明确归属与粒度；「哪些点没掌握」「现在该学哪个」「哪些还
  动不了」都有确定答案；已有知识与新学到的知识在一份数据里；学习状态与任务
  状态各司其职，不会把「跳过一个任务」误当成「掌握了一个知识点」。
- 代价：**新增一个聚合**（`LearningProgress`）与第二套状态机。Phase 1 现在有
  四个聚合：Learner、Course、LearningGoal、LearningProgress。
- 代价：**进度按课程分片，目标按（学习者 × 课程）分片**——同一门课的两个目标
  共享一份进度。这是对的（知识点状态是事实），但意味着「这个目标完成了多少」
  只能在查询时算，不能按目标分别存储历史。
- 风险：**「每个知识点一个状态」在知识点很多时会很大**。一个 200 个知识点的
  课程，进度对象会随每次学习活动重建。当前没有持久化，重建成本可接受；接数据
  库后需要考虑按点增量更新（这要求放弃不可变实体，或改用事件流）。
- 风险：**状态只有三档，没有「部分掌握」**。「学了一半」与「完全没学」在进度里
  都是 `in_progress`。区分它们需要掌握度模型（Topic 43）。
- 边界：复习调度（Topic 52）、诊断策略（Topic 20）、掌握度量化（Topic 43）、
  持久化都未建模。

## 补充说明（2026-11-24）

实现中确认的事实：

1. **每条迁移边只能有一个操作语义**：第一版让 `review()` 和 `start()` 都允许
   从 `not_started` 出发，测试立刻暴露出「复习」与「开始学」在迁移历史里无法
   区分。改成每个操作校验自己的来源状态后，错误信息也能指出该用哪个操作
   （"只有已学会的知识点才能复习；没学过的请用开始学习"）。
2. **派生查询要遍历全结构，不能只遍历已记录的**：第一版 `ready_points` 只看
   `progress.points`，结果「现在可以学什么」的答案是空的——而没记录过的点正是
   最该被推荐的点。
3. **「阻塞」要先排除已学会的点**：某个点的前置没学会不代表它被阻塞——它自己
   可能已经学会了（学过之后前置的复习到期，不影响「这个点我会不会」）。
4. **进度按课程分片比按目标分片更省事实**：第一版按 `goal_id` 分片，实现时
   立刻遇到同一个知识点在两个目标里要记两次的问题——这就是 ADR-0015 反对的
   双写。
5. **不引入额外的进度标识**：`(learner_id, course_id)` 这一对已经唯一，加一个
   `ProgressId` 只是多一个需要保持一致的东西。

## 补充说明（2026-11-25，Topic 20）

Topic 20 补上了本 ADR 留给它的「诊断策略」一侧。本 ADR 的进度模型不变，两处
接口得到兑现：

1. **`assess()` 的判定侧**：诊断判定「学习者本来就会这个知识点」，由应用层调用
   `assess()` 写成 `not_started → learned` 的迁移，来源标记 `assessed`。**衔接是
   应用层的动作，不是领域的自动同步**——诊断与进度是两个聚合，「一次事务只改一个
   聚合」（ADR-0015）。因此本项目**不提供**「诊断自动同步进度」的函数
   （ADR-0020）。
2. **「已有知识」有了具体的表达**：诊断的判定是**三态**（`known` / `gap` /
   `unknown`），「会」与「不会」必须带依据（`basis`）与理由（`reason`）。本 ADR
   说的「看迁移序列就能区分本来就会与本次学会」，其判定来源现在有了具体的载体
   ——诊断记录。

本 ADR §6 提到的「掌握度量化」仍未建模（Topic 43），「薄弱点判定」也未建模
（Topic 45）：诊断给的是离散判定，不是掌握程度。

同时，本 ADR 的 `LearningProgress` 分片方式（学习者 × 课程）在本主题得到一次
印证：诊断是**按目标**组织的活动（一次诊断针对一个目标），而进度是**按课程**
组织的状态；两者不是同一件事，因此也不该合并。
