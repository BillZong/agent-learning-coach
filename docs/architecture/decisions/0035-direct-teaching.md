# ADR-0035: 直接教学模式——结构化输出、worked example 与渐进式支持

- 状态：已接受
- 日期：2026-11-27

## 背景

Day 33（Phase 2 · AI Tutor）的工程问题是：**教学内容怎么生成？解释、示例与渐进式
讲解怎么做？**

Phase 2 的零件到 Day 32 已经齐了：上下文装配（Day 32 ✓）、引用与门禁（Day 31 ✓）、
检索与引用（Day 29–30 ✓）。缺的是**教学这一层**——模型拿到上下文之后，怎么讲。

Plan.md 的清单：Direct Teaching Prompt、结构化教学输出、知识点讲解、示例生成、
验证 RAG Citation、Teaching Evaluation Cases。

## 研究

### 1. Worked example effect：分步示范 > 让自己试错

Sweller & Cooper（1985）起的经典结论：**给学习者看完整的分步示范，比让他自己
解题学得更多**——学习同样的内容，用示范组的耗时少近六倍、错误更少 ✓✓。

机制是**认知负荷**：自己试错时，学习者的注意力花在「试错策略」上（「 plug-and-chug
——找一个表面特征相似的题」），而不是花在原理上 ✓。**分步示范让注意力回到原理** ✓。

**对本项目的直接含义**：示例必须是**分步的**（问题 → 步骤 → 结果），不是一段成品
代码 ✓。

### 2. 三个坑（caveats）——它们决定指令怎么写

MIT Teaching + Learning Lab 总结的三条：

| 坑 | 后果 | 对策 |
| -- | ---- | ---- |
| **被动阅读** | 效果被抵消（学习者不会主动自我解释） | 每个示例配**引导问题**（self-explanation）✓✓ |
| **只记表面** | 记住的是表面特征，不是结构 | 多个示例**表面不同、核心相同** ✓ |
| **不会独立做** | 学完不会自己做 | **渐隐支持**（faded support）：逐步撤掉支持 ✓ |

Hattie（2009）的元分析：让学习者**主动**研究示范时，worked example 的效果接近翻倍
✓——**引导问题不是装饰** ✓。

### 3. 新手与熟练者要不同的支持（expertise reversal）

Kalyuga & Renkl（2010）：**已经掌握的人看示范反而学得少**——对熟练者应该给练习
而不是继续给示范 ✓。

**对本项目的含义**：支持的强度要**随学习者水平变**——这正是 Day 32 的上下文里
「画像」的作用 ✓✓（上下文里的 profile 段有了用武之地 ✓）。

### 4. 错误示例也值得展示

Booth et al.（2013）：**同时展示正确与错误的示例**，让学习者指出错例错在哪，比只给
正确示例更有效 ✓。

**对本项目的含义**：指令要求「指出一个常见错误」 ✓——这是很多教学提示会漏掉的一步。

## 决策

### 1. 教学模式只决定**指令**

Day 33（直接教学）与 Day 34（苏格拉底式）**共用**装配、引用与门禁——差别只在**指令**
✓。因此：

- 指令按模式取（`instructions_for(mode)` ✓）；
- **不认识的模式要报错**——静默退回直接教学会让「模式」变成假的 ✓；
- **苏格拉底式在 Day 34 之前要明确报错**，不假装有（`instructions_for(SOCRATIC)`
  抛错 ✓）。

### 2. 结构化输出：讲解 / 分步示例 / 引用声明 / 下一步

```python
class TeachingOutput(BaseModel):
    explanation: str  # 讲解本身——要能独立成立
    examples: list[TeachingExample]  # 分步 + 引导问题
    citations: list[str]  # 声明引用了哪些标记
    follow_up: str  # 下一步的引导问题
```

**结构化而不是自由文本**：下游要能分别处理「讲解」「示例」「引用」（Day 31 的门禁要
查引用 ✓；Phase 3 的评估要读讲解 ✓）✓。

### 3. 门禁查**两处**引用：正文里的标记 + `citations` 字段的声明

**声明也是承诺**——模型说「我用了 [1]」，而 [1] 不存在，与正文里写一个不存在的
标记是一回事 ✓✓。因此声明的标记要一起进门禁 ✓（把它渲染成标记的样子再校验 ✓）。

**这是实现时才发现的漏洞**：第一版只校验正文，模型在 `citations` 里声明一个不存在的
标记能溜过去 ✓。

### 4. 教学评估量的是**机制**，不是教学质量

`core.application.teaching` 的评估部分 + `evals/teaching.json`（8 条场景用例）：

| 指标 | 量什么 |
| ---- | ------ |
| 讲解 / 示例 / 下一步的比例 | 结构齐不齐 |
| **示例带引导问题的比例** | 被动阅读的坑有没有踩 ✓ |
| 引用声明的比例、编造率 | 有没有依据 |
| 过门禁的比例 | 支撑判定 |

**明确不做**：不量「讲得好不好」——那要人评（Phase 3 另议）✓。

**评估集是人工合成的、模型是脚本化的**——所以它量的是**管道通不通**，不是教学质量
✓。这个限制写在模块 docstring 与示例输出里 ✓。

### 5. 引用门禁接在最后

`DirectTeacher.teach` 的顺序：**装配上下文 → 调模型（结构化输出）→ 门禁 → 打包** ✓。
被门禁拦下时**不给原文**（Day 31 的决定 ✓）——教学文本同样适用 ✓。

## 后果

- 好处：教学有**结构**（下游可分别处理 ✓）；指令的每一段都**对应一条研究结论**
  （改指令时知道在动什么 ✓）；门禁覆盖两处引用 ✓；教学第一次有量 ✓。
- 代价：**指令是硬编码的一段文字**——换教学风格要改代码 ✓（可配置，但那是过早设计 ✓）。
- 代价：**渐进式支持只落在指令里**（"按学习者水平调整"），**没有机制保证**——模型
  未必照做；真正的机制要靠 Phase 3 的练习（难度分级 ✓）。
- 风险：**「示例带引导问题」的比例可能很高但没意义**——模型可以机械地加一个问句 ✓。
  指标量的是**形式**，不是**效果** ✓。
- 边界：**教学质量不量**（要人评 ✓）；**苏格拉底式不做**（Day 34 ✓）；**真实模型下的
  表现没测过**（脚本化模型只证明管道通 ✓）。

## 补充说明（2026-11-27）

实现中确认的事实：

1. **门禁有个漏洞：只看正文不看声明**。模型在 `citations` 字段里声明 `[9]`，正文里
   没有 `[9]`——第一版的门禁看不见它 ✓✓。**声明也是承诺**，两处都要查 ✓。
2. **评估集能逮到真问题**：脚本化模型对每条用例都声明 `[1]」，而「不需要材料」的
   那条用例没有可用引用 → 编造率 0.12、过门禁 0.88 ✓✓——**管道确实在工作** ✓。
3. **Mock 客户端能驱动结构化输出**：`MockLLMClient(text=json.dumps(...))` 走
   `generate_structured` ✓——默认套件不依赖外部服务 ✓。
