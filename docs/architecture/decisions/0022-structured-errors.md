# ADR-0022: 结构化错误——原始错误是事实依据，摘要是理解入口

- 状态：已接受
- 日期：2026-11-25

## 背景

Topic 21 实现过程中暴露了一个设计问题：**模型输出的结构化校验失败后，错误信息
该怎么传递？**

第一版（ADR-0021）的做法是**压缩**：把 pydantic 的 `exc.errors()` 压成一句
「字段：原因」，回喂给模型重试。实现时踩到两个坑：

1. pydantic 的错误列表是 **Python 字面量**（单引号、元组），不是 JSON——
   `json.loads` 直接失败，得用 `ast.literal_eval` 反解。
2. 压缩前的原始错误**已经丢了**：`core/llm/structured.py` 在抛异常前把它
   字符串化进了异常消息，下游再从字符串里反解回结构。

第 2 点是真正的问题：**事实被降级成文本，又花力气解析回来**。而且
`ast.literal_eval` 反解出来的是「曾经被字符串化的东西」，不是原始条目——
厂商的上下文、输入值、错误码在第一手就已经被丢了一部分。

更根本的是**压缩被当成了终点**。压缩是为「模型需要看什么」服务的视图；它不该
消灭「排查问题的人需要看什么」。

## 决策

**原始错误作为事实依据保留在异常里；结构化摘要是给 Agent 的理解入口；细节按
当前任务选择性提供。**

### 1. 三层信息，各司其职

| 层 | 内容 | 消费者 |
| -- | ---- | ------ |
| **原始条目**（`FieldError.raw`） | 厂商的原始错误字典：错误码、字段位置、输入值、文档链接 | 排查问题的人、日志、未来的判官 |
| **归一化字段**（`FieldError.loc` / `type` / `msg`） | 跨厂商稳定的形状 | 程序逻辑、摘要渲染 |
| **摘要**（`FieldError.summary()`） | 「字段：原因」一行 | **模型**（重试反馈）、普通日志 |

**三层都要有。** 只留归一化字段会丢掉定位细节（厂商的 input 值往往就是问题
所在）；只留原始条目则每次消费都要自己解析厂商格式，换厂商就散落一地。

### 2. 摘要与细节是同一份事实的两种视图

```python
FieldError.summary()  # 'weak_points：Field required'
FieldError.detail()  # 'weak_points：Field required（原始：{...}）'
```

`LLMParseError` 暴露两个属性：

- `.summary`：字段级摘要连成一行——**给模型**；
- `.detail`：摘要 + 原始条目——**给排查问题的人**。

异常消息本身是第三种视图：给**调用方**看的（"模型输出不符合 X 结构：N 处校验
失败"）。

### 3. 原始错误在抛出点就被保留

`parse_structured_output` 捕获 `ValidationError` 时，把 `exc.errors()` 的每一项
**原样**放进 `FieldError.raw`，同时归一化出 `loc` / `type` / `msg`：

```python
FieldError(
    loc=("expected_answer",),
    type="missing",
    msg="Field required",
    raw={"type": "missing", "loc": ("expected_answer",), "msg": "Field required", ...},
)
```

因此**下游不再需要解析字符串**——`ast.literal_eval` 那个 hack 被删掉了。它本来
就是「事实被降级成文本」的症状，而不是一个独立的 bug。

### 4. 按当前任务选择细节

消费方自己决定要多细：

| 场景 | 用哪一档 | 理由 |
| ---- | -------- | ---- |
| 重试反馈给模型 | `.summary` | 模型要的是「哪个字段、为什么」，错误码与输入值是噪声 |
| 异常消息给调用方 | 异常消息 | 足够定位，不必刷屏 |
| 排查具体故障 | `.detail` / `ExerciseGenerationError.detail` | 需要厂商上下文与输入值 |
| 未来的题目质量判官（Topic 44） | `.raw` | 需要可比较的结构化字段 |

**这不是「压缩 vs 完整」的二选一，而是同一份事实的按需视图。** 摘要可以随时从
原始条目重新生成；反过来不行——原始条目丢了就永远丢了。

### 5. 领域层的失败也有 detail

`ExerciseGenerationError` 同样带 `detail`：领域层校验失败时，`detail` 就是
`DomainError` 的完整消息。规则统一：**摘要与细节并存**，而不是「摘要替代细节」。

### 6. 边界放在 `core/llm`，不在 `core/learning`

`FieldError` 是**模型抽象层**的概念：任何用结构化输出的地方（记忆抽取、题目
生成、未来的判官）都受益于「原始错误被保留」。把它放在 `core/llm/errors.py`，
`core/learning` 只负责**选用哪一档**。

这与 ADR-0021 的分层一致：`core/llm` 定义厂商无关的错误形状，
`core/learning` 做业务判断。

## 后果

- 好处：原始错误不再丢失；下游不需要解析字符串（`ast.literal_eval` 的 hack
  被删）；同一份事实有多个视图，模型与人各取所需；`core/llm` 的所有消费者
  （记忆抽取等）都受益。
- 代价：**`LLMParseError` 的构造签名变了**（新增关键字参数 `field_errors`）。
  旧调用方（只有 `structured.py` 一处）已迁移；`memory/extraction.py` 只是捕获
  类型、不读消息，不受影响。
- 代价：**异常消息不再包含具体字段**（只说「N 处校验失败」）。这是有意的——
  具体字段由 `.summary` / `.detail` 提供。若有人只 `print(exc)`，看到的信息变少
  了；这是可接受的取舍，因为**程序应当读结构化属性，而不是解析消息文本**。
- 风险：**`raw` 里可能含敏感内容**（例如模型的输出里带了用户数据）。原样保留
  意味着它会进日志。本项目当前无脱敏机制（ADR-0014 的 Trace 有记录需求），
  暂记为未决问题。
- 边界：**判官与质量评估**（Topic 44）还没做；那时 `.raw` 的结构化字段才有
  第二个消费者。

## 补充说明（2026-11-25）

实现中确认的事实：

1. **「压缩成一句话并完全替代」丢掉的是排查能力。** 第一版实现时，我在
   `core/llm/structured.py` 把 `exc.errors()` 字符串化进异常消息，下游再用
   `ast.literal_eval` 反解——**事实被降级成文本，又花力气解析回来**。那个 hack
   不是独立的 bug，是症状。
2. **摘要是视图，不是替代品。** 正确的关系是：原始条目是事实，摘要是从事实
   渲染出的视图。摘要是可以随时重新生成的；原始条目丢了就永远丢了。
3. **「按当前任务选择」需要两档而不是一档。** 一档（只有摘要）让人排查不了；
   一档（只有原始）会让模型收到一堆噪声。模型要「哪个字段、为什么」，人要
   「厂商上下文与输入值」——两者都需要，且不冲突。
4. **原始条目是跨厂商的事实。** pydantic 的 `loc` / `type` / `msg` 在换厂商后会
   变，但「哪个字段错了、错在哪类」不会。归一化层就是为这个存在的。
5. **异常消息不该是唯一的信息通道。** 第一版把具体字段塞进异常消息，等于让
   程序去解析消息文本。现在消息只说结论，结构化事实走 `.field_errors` 属性。
