# ADR-0024: 学习计划——粒度、范围与时间约束

- 状态：已接受
- 日期：2026-11-25

## 背景

Topic 23 的工程问题是：**Learning Plan Generator 的输入输出契约是什么？计划
任务粒度如何与知识点对齐？**

Phase 1 到 Topic 22 已经把「学什么」建好了：目标绑定知识点（ADR-0017）、知识
结构给出先修依赖（ADR-0016）、进度记录掌握状态（ADR-0018）、诊断给出判定
（ADR-0020、ADR-0023）。但**「按什么顺序、每天花多久」**一直没有答案——目标是
一份能力要求清单，不是日程。

`bridge.py` 里留了一个明确的问题等着本主题回答：

> 「计划任务粒度如何与知识点对齐」是 Topic 23（Learning Planning）要回答的问题，
> 那里再决定运行时契约是否需要扩展。

Plan.md 的 Day 23 清单：研究 Learning Planning / 研究 Planning 与 Dependency
Graph / 阅读 Agent Planning 资料 / 定义 Learning Plan / 定义 Learning Unit /
实现基础 Plan Generator / 实现知识依赖顺序 / 实现时间约束 / 编写 Planner Tests /
交付 Learning Plan Generator。

Phase 1 已有的相关零件：

- `KnowledgeStructure.order()`（ADR-0016）：`requires` 的拓扑序，并列按声明顺序；
- `KnowledgeStructure.prerequisite_closure()`：传递前置，按学习顺序——**补课
  顺序**，此前没有消费者；
- `LearningProgress`（ADR-0018）：知识点级的掌握状态；
- `LearningGoal.time_window` / `daily_effort`（ADR-0017）：时间范围与每日投入；
- `LearningGoal.requirements`（ADR-0017）：目标绑定哪些知识点；
- 运行时的计划（ADR-0013 §10）：`GoalSpec` → `PlanDraft` → `Plan`，带状态机与
  历史，是**执行层**的计划。

## 决策

**单元与知识点一一对应；范围由「目标 + 进度」决定；顺序遵守依赖；排不下要报告
而不是少排；运行时契约不扩展。**

### 1. 单元粒度：一个单元 = 一个知识点

`LearningUnit` 有 `point_id`、标题、理由、支撑的结果、估时、依赖、排期日。

**它没有独立 id**——知识点就是它的身份。

理由：掌握度进度（ADR-0018）、诊断判定（ADR-0020）、知识依赖（ADR-0016）**都
以知识点为单位**。如果计划单元不对齐到知识点，完成一个单元之后回写进度就要再
做一次映射，而那次映射没有权威来源（哪些任务算掌握了 k1？）。**粒度不对齐，进
度就写不回去。**

替代方案（一个单元覆盖多个知识点 / 一个知识点拆成多个单元）都被否掉：前者无法
回写进度，后者把「掌握一个点」拆成需要跨单元对齐的事实，且实践环节（练习、
复习）还属于后续主题（Topic 44、Topic 52）。

### 2. 范围：目标要求 ∪ 前置闭包 − 已学会

```
计划范围 = (目标要求的知识点 ∪ 它们的前置闭包) − 已经学会的知识点
```

**带上前置闭包**：目标要求 k3，而 k3 依赖 k2、k2 依赖 k1——不学会 k1、k2就学
不了 k3。不带闭包的计划是**执行不了**的。带上前置不扩大目标（掌握 k3 本来就意
味着会 k1、k2），但它让每个单元能说清「它为什么在计划里」。

**减去已学会的**：已经会的点不需要再排一次时间。

**目标的前置（`goal.prerequisites`）不进范围，只被报告**。这是两种不同的东西：
课程里的 `requires` 是**知识点之间的学习依赖**（「要学这个得先学那个」）；目标
的前置是**学习者层面的前提条件**（「开始这个目标前必须已经会」）。前者是学习内
容，后者是另一个目标的内容。补前置属于另一个目标，因此只报告
（`unmet_prerequisites`）——与 ADR-0017 第三档一致。

### 3. 范围由「目标 + 进度」决定，不由诊断决定

诊断是**判断**而不是事实。ADR-0020 已定「诊断到进度的衔接是应用层的动作」——
领域层不替应用层在两份事实之间选边。因此计划范围只由目标（要什么）与进度
（已经会什么）决定；诊断只用来写清每个单元的**理由**：

| 单元来源 | 理由 |
| -------- | ---- |
| 诊断判定为缺口 | 「诊断判定为缺口：……」 |
| 目标要求掌握 | 「目标要求掌握它以支撑：……」 |
| 只是别人的前置 | 「它是 k2 的前置」 |

理由按信息量排序：诊断结论 > 目标要求 > 结构位置。三者都比「因为它在范围里」有
用——「为什么先学这个」必须能回答。

**应用层应先按 ADR-0020 把诊断同步进进度，再生成计划**。领域层不挑边，也不
报告两份事实的矛盾（那是同步那一层的责任）。

### 4. 顺序：依赖是硬约束

计划顺序 = `structure.order()`（拓扑序，并列按声明顺序）限制到计划范围内。

过滤一个拓扑序仍得到拓扑序，因此**前置一定排在后继之前**。这不是一个「尽量好」
的启发式——它是硬约束：知识点之间有先修依赖（ADR-0016），跳过一处会让后面全
部塌掉（ADR-0023 选严格汇总时用的就是这条理由）。

`depends_on` 只含**计划内**的前置：已经学会的前置已被满足，不构成计划内的依赖。
`LearningPlan` 在构造期校验两件事——依赖必须在计划内、后继不得排在前置之前。

### 5. 时间：装箱 + 报告超载

**排期**：贪心装箱——当前天放得下就放，放不下就开新天。因此每天都不超过每日投
入，除非单个单元本身就超过它（那天 `is_overloaded` 为真）。

**没有约定每日投入时不排期**（`day` 为 `None`，`days` 为空）。硬排一个「第 0
天装下全部内容」是假精度——它看起来像有日程，其实没有。

**装不下要报告，不能少排**。超载时（需要的天数 > 时间范围内的天数）：

- 计划**仍然包含全部单元**；
- 给出 `PlanOverload`（总量、需要几天、有几天、超出几天）；
- 标出哪些天已超出期限（`DailyLoad.within_window`）。

理由与 ADR-0023 的严格汇总是同一条：**悄悄丢掉内容会让「要补的地方」凭空消
失**。丢掉单元和宽松汇总犯的是同一个错——让计划跳过真正没学会的知识点。超载是
一个需要人来决定的事实（加时间、延期限、砍范围），领域层**报告**，不替应用层
决定（ADR-0017 第三档）。

### 6. 估时可替换

`EffortEstimator` 协议 + `UniformEffort` 默认实现（每个点 30 分钟）。

领域层定义「需要估什么」，不规定「怎么估」——与 ADR-0023 的 `Grader`、ADR-0002
的 `LLMClient` 是同一个做法。默认的 30 分钟**没有实证依据**，它只是让「每天能
学多少」有个起点；真实估时应来自学习数据（Topic 46）。

### 7. 运行时契约不扩展

`bridge.to_unit_goal_spec(unit, goal)` 把一个学习单元映射成 `GoalSpec`。

**知识点 id 不进入 `GoalSpec`**：把知识点塞进运行时契约会让运行时开始认识学习
领域的概念，破坏 ADR-0013 §10 的分层。应用层要做的是：取出当前要学的那个单
元，映射成 `GoalSpec`，交给运行时拆成任务。

**两个「计划」不是一回事**：

| | 学习计划（领域） | 运行时计划（`core.agent`） |
| --- | --- | --- |
| 回答 | 接下来学哪些知识点、每天多久 | 当前这一步要做什么任务 |
| 粒度 | 知识点 | 任务 |
| 生命周期 | 派生，无状态 | 有状态机与历史 |
| 消费方 | 应用层 / 展示 | Agent 运行时 |

### 8. 计划是值对象

`LearningPlan` 是**派生**的：给定目标、知识结构与进度就能算出来，因此没有独立身
份，也不自己维护状态。计划的**版本与历史**属于 Topic 24。

## 后果

- 好处：单元与知识点对齐，进度可以逐单元回写；依赖顺序由不变量强制；时间装不
  下被如实报告而不是悄悄少排；换估时器不改领域模型；运行时契约不用动。
- 代价：**计划不含内容**。单元只有标题、理由、估时——「这个单元具体怎么学」要
  由应用层或模型补上（Phase 2 的 AI Tutor）。这是刻意的：领域层给**结构**，内容
  由生成层给（同 ADR-0021 的题目生成）。
- 代价：**估时是占位值**。30 分钟没有实证依据，会让排期看起来精确而实际不准。
- 代价：**每天的负载是「总量」，不是「学什么」**。同一天可能排了三个单元，但没
  说它们的先后——单元之间的先后由依赖决定，与「第几天」无关。
- 风险：**严格的前置闭包可能带进大量内容**。一条长链会让计划比目标本身大很
  多。这符合「掌握 k3 本来就意味着会 k1、k2」，但当课程结构过细时体验会差。
- 风险：**排期是贪心的，不是最优的**。装箱没有考虑「哪一天放哪个点更划算」——
  但每天的容量上限相同，贪心即最优（等价的单位换时间装进等容量的箱子）。
- 风险：**计划与诊断可能不同步**。诊断说会、进度说没学会的点仍会进计划。领域层
  不选边（见 §3），因此这是应用层同步责任的直接后果。
- 边界：计划的**版本与持久化**属于 Topic 24；**复习安排**属于 Topic 52；**练习
  与评估**属于 Phase 3；**能力估计（连续掌握度）**属于 Topic 43。

## 补充说明（2026-11-25）

实现中确认的事实：

1. **粒度不是审美问题，是回写问题。** 「一个单元一个知识点」看起来朴素，但它是
   「完成单元 → 更新进度」能成立的前提。粒度一旦不对齐，后面每一次进度回写都
   要先猜「这个单元算掌握了哪个点」。
2. **前置闭包此前没有消费者。** ADR-0016 定义的 `prerequisite_closure()` 是
   「补课顺序」原语，但一直没有服务用它。本主题是它的第一个消费者——**原语要先
   有领域问题，才会有正确的形状**。
3. **`requires` 的方向容易搞反。** 关系是「source 必须先掌握 target」，也就是
   source 的前置是 target。写测试时把方向写反，计划里就只剩目标点本身——**依赖
   方向错了，前置闭包会静默地空掉**，不报错。
4. **目标的前置与课程的前置不是一回事。** 前者是「开始这个目标前必须已经会」，
   是前提条件；后者是「要学这个得先学那个」，是学习内容。把两者混为一谈，要么
   让计划跑偏（把前提当内容学），要么让前提永远不被检查。
5. **「没有每日投入就不排期」比硬排更诚实。** 排一个「第 0 天装下全部内容」的
   计划看起来完整，但它给出的信息量是零。
6. **超载报告的价值在于它不替代决定。** 领域层算出「超出 1 天」，但加时间、延期
   限、砍范围三个选择各有代价——那是应用层与用户的事。**报告事实，不替人决定**
   （ADR-0017 第三档）。
7. **同一条规则第六次拦住了我**：不变量必须在构造期拦。`LearningPlan` 的两条
   不变量（依赖必须在计划内、后继不得排在前置之前）在构造期就挡住了自相矛盾的
   计划——**写测试时又一次被它拦下**。
