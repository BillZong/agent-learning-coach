# ADR-0021: 诊断题生成——两层校验、拦截与重试

- 状态：已接受
- 日期：2026-11-25

## 背景

Topic 21 的工程问题是：**生成的诊断题如何做结构化校验？无效题目应该在生成层
拦截，还是在评估层兜底？**

这是 Phase 1 第一次让 **LLM 进入学习领域**。ADR-0020 已经建好了诊断的判定与
准入，但**题目从哪来**一直空着——那需要模型。

Plan.md 的 Day 21 清单：实现诊断题生成 / 题目 Schema Validation / 题目难度
字段 / 题目持久化 / 建立诊断题测试集 / 交付 Diagnostic Exercise Generator。

两个前提已经确定：

1. **依赖方向**：`core.learning` 不认识模型、工具与运行时（ADR-0015 §6）。领域
   模型文件不 import `core.agent`；映射只在 `bridge.to_goal_spec` 里发生。
2. **结构化输出**已有基础设施：`core/llm/structured.py` 提供「提示词约束 +
   严格 JSON 解析」的统一回退路径（ADR-0002）。

Phase 1 没有主教材章节，生成与校验的取舍由本项目自己定。

## 决策

**无效题目在生成层拦截；校验分结构层与领域层；重试把失败原因回喂给模型；不合格
的题目不外流，模型调用失败不重试。**

### 1. 在生成层拦截，不在评估层兜底

三条理由：

1. **一道坏题会污染判定。** 题目若与目标知识点无关，学习者答错时，我们分不清
   是「他不会」还是「题问偏了」——判定因此不可信。坏题必须挡住，不能流到学习者
   面前。
2. **生成层是唯一能修的地方。** 无效输出在生成层可以要求模型重来；到了评估层，
   题目已经呈现给学习者，只能事后解释。**问题在能修的地方修。**
3. **兜底是最后防线，不是主要防线。** 评估层仍要校验（题目可能来自存储、导入或
   历史数据），但那是**防御性检查**，不是正常路径。ADR-0012 的同一条原则：校验
   不能被绕过。

因此：**生成层是主要防线，评估层是防御性兜底。** 这与 ADR-0020「领域层只报告、
不替调用方决定」一致。

### 2. 两层校验，各管各的

| 层 | 校验什么 | 失败怎么办 |
| -- | -------- | ---------- |
| **结构层**（`ExerciseSchema`） | 字段齐全、类型正确、长度合理 | 带反馈重试 |
| **领域层**（`DiagnosticExercise` 构造） | 题目针对目标知识点、难度符合要求 | 带反馈重试 |

- **结构层是「模型有没有按格式回答」**：字段缺失、类型错、题面太短。它用
  pydantic 模型表达（`core/llm/structured.py` 已有解析路径），失败抛
  `LLMParseError`。
- **领域层是「这个回答在业务上成不成立」**：难度与要求不符、题目跑题。它是
  `DiagnosticExercise` 的构造期校验，失败抛 `DomainError`。

**两层不合并**：结构层可以被别的生成器复用（任何「让模型按 schema 回答」的场景
都用得上），领域层只属于学习领域。合并会让结构校验带着业务语义，反之亦然。

### 3. 题目补齐三个字段

Topic 20 的 `DiagnosticExercise` 只有题面。Topic 21 补上：

| 字段 | 为什么必须有 |
| ---- | ------------ |
| `expected_answer` | 没有可判定的标准答案，题目只是一段文字——ADR-0020 的判定要靠它 |
| `difficulty` | 同一知识点可出不同难度的题；难度是**题目**的属性，不是知识点的（ADR-0017 已决定难度不建模为目标约束） |
| `rationale` | 让题目可被审阅：「为什么用这道题考这个点」有答案，而不是只能相信它 |

难度取值（`basic` / `intermediate` / `advanced`）放在**领域模型**里而不是生成器里：
难度是题目自身的属性，任何来源的题目都受同一套约束——包括从存储里读出来的历史题目。

### 4. 带反馈重试

不合格时把**失败原因**回喂给模型再试一次：

```
上一次生成的题目不合格：题目难度为基础，与要求的进阶不符
请重新生成，确保题面针对目标知识点、难度符合要求……
```

模型能看见自己错在哪，重试才有意义。只说「失败了」等于没给信息。

**重试次数有限**（`max_attempts`，默认 2）：重试不是无限的——题目一直不合格时
继续重试只是浪费额度。耗尽后抛 `ExerciseGenerationError`。

### 5. 两种失败要分开：题目不合格 ≠ 调用失败

| 失败 | 处理 | 理由 |
| ---- | ---- | ---- |
| **题目不合格**（结构层/领域层） | 带反馈重试 | 换一次输出可能就对了 |
| **调用失败**（超时、限流、服务端错误） | **直接上抛，不重试** | 重试不会让超时变好；这是传输问题，交给调用方按自己的策略处理 |

把它们混成「都重试」会让一次限流变成 N 次限流，把配额耗光。

### 6. 不合格的题目不外流

`ExerciseGenerator.generate()` 只有两种结局：返回**合格**的题目，或抛错。**没有
「返回一道题但质量存疑」的第三种可能。**

因为坏题一旦交出去，下游（诊断流程、判定）就没有理由再怀疑它——判定会把它当成
依据。**在源头拦住，是唯一可靠的位置。**

### 7. 生成器不认识诊断流程

`ExerciseGenerator` 只接收「要考哪个知识点、要什么难度」，产出
`DiagnosticExercise`。它**不判断**：

- 这次诊断够不够驱动计划生成（ADR-0020 的准入条件）；
- 学习者会不会（那是判定的事）。

请求里**刻意不含学习者信息**：诊断题考的是知识点，不是针对某个人的定制题——
定制属 Topic 22 的诊断策略。

### 8. 生成器住在 `core.learning` 里

`core/learning/generation.py` import `core.llm`。这**看起来**违反 ADR-0015 的
「core.learning 不认识模型」，但那条规则的实际内容是：

> 领域模型文件不 import `core.agent`；映射只在 `bridge.to_goal_spec` 里发生。

规则针对的是**领域模型文件**（`domain.py` / `goal.py` / `progress.py` /
`diagnosis.py`），它们仍然一个模型都不认识。`generation.py` 是**生成适配器**，
与 `bridge.py` 是同一类东西——领域与外部世界之间的窄接口。它依赖 `core.llm` 的
**协议**（`LLMClient`），不依赖任何厂商。

这个区分要靠**文件边界**而不是包边界来保证，因此 ADR-0017 的三档保证边界同样
适用：

| 判断 | 落在哪里 |
| ---- | -------- |
| 题目在业务上成不成立 | 领域层（`DiagnosticExercise` 构造期） |
| 模型输出在结构上合不合法 | 结构层（`ExerciseSchema`） |
| 模型能不能调用、要不要重试 | 生成适配器（`generation.py`） |
| 这次诊断够不够驱动计划 | 领域服务（ADR-0020 的准入条件） |

## 后果

- 好处：坏题在源头被挡住，不会污染判定；不合格题目不外流；重试带反馈，模型能
  自我修正；题目带参考答案与出题理由，判定有依据、可审阅；结构层可被其他生成
  场景复用。
- 代价：**`core.learning` 出现了对 `core.llm` 的依赖**。缓解办法是文件边界——
  领域模型文件仍然不认识模型，且这条规则由本 ADR 与 ADR-0017 的三档边界共同
  保证。
- 代价：**题目与知识点的关联检查是弱检查**。`_addresses_point` 靠「题面或理由里
  出现知识点实词」判断，挡得住完全跑题，挡不住「相关但角度偏了」。后者需要更
  强的判断（模型打分或人工审阅），留给 Topic 22。
- 代价：**题目持久化未实现**。Plan.md 列了它，但 ADR-0019 已决定仓储层留待后续
  （不可变实体与迁移历史的存储形态尚未决策）。本主题只交付生成与校验。
- 风险：**重试会放大模型调用量**。`max_attempts` 默认 2，即最坏情况调用两次。
  额度控制属于应用层（与 ADR-0013 的重规划预算同理）。
- 风险：**题面长度下限（8 字符）是启发式的**。它挡得住「闭包？」，挡不住
  「解释一下闭包」这种同样没信息量的问法。真正的质量判断需要内容评审。
- 边界：题目持久化、诊断结果到知识点的映射与降级（Topic 22）、题目质量评估
  （Topic 44）都未建模。

## 补充说明（2026-11-25）

实现中确认的事实：

1. **pydantic 的错误列表是 Python 字面量，不是 JSON。** 直接 `json.loads` 解析
   失败——单引号与元组都是 Python 语法。必须用 `ast.literal_eval`。这个坑在实现
   时真实踩到：结构层拒绝的原因原样回喂给模型时，是一长串带 `ctx`/`url`/`input`
   的字典，模型既看不懂也用不上。
2. **失败信息要压成一句人话再回喂。** 模型需要知道的是「哪个字段不合法」，不是
   完整的校验上下文。`expected_answer：Field required` 比一整段 pydantic 报错有用
   得多。
3. **「题目不合格」与「调用失败」必须分开。** 实现时第一版用 `except Exception`
   一把抓，结果模型超时时也会重试——重试不会让超时变好，只是把一次限流放大成
   N 次限流。现在只对 `LLMParseError` 与 `DomainError` 重试，其余上抛。
4. **题目跑题的检查只能是弱检查。** 「题面或出题理由里出现知识点实词」挡得住
   完全跑题，挡不住角度偏了。强判断要模型打分或人工审阅——那是 Topic 22 与 44
   的事。这里明确写下这个局限，比假装检查很可靠要好。
5. **难度属于题目，不属于知识点**（也不要放回目标上）。同一个知识点出基础题与
   高难题是正常的；难度是**这道题**的属性。ADR-0017 已决定难度不建模为目标
   约束，本主题把它放在题目上，两处不冲突。
