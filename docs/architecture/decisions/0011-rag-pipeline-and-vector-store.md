# ADR-0011: RAG 流水线与向量存储选型

- 状态：已接受
- 日期：2026-11-23

## 背景

学习教练要能回答「按我的教材，闭包到底是什么」。教材是外部材料（Markdown、
PDF、网页），不可能塞进系统提示词——那是 RAG 要解决的问题。

主教材 Ch5 5.1～5.3 给了完整路径：5.1「用内部数据的问题」、5.2「搜索方法的
类型」（关键词 / 向量 / 图 / 结构化）、5.3「实践向量搜索」（嵌入 → 切分 →
向量检索）。参考实现 `ai-agent-from-scratch` 的 Ch5 快照提供了可核对的代码形态：
OpenAI embeddings + 定长切分 + `cosine_similarity` + `argsort` 取 top-k。

但主教材的 5.3 是**教学用的最小实现**，直接照搬到生产会有几个问题：

- 嵌入绑定 OpenAI，离线跑不了、CI 跑不了、测试无从下手。
- 定长切分会**截断语义单元**——一句话被切成两半，两半都检索不到完整的意思。
- 检索就是纯向量 top-k，**没有元数据过滤**，也没有把过滤下推到存储层。
- 全量向量在内存里算相似度——语料一大就不可行。

Topic 11 的工程问题：**Chunking 策略如何影响检索质量？Document Loader 到
Vector Retrieval 这条流水线中，哪一环最先失效？**

## 决策

**流水线分成四段，每段都是协议；两种存储与两种嵌入各备一套实现，生产路径与
离线路径行为一致。**

### 1. 四段流水线，接口都是协议

```
DocumentLoader → Chunker → EmbeddingClient → VectorStore
   读成文档        切成检索单元    变成向量        存下来
                                     ↓
                              VectorRetriever
                              （嵌入 → 检索）
```

`VectorRetriever` **刻意很薄**——只有「嵌入 → 检索」两步。没有重排、没有查询
改写、没有多路召回。每加一层就多一个「哪一层先失效」的排查对象；基础检索先
跑对，再谈优化。

### 2. 文档与切片是两种类型

检索命中的是**切片**，但切片必须能回溯到它的来源。混成一个类型的后果是：重新
切分时无法判断「这条记录是旧切法还是新切法」，也无法在检索结果里指回出处。

### 3. 文档 id 由来源推导

同样的文件每次摄取要得到同样的 id，否则重新摄取会产生「同一份材料的两份
记录」，而向量库里无法区分。id 由**来源路径**的哈希推导，不是随机 UUID。

### 4. 两种切分器，默认用递归的

- `FixedSizeChunker`：定长（主教材 5.3.2 的做法）。简单、可预测，适合结构
  不明的文本（如网页抓取结果）。
- `RecursiveChunker`：先按段落切，段落太大再按句子切，句子还太大再按字符切，
  最后合并成不超过上限的块。

**递归切分不截断自然段**——这是它存在的全部理由，测试里直接观察到两者差别。

**切片大小按字符，不按 token。** 按 token 更精确，但会让切分器依赖分词器——
而切分器不该知道用的是哪种模型。token 预算由呈现层负责（ADR-0008）：切得太碎
只是多占一点检索空间，切得太大才是检索质量问题。

### 5. 嵌入是协议：离线实现 + 生产实现

- `HashingEmbedder`：**确定性、离线、零依赖**。词袋 + 带符号的哈希投影。
  **它不是语义嵌入**——同义词可能匹配不上。它的价值是让整条流水线可离线跑通：
  测试、示例、CI 都不需要外部服务。**它是占位级的**，生产环境要换成真正的语义
  嵌入模型。
- `OpenAICompatibleEmbedder`：调用任何 OpenAI 兼容的 `/embeddings` 接口
  （OpenAI、Azure OpenAI、以及兼容该协议的其它服务）。用 `httpx` 的
  `MockTransport` 可以**离线测试**——生产路径本身也是可验证的。

哈希用 SHA-256 而不是 Python 内置 `hash()`：后者每个进程的随机种子不同，会让
「同样的文本得到同样的向量」这条性质失效。

### 6. 向量存储是协议：内存实现 + pgvector 实现

- `InMemoryVectorStore`：numpy 算余弦相似度。测试与演示用，不需要外部服务，
  检索结果完全确定。
- `PgVectorStore`：PostgreSQL + pgvector，向量列用 `vector` 类型，HNSW 索引，
  检索用 `<=>`（余弦距离）算子。

**统一对外暴露相似度（越大越相关）**：pgvector 的 `<=>` 返回的是**距离**
（越小越近），方向相反，实现负责换算。因此两种实现的**相对顺序一致**——
测试里直接验证这一点。

### 7. 过滤下推到存储层

检索器把元数据过滤条件原样传给存储，由数据库用索引筛。**在应用层过滤等于把
全部向量拉回内存再筛**——那是「索引 ≠ 检索」最常见的误用。LangChain 引用
Windsurf 的话：「Indexing code ≠ context retrieval」。

### 8. 无数据库时跳过，不伪造通过

pgvector 的测试在本地没有数据库时**跳过**并给出说明。伪造通过比不测更糟。

### 9. 每次操作开一条连接

`PgVectorStore` 每次操作开一条连接。这是有意的简化：本项目的规模（一个
学习者的课程材料）用不着连接池，而连接池会引入生命周期管理的问题。生产环境
应当换成 `psycopg_pool.AsyncConnectionPool`。

## 后果

- 好处：整条流水线可离线跑通、可测试；两种存储与两种嵌入可互换；切分策略的
  差别可被测试观察到；过滤下推到数据库；生产路径（OpenAI 兼容嵌入、pgvector）
  本身也有测试。
- 代价：切分器按字符不按 token，块大小与真实 token 数有偏差；`HashingEmbedder`
  只有词汇级相似度；`PgVectorStore` 每次操作开连接，不适合高并发。
- 边界：**只有向量检索，没有关键词检索**。纯向量检索在**精确标识符**上不如
  BM25（问「函数 `foo` 的定义」时，向量会召回一堆沾边内容，关键词会精确命中）。
  混合检索（向量 + BM25）通常优于任一单独方案——但本阶段还没有关键词检索，
  因此这是明确的缺口而不是设计选择。
- 边界：**没有重排**。取回的 top-k 直接交给模型，没有交叉编码器精排。
- 边界：**没有查询改写**。多轮对话里的指代（「那个函数的第二个参数」）不会被
  改写成可检索的形式。
- 边界：**没有增量更新**。文档改了要重新摄取整份文档。
- 边界：**加载器只支持纯文本与 Markdown**。PDF、Word 留给 Day 25「Document
  Ingestion」——那是学习领域侧的摄取工作，与检索基础设施是两件事。

## 补充说明（2026-11-23）

实现中确认的事实：

1. **ruff 抓到一个真 bug**：内存存储的检索里，列表推导引用了未定义的
   `vector`（本意是取 `self._vectors[chunk_id]`）。这类错误只在运行时暴露，
   而检索路径当时还没有测试覆盖。
2. **文档 id 与切片 id 都必须可复现**。文档 id 由来源哈希推导，切片 id 由
   「文档 id + 序号」推导——重新摄取不会产生重复记录，也不会让检索结果指向
   同一个内容的多个版本。
3. **`HashingEmbedder` 用了带符号的哈希投影**：不同词落到同一个桶时，随机
   符号让它们**相互抵消**而不是叠加。这是从随机投影（Johnson–Lindenstrauss）
   的标准做法借来的。
4. **`chromadb` 已在依赖里但本模块不用它**。它是早期从参考项目带过来的声明，
   而本项目的路线是 PostgreSQL + pgvector。保留它是因为后续 Topic 可能用到，
   但**本模块的向量存储不基于它**——不要以为 RAG 走的是 ChromaDB。
