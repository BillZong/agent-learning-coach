# ADR-0025: 计划版本——修订与全新计划、查询规则与生成依据

- 状态：已接受
- 日期：2026-11-25

## 背景

Topic 23 的工程问题是：**计划版本化后，如何表达「同一计划的修订」与「全新计
划」？查询接口应如何排序与过滤？**

Topic 23 交付的 `LearningPlan` 是**派生的值对象**：给定目标、知识结构与进度就
能算出来。它因此没有身份、没有历史——算两次得到两个相等的对象，但「这份计划
从第一次到现在改过什么、为什么改」无处可查。

Phase 1 的验收标准里有一条直接指向它：**「用户能够查询计划和计划版本」**。

Plan.md 的 Day 24 清单：研究版本化数据模型 / 研究计划变更记录 / 实现 Learning
Plan Version / 实现 Plan Query / 实现 Plan Update / 保存计划生成依据 / 实现
基础 API / 编写集成测试 / 交付 Learning Plan API / 完成 Week 4 Review。

Phase 1 已有的相关零件：

- `LearningPlan`（ADR-0024）：计划内容——单元、每天负载、超载报告；
- `LearningGoal.transitions`（ADR-0017）：目标的状态迁移历史——**活动留痕**的先
  例；
- `DiagnosisId`（ADR-0020）：**同一目标可以诊断多次，每次是独立的一条记录**——
  活动有独立身份的先例；
- ADR-0019：**仓储层留待后续**——因此本主题不给存储实现。

## 决策

**用 `PlanId` 区分「同一计划的修订」与「全新计划」；排序按版本号，不过按时间；
每一版都带依据、差异与理由。**

### 1. 版本是实体，计划内容是值对象

| 对象 | 身份 | 是什么 |
| ---- | ---- | ------ |
| `LearningPlan` | 无（按值相等） | 计划**内容**：单元、每天负载、超载 |
| `PlanVersion` | `PlanVersionId` | 一次**修订的记录**：内容快照 + 依据 + 差异 + 理由 |
| `PlanBasis` | 无 | 生成依据：目标、当时的进度、参考的诊断、结构指纹 |
| `PlanDelta` | 无 | 与上一版的差异：新增、移除、重排 |

内容保持为值对象，因此**两个版本的内容可以直接比较**——「这一版和上一版有没有
区别」是一个相等判断，而不是一段 diff 逻辑。

### 2. `PlanId` 区分「修订」与「全新计划」

- **修订**：同一 `PlanId` 下，版本号 +1。它是同一份计划的演进。
- **全新计划**：新的 `PlanId`，版本号从 1 开始。

**为什么必须有 `PlanId` 这一层**：少了它，「重新规划一次」既可以写成新版本、也可
以写成新计划，两种解释都能自圆其说——**无法判定的区分等于没有区分**。而且「重
新规划」有两种截然不同的含义：进度推进导致的重新生成（同一条线的下一个版
本），以及换了一条学习路径（新的一条线）。没有 `PlanId`，这两件事在数据里长
得一样。

它与 `DiagnosisId` 是同一条线索：**活动有独立身份**。同一个目标可以有多条诊断
记录，同一个目标也可以有多条计划线。

**目标不充当计划线**：一个目标可以先后有两条计划线（先按教材顺序，后来改成从
实践倒着学），它们都服务于同一个目标。

### 3. 排序按版本号，不按时间

- **同一计划线内**：按 `number` 升序。版本号是**领域分配的序号**。
- **跨计划线**：按该线**首个版本的时间**升序。

**为什么不让时间决定顺序**：`at` 由调用方传入，可能补录、乱序、录错。版本号
不会——它是领域在生成时分配的。如果排序依赖时间，「谁是当前版本」就变成了猜。

**跨线为什么只能用时间**：两条计划线之间没有共同序号。能比较的只有「哪条更
近」，而那只能用时间。

### 4. 「当前版本」的规则

| 查询 | 答案 |
| ---- | ---- |
| 指定 `plan_id` | 该线里 `number` 最大的版本 |
| 只指定 `goal_id` | 该目标**当前计划线**（首个版本时间最新的那条）里 `number` 最大的版本 |
| 都不指定 | 全部版本里 `at` 最新的 |

跨计划线时，「当前」= **最近开始的那条线**——不是「版本最多的那条线」，也不是
「最近改过的那条线」。最近改过的那条线可能是一条早就不用的旧线。

### 5. 每一版都带依据、差异与理由

**依据**（`PlanBasis`）记录的是**输入**，不是输出（输出在 `LearningPlan` 里）：

- 目标与它要求的知识点；
- **生成时已经学会的知识点**——同一个目标在不同时刻生成的计划是不同的版本，
  它们的区别正在于此；
- 参考的诊断（可空）；
- **课程知识结构的指纹**。

结构指纹让「课程结构变了之后，旧版本是否还成立」能看出来——否则只能靠猜。

**差异**（`PlanDelta`）只比三件事：有哪些知识点、排在第几天、估时多少。计划的
内容文字（标题、理由）不在差异里——它们是**解释**，不是排程。

**理由**必填。没有理由的版本变化无法解释——这与 `GoalTransition.reason`、
`PointTransition.reason` 是同一条要求。

### 6. 领域侧的基础 API，不做 HTTP

本主题交付的是**领域侧的基础 API**（纯函数）：`start_plan`（全新计划）、
`revise_plan`（修订）、`plan_versions`（查询）、`current_plan_version`（当前版
本）、`fingerprint_structure`。

**不做 HTTP API**：技术选型表里「API 框架」仍是 TBD，而仓储层按 ADR-0019 尚未
实现。在框架与存储都未定的情况下搭一层 HTTP 接口，等于把两处未定的选择固化
进代码。版本集合由调用方持有，存储是调用方的事——**这一层留给应用层**。

### 7. 首版没有差异

`PlanVersion.delta` 对首个版本必须是 `None`：没有上一版，就不存在差异。这条不
变量在构造期校验——**「与上一版的差异」在首版上是自相矛盾的**。

## 后果

- 好处：「修订」与「全新计划」在数据上可区分；「谁是当前版本」有确定答案；
  「这一版基于什么生成」「和上一版差在哪」都有记录；领域层不依赖存储与框架。
- 代价：**版本集合没有聚合根**。版本号唯一、序号连续这些约束靠调用方传入的集
  合来保证（`revise_plan` 会检查版本号重复，但「不能跳号」目前没人检查）。
- 代价：**结构指纹是内容哈希**，不承诺跨版本稳定（实现细节变了指纹就变）。它只
  用来回答「同一份结构算出来的是不是同一个指纹」，不承诺长期有效。
- 代价：**修订的理由由调用方给**。领域层校验它非空，但「理由是否贴切」它答不
  上来——这是应用层与用户的事。
- 风险：**计划线可能越开越多**。同一个目标反复「换路径」会留下一堆计划线，而查
  询只给得出「最近开始的那条」。清理策略（归档旧线）没有设计。
- 风险：**版本内容是快照，不是引用**。课程改了知识点标题，旧版本仍然显示旧标
  题——这是快照的代价，也是它可审计的代价。
- 边界：**仓储层与持久化**留给后续主题（ADR-0019）；**计划的结构性调整**（改
  目标范围）属于 Topic 50；**复习计划**属于 Topic 52；**HTTP API** 等框架选型
  确定后再做。

## 补充说明（2026-11-25）

实现中确认的事实：

1. **无法判定的区分等于没有区分。** 「重新规划」有两种含义——进度推进导致的重新
   生成，和换了一条学习路径。没有 `PlanId` 这层区分，两者在数据里长得一样，
   事后谁也说不清。**先把两种含义分开，再谈查询**。
2. **版本号比时间可靠。** 时间由调用方传入，会补录、会乱序；版本号是领域分配
   的序号。让时间决定顺序，「谁是当前版本」就变成了猜——而「当前版本」恰恰是
   最常被问的问题。
3. **跨线只能比时间。** 两条计划线之间没有共同序号，因此「哪条线是当前的」只
   能用「最近开始的那条」回答。用「版本最多的那条」会选错：用过的旧线往往版本
   更多。
4. **依据要记输入，不记输出。** 输出（计划内容）已经在版本里了；依据的价值在于
   记录**当时已经会了什么**——那才是两个版本真正的区别。结构指纹补上了第三样
   输入：课程结构变了之后，旧版本是否还成立能看出来。
5. **差异只比排程，不比措辞。** 单元的标题与理由是解释，不是排程——把它们放进
   差异里，差异就会每次都「有变化」，于是「这一版变了吗」永远答不上来。
6. **同一条规则第七次拦住了我**：不变量必须在构造期拦。首个版本带差异、版本号
   非正、版本号重复——三个错误在构造期与修订入口就被挡住。**构造期校验的价值
   就在这里：把错误挡在写代码的当下**。
