# ADR-0012: 工具回调、Citation 绑定与 HITL 的组合

- 状态：已接受
- 日期：2026-11-24

## 背景

主教材 Ch5 5.5「Extending agents with callbacks」给出两件事：

- **工具回调**：`before_tool_callbacks` / `after_tool_callbacks`。前者可以返回
  一个结果来**短路**工具执行，后者可以**替换**工具结果。5.5.3 用一个
  `before` 回调实现人工审批，5.5.4 用一个 `after` 回调压缩检索结果。
- **结构化检索**（5.4）：按文件名与目录结构取回内容，与向量检索互补。

Topic 12 的工程问题是两个：**Citation 如何绑定到具体检索片段？Tool Callback
如何与 HITL 审批组合，而不破坏事务语义？**

本项目已经有两套现成机制，问题在于它们如何相遇：

- HITL 审批在**运行时**（`AgentRuntime`）：遇到需要确认的工具，整个步骤暂停，
  等人工决定后 `resume()`。批准可以带**修改过的参数**。
- 工具执行在**调度器**（`ToolDispatcher`）：权限检查 → 参数校验 → 执行 →
  归一化。它是唯一的执行边界。

回调要加在哪里，是这两个问题的交汇点。

## 决策

**回调挂在调度器上；审批仍然留在运行时；引用做成可校验的对象。**

### 1. 回调挂在 Dispatcher 上

`ToolDispatcher` 新增 `before_hooks` / `after_hooks`。

**理由与权限检查同源**：Dispatcher 是唯一的执行边界，「新增一种工具来源
不能绕过检查」是这个项目一贯的原则。回调放在这里，意味着本地工具、MCP 工具、
结构化输出的 `final_answer` 全部受同一套回调约束。放在运行时的话，每种工具
来源都要单独接一遍——迟早会漏。

执行顺序固定：

```
权限检查 → 参数校验 → 执行前钩子 → 工具执行 → 执行后钩子 → 结果
```

- **权限检查在钩子之前**：钩子不能绕过权限。被拒绝的工具既不进入校验，也不
  触发任何钩子。
- **参数校验在钩子之前**：钩子拿到的是**已通过校验**的参数，因此钩子不必
  重复校验，也不必防御畸形输入。

### 2. 钩子的签名

```python
BeforeToolHook = Callable[[ToolContext, str, Mapping[str, Any]], Any]
AfterToolHook = Callable[[ToolContext, ToolOutcome, Mapping[str, Any]], Any]
```

**执行后的钩子也拿到参数**：钩子常要按「这次调用的是什么」做事——把检索结果
写进缓存，键就得包含查询与过滤条件。只有结果的话，键只能从结果里反推，那
是把工具的数据格式泄漏给钩子。

**钩子拿到的不是完整的 `ToolCall`**：调用 id 属于转录，调度器并不掌握。

同步与异步钩子都支持——调度器判断返回值是否可等待。

### 3. 事务语义：一条 tool_call 恰好对应一条 tool_result

这是运行时最硬的不变量。厂商 API 会拒绝「有调用没结果」的请求，而且报错完全
指不到真正的原因。回调的四种情况都必须守住它：

| 情况 | 工具是否执行 | 产出几条结果 |
|---|---|---|
| 执行前钩子返回 None | 是 | 1（工具的） |
| 执行前钩子短路 | 否 | 1（钩子的） |
| 执行前钩子抛异常 | 否 | 1（错误结果） |
| 执行后钩子替换结果 | 是 | 1（替换后的） |
| 执行后钩子抛异常 | 是 | 1（工具的，错误记进 metadata） |

**执行后的钩子失败不丢弃工具的结果**：工具已经把事情做完了，丢掉它的输出等于
白跑一趟。失败被记进 `outcome.metadata["callback_errors"]`——可观测，而不是被
吞掉。代价是：**转录里看不到回调错误**，应用层要主动查 `AgentResult.steps[*]
.outcomes[*].metadata`。

### 4. 审批在回调之前

HITL 留在运行时：遇到需要确认的工具，**本步骤的工具调用一个都不执行**，运行
暂停（`stop_reason="pending_approval"`）。恢复时只有被批准的调用才进入调度器。

因此：

- **被拒绝的调用不触发任何回调**——它根本没进调度器。
- **回调无法放行一个未获批准的调用**——回调在审批之后才有机会运行。
- **批准时修改过的参数会经过回调与校验**——它们是这次调用的真实参数。

这与主教材的差别值得记下来：教材用 `before_tool_callback` + `input()` 实现
审批，**阻塞在回调里**。本项目的审批是**暂停—恢复**：运行状态可持久化，进程
重启后还能接着等人工决定。阻塞式回调做不到这一点——它把整个执行挂在一个
终端输入上。

**混用两套审批是危险的**：如果既有运行时的 `requires_confirmation`，又有一个
阻塞式审批回调，拒绝路径会被绕过（回调先短路，运行时根本没机会看到这次调用）。
本项目因此**只保留一套**：运行时的暂停—恢复。回调只做「审批之外的事」。

### 5. Citation 绑定到切片，标记稳定

`Citation` 指向**具体的切片**（`chunk_id` + `source` + `index` + 原文），而不是
文档或章节。绑定得太粗读者无法核对，太细（精确到句子）切片粒度又不支持。

**标记按切片分配且稳定**：同一个切片无论被检索多少次，标记都不变（先到先得）。
这靠 `CitationRegistry` 实现。稳定性很重要：模型看到 `[1]` 之后会记住它指的是
哪段文字；同一段文字在不同检索里拿到不同标记，引用就失去了指代能力。

标记是**小整数**而不是哈希：模型复制 `[1]` 可靠，复制 `[1a2b3c]` 不可靠。

### 6. 引用必须可校验

`CitationValidator` 做三类检查：

1. **编造**（错误）：答案里的标记在引用集合里不存在。
2. **不支撑**（警告）：引用的切片与它标注的句子没有词面交集。
3. **无引用**（警告）：答案里一个标记都没有。

**为什么「编造」比「没有引用」更严重**：没有引用只是「没有依据」，编造引用是
「假装有依据」。后者会让读者去核对一段根本不存在的材料。

**校验是词面的，不是语义的**：判断「这段引用是否真的支撑这个说法」需要语义
理解，那是模型的事。这里做的是更基础的一层——**引用指向的东西必须真的存在**。

### 7. 引用存进执行上下文的草稿本

`StateCollector`（`core/agent/hooks.py`）把工具结果里的结构化数据收进
`ExecutionContext.state["citations"]`。

- **模型看不到**（草稿本不进模型上下文）。
- **随会话持久化**（`SessionState` 存 `state`）。
- **按执行隔离**（钩子在**调用时**从 `ToolContext.metadata` 取执行上下文，
  不是构造时绑定）——同一个调度器可以服务多次运行。

`StateCollector` 是**通用机制**，不认识引用的格式；格式由工具与应用层约定。

### 8. 工具可以直接返回 ToolOutcome

`normalize_outcome` 遇到 `ToolOutcome` 时原样采用。

**解决的问题**：检索工具既要给模型看的可读文本（带引用标记），又要给程序用的
结构化数据（引用对象）。纯文本返回拿不到结构，纯字典返回给模型的是 JSON 而
不是可读文本。

### 9. 语义检索与结构化检索是两个工具

- `SearchCourseMaterialTool`：**语义检索**。问「闭包是什么」。
- `RetrieveKnowledgeTool`：**结构化检索**。问「闭包.md 里都写了什么」。

后者不经过嵌入，因此不受嵌入质量影响；返回顺序是材料的自然阅读顺序。

**相似度下限 `min_score` 没有通用默认值**：相似度分布随嵌入模型而变，写死一个
阈值要么过滤掉全部，要么形同虚设。由调用方按自己的嵌入模型设定。

## 后果

- 好处：回调对所有工具来源统一生效；审批与回调职责清晰、互不绕过；转录完整性
  在四种回调路径下都有测试守着；引用可校验、可持久化、可跨会话核对。
- 代价：回调错误只落在 `outcome.metadata` 里，转录看不到，应用层要主动查；
  钩子不能修改参数（改了要重新校验）；执行前钩子看不到 `ToolCall`。
- 边界：**没有混合检索**（向量 + BM25）。精确标识符仍是弱项。
- 边界：**没有重排**。top-k 直接进上下文。
- 边界：**引用校验是词面的**。「引用是否真的支撑这个说法」仍要靠人或模型判断。
- 边界：**标记在工具实例的生命周期内稳定**。长期运行且不复位时，标记会持续
  增长——不影响正确性，只是不好看。
- 边界：**没有并发安全的缓存**。`RetrievalCache` 是单进程内的字典。
