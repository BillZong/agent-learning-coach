# ADR-0031: 检索评估——评估集、命中率与召回、据此调整检索

- 状态：已接受
- 日期：2026-11-26

## 背景

Day 30（Phase 2 · AI Tutor）的工程问题是：**检索评估集应该如何构建？Recall 与
相关性的差异说明了什么？**

Day 29 留下一个**未验证的假设**：「按材料类型选切分策略真的更好吗」。本主题就是
去验证它——**并且诚实地报告验证结果**。

Phase 0–1 已有的相关零件：

- `core.rag.evaluation`（Day 11）：`RetrievalCase`、`RetrievalMetrics`、
  `evaluate_retrieval`——命中率@1/3/5 与 MRR，**相关性以「来源」为粒度**；
- `core.rag.chunking`（ADR-0029）：三种切分器 + 策略集合；
- `core.rag.store`（Day 11/ADR-0030）：过滤与阈值下推、索引方案可选；
- `evals/phase0.json`：Phase 0 的评估集（运行行为，不评答案质量）。

Plan.md 的 Day 30 清单：研究 RAG Evaluation / 研究 Recall、Precision、MRR / 研究
Reranking / 建立 Retrieval Evaluation Dataset / 实现 Recall@K / 实现 MRR / 对比
不同 Chunking Strategy / 记录检索失败案例 / 根据结果调整 Retrieval / 交付 Retrieval
Evaluation Report。

## 决策

**评估集用来源粒度、人工合成；命中率与召回分开报；每条用例的详情可查；据评估结果
把检索改成「按来源去重」。**

### 1. 评估集：来源粒度、人工合成、分类

`evals/retrieval.json` + `evals/corpus/`（六份材料）。三条构建原则：

**相关性的粒度是「来源」，不是切片。** 切片 id 随切分参数与路径变化，改一次切分
策略整个数据集就失效；来源不会。这条是 Day 11 就定的（ADR-0011 已有的口径），
本主题只是把它贯彻到评估集里。

**用例分三类**：

| 类别 | 是什么 | 作用 |
| ---- | ------ | ---- |
| `lexical` | 查询与目标**共享实词** | 基线：任何嵌入都该命中 |
| `semantic` | **换词提问** | 只有真正理解语义的嵌入才命得中 |
| `multi` | 应命中**多个来源** | 测**召回**：找对一份不算找全 |

词面与语义的**差距就是嵌入模型的能力边界**。用占位级的哈希嵌入时，差距大得刺眼
——那不是检索坏了，是嵌入不够语义。

**评估集是人工合成的，必须明说。** 本项目还没有真实学习者提问。这份评估集能验证
「机制对不对」（切分、过滤、排序、去重），**不能**验证「真实用户会不会这样问」。
**把它当作可外推的结论，是这类评估最常见的误用。**

### 2. 命中率与召回@来源

| 指标 | 问什么 |
| ---- | ------ |
| **命中率@k** | 前 k 条里**有没有**相关的来源 |
| **召回@来源** | 应命中的来源**找全了没有**（命中的来源数 ÷ 应命中的来源数） |
| **MRR** | 第一个命中的排名倒数 |

**两者的差说明了什么**：

- **命中率高、召回低** = 找对了材料，却只找回了它的一部分 → **切分粒度**（一份
  材料被切成二十片，只召回一片）或向量检索的近似误差；
- **两者都低** = 查询与材料的表达对不上（嵌入质量）或过滤太严；
- **两者都高** = 这条查询没问题——**但不能推广**（语料可能太简单）。

**Precision 没有做**：在切片粒度上算 Precision 会误导——一份材料切成十片，命中它
的十片里有十片「相关」，但那是同一份材料的十片。**相关性的粒度是来源，指标就也该
在来源上算。**

### 3. 每条用例的详情：失败案例可查

`RetrievalCaseResult` 记着：期望哪些来源、实际命中了哪些、排第几、召回多少。

**只给汇总数字的评估没法指导改进**——要知道改哪儿，得看见**哪条没中、为什么**。
（`RetrievalMetrics.misses` 之前只有查询文本，看不出「期望什么、实际命中什么」。）

### 4. 策略对比的结果（以及它不能说明什么）

同一份语料、同一份评估集、同一套嵌入，只换切分器：

| 策略 | 切片数 | hit@1 | hit@3 | hit@5 | MRR | 召回 |
| --- | --- | --- | --- | --- | --- | --- |
| 按类型选 | 16 | 0.27 | 1.00 | 1.00 | 0.59 | 1.00 |
| 全部递归 | 6 | 0.55 | 1.00 | 1.00 | 0.76 | 1.00 |
| 全部定长 | 6 | 0.55 | 1.00 | 1.00 | 0.76 | 1.00 |

**两点结论**：

1. **「按类型选」切得更细**（16 片 vs 6 片）——这是机制的事实：代码按顶层定义
   切、习题按题号切，块自然更小。
2. **在这个评估集上它并不更好**——hit@1 与 MRR 都更低。

**但这个结论不成立**：占位的哈希嵌入**按词重叠打分，块越大越容易与查询共享词**
——所以这个对比**偏向大块**。再加上语料只有六份、查询十一条。**只能看趋势，不能
看绝对值**；要判定「按类型选是否更好」，需要真正的嵌入模型与真实语料。

**所以 Day 29 的假设仍然没有验证**——本主题的诚实结论是「**测不出来**」，而不是
「它更好」或「它更差」。

### 5. 据此调整检索：top_k 是「几份材料」，不是「几片」

评估暴露的问题：**切细之后，一份材料的多个碎片会互相竞争 top_k 名额**，把别的
材料挤出去（这就是「命中率高、召回低」的那个机制）。

修法：**检索结果按来源去重**——每份来源默认只保留最相关的一片。理由是相邻切片
**内容高度重叠**（切分器本来就带重叠），一起放进上下文是浪费。

因此：

- `VectorRetriever` 增加 `per_source`（默认 1）与 `oversample`（默认 3，去重前
  多取几倍候选，否则去重会把结果砍到远少于 top_k）；
- **top_k 的含义变成「几份材料」**——与学习侧的用法一致（「讲 k1 时给 3 份材料」）。

**调整的效果**（同一份评估集）：按类型选的召回 **0.77 → 1.00**，hit@3
**0.73 → 1.00**，MRR **0.51 → 0.59**。

**但这仍然是在占位嵌入器上量的**——它证明的是「去重这个修法在机制上有效」，不是
「按类型选最终更好」。

### 6. 顺带修掉的一个真 bug：pgvector 扩展必须在适配器注册之前建

集成测试在**空库**上跑时暴露：`register_vector_async(conn)` 会去查 ``vector`` 类型，
扩展没建时它抛「vector type not found in the database」——**这句话完全指不到真正
的原因**（人只会以为是版本不匹配）。

**硬顺序**：建扩展 → 注册适配器 → 建表。而且扩展**由部署建**（`CREATE EXTENSION`
要超级用户权限，应用连接串不该有）——所以：

- 应用**不建扩展**，缺扩展时给出**能照着做**的错误：「pgvector 扩展未安装：请先
  执行 CREATE EXTENSION vector（见 migrations/）」；
- 集成测试**自己先建扩展**（模仿部署步骤）。

**这条 bug 之前一直藏着**：Day 29 验证时我手工先建了扩展，于是「从空库开始」这条
路径从没被走过。**手工准备过环境，就等于替代码走完了它该走的路。**

## 后果

- 好处：「按类型选策略真的更好吗」有了**可执行的验证方式**（尽管这次的结论是「测不
  出来」）；召回成为独立指标；失败案例可定位；检索按来源去重（top_k 的含义变清楚
  了）；pgvector 的空库路径修好了。
- 代价：**评估集是人工合成的**，结论不可外推到真实用户提问。
- 代价：**占位嵌入器的偏差**让策略对比只能看趋势——要得出可信结论需要真嵌入模型
  与真实语料，而后者还不存在。
- 代价：**指标不可信时对比也不可信**。用占位嵌入器做的任何「A 比 B 好」的结论都
  站不住——**评估的前提是嵌入可信**。
- 风险：**召回低也可能只是 top_k 太小**。碎片化之后要拿到 N 份材料，名额必须放宽
  或去重——这正是本主题的修法，但反过来也说明：**指标之间会互相影响**。
- 边界：**重排、查询改写、多路召回**仍不做（ADR-0011）；**真实语料与真实嵌入**待
  有；**Precision 在来源粒度上的算法**没做（已说明为什么不做）。

## 补充说明（2026-11-26）

实现中确认的事实：

1. **评估集的大小决定对比有没有意义。** 第一版语料只有五份、每份三百来字——三种
   策略切出来的结果**完全一样**（材料比块还短，切法无从体现）。把语料加长、加上
   代码与习题（并**显式声明种类**：扩展名推断不出「习题」——`exercises.md` 推断出来
   是讲义），策略差异才显现。**评估集太小时，对比是空的。**
2. **命中率高但召回低，指向切分粒度。** 切细之后一份材料的多个碎片**互相竞争
   top_k 名额**，把别的材料挤出去。这不是嵌入的问题，是**名额**的问题——修法是按
   来源去重，而不是换嵌入。
3. **占位嵌入器会让「A 比 B 好」的结论站不住。** 哈希嵌入按词重叠打分，块越大越
   容易与查询共享词 → 对比**偏向大块**。所以「按类型选在评估集上更差」这个观察
   **不能当结论**。**评估的前提是嵌入可信**——用占位嵌入器做的任何优劣结论都不
   成立。
4. **指标之间会互相影响。** 碎片化让召回下降，召回下降让人以为检索变差了，其实
   该调的是「每份来源取几片」。**先分清是召回问题还是名额问题，再动手。**
5. **手工准备过环境，就等于替代码走完了它该走的路。** pgvector 的「从空库开始」这
   条路径因为「我手工先建了扩展」而一直没被走到，集成测试第一次从空库跑就逮到了它
   ——而报出来的错误（「vector type not found」）完全指不到真正的原因。**能照着做的
   错误信息，和不能照着做的错误信息，差的是排查时间。**
