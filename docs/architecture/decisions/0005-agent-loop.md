# ADR-0005: Agent Loop 的职责边界与停止策略

- 状态：已接受
- 日期：2026-11-19

## 背景

Topic 04 交付了 MCP 协议适配，Topic 05 要做 ReAct 执行循环。此时基础设施已经
齐备：`core/llm` 提供 `LLMClient` 协议与厂商无关的 `ToolSpec` / `ToolCall` /
`ToolResult`；`core/tools` 提供 `ToolRegistry`、`ToolDispatcher`、参数校验、超时
与结果归一化。缺的是把它们串起来的循环。

Topic 05 提出的工程问题是：**ReAct 循环在什么条件下必须停止？Stop Condition
与 Max Steps 如何配合，既避免死循环，也避免过早收敛？**

需要回答的问题：

1. 循环代码放在哪一层？放进 `core/llm` 会让模型客户端不再纯粹；放进
   `core/tools` 则让工具系统知道模型的存在。
2. 工具执行失败时，循环应该终止还是继续？
3. 停止条件有几个？彼此如何配合，谁优先？
4. 运行结果要保留什么，才能回答「为什么停了」？

参考项目 `ai-agent-from-scratch` 的 `scratch_agents/agent.py` 把循环写在 Agent
类里，工具失败直接抛异常终止，没有停止原因的概念，也没有对话记录不变量。

## 决策

**新建 `core/agent` 包，与 `core/llm`、`core/tools` 平级，只负责「模型 ↔ 工具」
的循环控制。**

### 1. 循环独立成包，不寄生在模型客户端或工具系统里

`core/agent` 与 `core/llm`、`core/tools` 平级：

- `core/llm` 保持「只管模型调用」的纯粹性；
- `core/tools` 保持「不知道模型存在」的纯粹性；
- 循环通过 `LLMClient` 与 `ToolDispatcher` 两个既有抽象协作，**不重复实现**
  任何一方的能力。

结果是：换模型不用改循环，换工具来源（本地 / MCP）也不用改循环。

### 2. 停止策略分层：自然结束是主路径，预算是兜底

```
模型不再请求工具          -> completed   （唯一成功路径）
连续工具失败超限          -> consecutive_errors
同一工具同一参数反复调用   -> repeated_call
工具调用预算耗尽          -> max_tool_calls
步数上限                  -> max_steps
整体截止时间已到           -> timeout
```

分层的理由：**只有模型自己知道任务是否完成**。任何预算都不该替代这个判断，
否则会把「正在取得进展的任务」提前掐掉——这就是「过早收敛」。

因此预算是**兜底**，只在模型不再前进时生效：它保证失控的循环一定会停下来，
而不是为了提前结束一个正在推进的任务。

### 3. 工具失败回填给模型，不终止循环

工具执行失败（参数不合法、工具内部报错、工具不存在）一律归一化成
`ToolOutcome(status="error")` 回填给模型，让它换参数、换工具或直接回答。

这与 ADR-0003 的「调用级失败归一化」是同一条语义：模型能读懂错误并据此调整
下一步。**模型能自愈的错误，就让它自愈**——这是「过早收敛」的主要防护。

只有当失败**连续发生**到一定次数（模型陷在同一个错误里，继续回填只是浪费
预算）才停止。

### 4. 更具体的停止原因优先

`repeated_call` 与 `consecutive_errors` 指向模型行为，`max_steps` 只是预算耗尽。
同时命中时上报更具体的原因——「模型在原地打转」比「步数用完了」更能说明问题。

### 5. 对话记录保持「每条 tool_call 都有对应 tool_result」的不变量

这是结果能直接作为下一轮对话输入继续的前提。

为此，**工具调用预算在步之间检查**：达到上限后不再开始新的一步；当前步内的
调用全部执行完。否则会出现「模型请求了工具但没有结果」的悬空调用，多数厂商
API 会直接报错。

### 6. 预算之外再加一个「原地打转」检测

`max_steps` 只能保证循环会停，不能保证它**及时**停：模型可能用满 12 步反复
调用同一个工具。因此额外检测「同一工具以相同参数被调用 N 次」。

它与「连续失败」检测互补：工具每次都成功但被反复调用（模型忘了自己已经查过）
只有前者能抓住。

### 7. 模型调用失败向上抛出，不重试

`LLMError` 直接抛给调用方。响应可靠性属于模型客户端的职责，循环只管工具调用
周期。重试策略是调用方的选择。

## 后果

- 好处：职责边界清晰，循环可复用；停止原因可诊断；失败回填让模型具备自愈
  能力；对话记录可直接续接；预算与「模型行为」两类停止信号分开，能区分
  「资源用完」与「模型卡住」。
- 代价：多一个包与一层抽象；`AgentConfig` 的阈值需要调参（默认 12 步、连续
  失败 3 次、重复调用 3 次）；停止原因有 6 种，调用方需要区分处理。
- 边界：**工具顺序执行，不并发**——并发需要考虑取消传播、超时传播与结果顺序
  的确定性；**上下文不裁剪**——对话记录原样保留并返回，由调用方决定如何压缩；
  **无中断与恢复**——一次运行是原子的，中途失败不会留下可续接的检查点；
  **模型调用无重试**。

## 补充说明（2026-11-19）

实现中确认的事实：

1. **工具调用失败与工具不存在都应回填**：最初担心「工具不存在」是配置错误、
   应该终止；实测模型幻觉出不存在的工具后，把它作为错误回填，模型会自行改用
   其它工具并正常完成。终止反而更早地放弃了一个模型能纠正的错误。
2. **停止原因的优先级必须显式定义**：实现初版里「步数用完」与「原地打转」
   同时命中时，测试断言失败暴露了歧义。规则定为「更具体者优先」，并补了
   对应测试。
3. **预算在步之间检查是被不变量逼出来的**：若在步内检查并中断，会留下没有
   结果的 `tool_call`，破坏「每条 tool_call 都有对应 tool_result」。
4. **「换工具来源不改循环」已被集成验证**：远端 MCP 工具接入注册表后，与本地
   工具在同一个循环里平级共存，模型看到的工具清单混在一起，走同一个调度器。
   集成时暴露了一条此前只写在文档里的约束——**远端工具的生命周期绑定在会话
   上**，会话一关，已接入注册表的远端工具立即失效。适配器因此按
   `CONNECTION_CLOSED` 错误码识别这种情况，给出明确错误而不是含糊的
   "Connection closed"。
